# Jev 슬라이딩 퍼즐

그림을 3×3으로 자르고 섞은 뒤, Jev가 한 칸씩 밀어서 맞춘다. 2026-09-19, `jev-latest`.

Jev는 그림도 보드도 못 본다(`experiments/vision`). 그래서 테트리스와 같은 분업이다: **코드가 보고 Jev가 고른다.** 밀기마다 코드가 가능한 밀기 2~3개를 열거하고 각각의 결과를 한 줄로 쓴다. Jev는 그 줄들을 읽고 하나를 가리킨다. 이 실험의 결론은 짧다: 그 한 줄에 든 숫자로 3×3을 풀면 Jev는 **결정론적 탐욕 탐색**만큼 풀고, 그 이상은 못 한다. 슬라이딩 퍼즐은 반사가 아니라 계획 문제라서.

## 설계

밀기 하나에 `sif.ask()` 요청 하나, 질문 셋:

| 질문 | 종류 | 쓰임 |
|---|---|---|
| move | Choice | 되돌리기를 뺀 가능한 밀기마다 `tile 5 slides left. distance 8 (-1), tiles home 3 (+1)`. 확률이 오른쪽 패널의 막대. |
| looping | Noul | 최근 밀기 8개를 보고 "같은 판 몇 개를 왔다 갔다 한다". 표시용 게이지. |
| progress | Score | scrambled → some tiles home → one row done → almost solved. 표시용. |

`distance`는 맨해튼 거리 + 선형 충돌×2. 상태는 `{"board": 행 3줄, "goal", "distance", "tiles_home", "recent_slides"}` 매핑. 되돌리기(직전 밀기의 반대)는 코드가 선택지에서 빼고, 남은 선택지가 하나면 묻지 않고 민다(모서리). 정확한 문구는 `brain.py`.

그림은 페이지가 캔버스로 그린 것(산과 해). "그림 바꾸기"로 아무 이미지나 넣으면 가운데를 정사각형으로 잘라 쓴다. Jev에게 그림은 전혀 가지 않는다 — 타일 번호만.

## 실행

```sh
op run --env-file=sliding-puzzle/.env.tpl -- uv run python sliding-puzzle/server.py   # http://127.0.0.1:3459
```

섞기 깊이(최단 수)를 고르고 섞기 → Jev 시작. 밀기마다 요청 하나, 약 250ms. `?demo=1&depth=14`로 열면 혼자 섞고 풀며, `?clean=1`은 컨트롤을 숨긴다.

```sh
uv run python sliding-puzzle/run_trials.py --no-jev                        # 기준선만, 키 없이
op run --env-file=sliding-puzzle/.env.tpl -- uv run python sliding-puzzle/run_trials.py   # 전부 → results.json
```

## 측정

최단 8·12·16·20수짜리 판 15개씩 60개(BFS 표로 뽑아 최단 거리가 정확), 60수 안에 풀면 성공. 모든 조건이 같은 판을 받는다.

| 조건 | 푼 판 | 8 / 12 / 16 / 20 | 최적 대비 중앙값 |
|---|---|---|---|
| random | 0/60 | 0/0/0/0 | - |
| greedy (같은 숫자, 동률 무작위) | 41/60 | 12/11/9/9 | 1.83 |
| greedy (동률을 항상 첫 번째로) | 36/60 | | |
| greedy + 본 판 금지 | 35/60 | 11/13/6/5 | 1.00 |
| **jev** | **26/60** | 11/7/5/3 | 1.87 |
| jev, 확률에서 표본 추출 | 25/60 | 9/9/5/2 | 2.50 |
| jev, 숫자 없이 | 10/60 | 5/3/0/2 | 1.32 |

- Jev 조건 1,889회 호출(강제 밀기 879회는 호출 없음). latency 중앙값 246ms, p95 344ms. 요청당 입력 576, 출력 64 토큰.
- **Jev는 숫자를 100% 따른다.** 최저 distance 선택지가 유일하게 갈릴 때(1,151회) 예외 없이 그걸 골랐다. 그러니 Jev = 탐욕 탐색이고, 남는 차이는 **동률 처리**뿐이다. 동률이 절반 가까이(738/1,889)인데 Jev는 `up`·`left`를 편애한다(up/down 동률에서 up 141 : down 26, left/right에서 left 137 : right 12). 편애가 결정론이라 빈칸이 2×2 안을 `up, left, down, right`로 도는 4주기에 갇힌다. 동률을 무작위로 깨는 탐욕이 41, 항상 첫 번째를 고르는 탐욕이 36, Jev가 26. 확률에서 표본을 뽑아도 안 도움이 된다 — 최고 확률 중앙값이 0.92라 사실상 결정론이다.
- 숫자를 빼면 10/60. 그래도 0이 아닌 건 state에 판과 목표 배열이 있어서 부분적으로 읽기 때문(최저 선택지 71%).
- `looping` 뉴런은 진짜다. 이미 본 판으로 가는 밀기에서 0.84, 새 판에서 0.60. 갇힌 걸 알지만 빠져나오진 못한다.
- 짧은 미리보기(3~6수 앞까지 가장 낮은 distance)를 코드가 계산해 줘도 탐욕이 33~44/60. 3×3에서도 국소 특징은 이 정도가 천장이다.

## 문구를 두 번 바꿨다

첫 문구는 "본 적 있는 판이면 조금 나빠도 새 판을 골라라" + 선택지에 `board seen 2x before` 태그. 3×3은 몇십 수면 상태 공간이 포화해서 거의 모든 선택지에 태그가 붙고, Jev는 +1 밀기를 45% 골랐다. 10/60. 같은 금지를 탐욕에 걸어도 41→35로 나빠진다.

둘째 문구는 태그를 빼고 "직전 밀기를 되돌리지 마라, 유일한 선택지일 때만 예외"를 지시문에. Jev는 되돌리기가 유일한 -1이면 그냥 되돌렸다(`right, left, right, left …`). 7/60. 그래서 되돌리기는 지시가 아니라 **코드가 선택지에서 뺀다** — 탐욕도 그렇게 한다. 그게 지금 26/60.

교훈은 테트리스와 같다: 규칙은 지시문이 아니라 후보 열거에 넣어야 한다. Jev는 숫자 비교는 완벽하게 하고 규칙은 숫자에 지면 버린다.

## 영상

`demo.mp4`(32초, 2560×1440)는 페이지의 데모 모드(`?demo=1&depth=12`)를 `record.mjs`로 찍은 것. 서버는 `SIF_CACHE=0`으로 띄워 요청이 전부 실제다. 12수 판을 60수 안에 푸는 게 15판 중 7판이라 9번 찍어 3번 풀렸고, 그중 가장 짧은 28수짜리를 썼다(나머지 둘은 36수·58수). 밀기 사이 650ms 쉼은 데모 모드에만 있다.

녹화기가 둘이다. `record.sh`는 bug-hunter와 같은 방식(크롬리스 Chrome 창 + `screencapture -v`)인데 메인 화면이 비어 있어야 한다 — 이번엔 다른 창이 앞에 있어서 그 창이 찍혔다. `record.mjs`는 Playwright 헤드리스 `recordVideo`. 1x 밖에 안 나오므로 뷰포트를 2560×1440으로 잡고 `body.style.zoom = 2`를 걸어 1280×720 레티나 창과 같은 픽셀을 얻는다. 프레임 간격은 고르다(25fps). Playwright는 `~/.npm/_npx/*/node_modules`에 있는 걸 `node_modules` 심링크로 빌려 쓴다.

## 한계와 다음

- 3×3만. 4×4는 BFS 표(10¹³)를 못 만드니 `random_walk`로 섞고 최단 거리 없이 재야 한다. 국소 탐욕은 4×4에서 거의 못 풀 것이다.
- Jev가 더한 것은 동률 처리인데 그게 탐욕의 무작위보다 나쁘다. Jev를 쓸 자리는 밀기 하나가 아니라 **목표 고르기**일 것이다 — "다음에 집에 보낼 타일은?"을 Choice로 묻고, 그 타일을 집에 보내는 밀기 열은 코드가 BFS로. 순서가 나쁘면 막히는 판이 생기므로 순서 판단이 측정 가능해진다.
- 그림은 장식이다. 번호 없는 그림 조각의 "이 조각이 어디 조각인가"를 코드가 이음새 픽셀 차이로 숫자화해 Jev에게 묻는 건 eye 쪽 실험감.
