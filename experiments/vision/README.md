# Jev 시각 실험: 그림을 글자로 주면 뭘 읽나

Jev의 `state`는 문자열·매핑·리스트뿐이라 이미지는 글자로 바꿔서 줘야 한다. 그러면 질문은 "어떤 철자를 읽을 수 있나"가 된다. 2026-09-19, `jev-1.13.0`.

## 설계

두 축, 모두 질문 하나짜리 `sif.decide`. state는 `{"format": 설명, "width", "height", "data"}` 매핑이고 지시문도 포맷을 다시 말해서 포맷 추측이 아니라 읽기를 잰다.

**encode** — 4×4 / 8×8 격자, 4색(red green blue yellow) / 8색(+black white cyan magenta), 조건당 이미지 25장. 색은 성분이 0/255뿐인 순색이고 선택지 설명에 `RGB (255, 0, 0), hex ff0000`을 적어 색 이름 변환이 숨은 과제가 되지 않게 했다. 같은 이미지를 9가지로 철자한다.

| 철자 | 무엇 |
|---|---|
| names | `red blue red yellow` 행 단위 |
| rgb | `(255,0,0) (0,0,255) …` |
| hex | `ff0000 0000ff …` |
| ppm | PPM P3: 헤더 + 픽셀 구분 없이 정수 나열 `255 0 0 0 0 255 …` |
| b64rgb | raw RGB 바이트의 base64. 3바이트=4글자라 픽셀 경계가 글자 경계와 맞음 |
| b64rgb_off | 앞에 0 바이트 하나. 정렬 깨짐 |
| b64bmp | 24비트 BMP (54바이트 헤더, BGR, 아래 행부터) |
| b64png0 | PNG, deflate stored(무압축) |
| b64png | 보통 PNG (deflate 9) |

질문 둘: `pos` "r행 c열 픽셀의 색은?" (위치 인덱싱 필요), `mode` "가장 많은 색은?" (인덱싱 없이 디코딩만). 목표 칸의 색은 팔레트를 순환하고 최빈색은 유일하게 만들어서 상수 답이 우연을 못 넘게 했다. 900 + 900 = 1,800호출.

**grid** — 눈이 실제로 줄 입력: 화면을 거친 격자로 줄이고 칸마다 라벨 하나(`blank text button image edge input`, blank 60% 가중). 8×8 → 16×9 → 24×14 → 32×18(576칸). `input`은 격자당 정확히 한 칸. 철자 둘: `words`(칸마다 단어) / `letters`(칸마다 글자 하나, 행이 문자열 하나). 질문 셋: `pos` "r행 c열은 뭐?", `find_row` "input이 있는 행은?", `find_col` "input이 있는 열은?" (사카드의 굵은 단계). 600호출.

**pixel** — MNIST 테스트셋 숫자별 10장, 28×28 → 14×14(2×2 평균), 5가지 철자: `binary`(`#`/`.`), `density`(` .:-=+*#%@` 10단계), `braille`(2×4 블록을 점자 한 글자), `coords`(잉크 픽셀 좌표 목록), `runlength`(행마다 종이/잉크 런 길이). Choice 0~9. 500호출.

## 결과

`summary.md`에 표 전부. 요약:

**encode `pos` (위치 읽기)**

| 철자 | 정답률 | 우연 |
|---|---|---|
| names / rgb / hex | 0.98 / 1.00 / 1.00 | 0.19 |
| ppm | 0.40 | |
| base64 5종 | 0.19~0.22 | |

**encode `mode` (최빈색)**

| 철자 | 정답률 |
|---|---|
| names / rgb / hex | 0.87 / 0.82 / 0.79 (4×4에서 0.9대, 8×8/8색에서 0.6~0.76) |
| ppm | 0.42 |
| base64 5종 | 0.13~0.17 (우연 이하, top pick이 red로 50% 쏠림) |

**grid `words`** (조건당 25)

| 격자 | pos (우연 0.17) | find_row | find_col |
|---|---|---|---|
| 8×8 | 1.00 | 1.00 | 1.00 |
| 16×9 | 0.80 | 1.00 | 0.80 |
| 24×14 | 0.68 | 1.00 | 0.56 |
| 32×18 | 0.64 | 0.88 | 0.40 (한 칸 차이 10, 두 칸 이상 5) |

`letters`는 전부 더 나쁘다(8×8 pos 0.84, 32×18 pos 0.28; find_row만 1.00 유지). 행 하나가 문자열 하나로 붙으면 토큰이 칸 경계를 지키지 않는다.

**pixel** (MNIST 14×14, 우연 0.10)

| 철자 | 정답률 | 최다 답 비율 |
|---|---|---|
| binary | 0.36 | 9 (48%) |
| density | 0.31 | 7 (32%) |
| coords | 0.22 | 8 (45%) |
| braille | 0.16 | 7 (94%) |
| runlength | 0.11 | 0 (76%) |

binary에서 숫자별: 1은 10/10, 8은 8/10, 7은 7/10, 9는 6/10. 2·3·4·5·6은 합쳐서 3/50이고 대부분 9로 답했다.

전체 2,900호출, 입력 2,131,638 + 출력 217,452 토큰, $0.10, 오류 0, 지연 중앙값 259ms.

## 해석

- **base64는 못 읽는다. 어떤 변형도.** 픽셀 경계가 글자 경계와 맞는 b64rgb도 우연이고, 정렬을 깨도 차이가 없다. 토큰 패턴 매칭조차 안 일어난다. PNG 압축 여부는 무관하다 — 그 앞 단계인 base64에서 이미 끝난다. "저해상도 이미지를 base64로 주면 되지 않나"의 답은 아니오.
- **픽셀이 글자 단위로 묶여 있으면 위치까지 정확히 읽는다.** rgb/hex는 8×8/8색에서도 `pos` 100%. 행·열을 세서 한 칸을 짚는 건 된다. names는 8×8 7~8행에서 몇 번 틀렸다.
- **같은 숫자라도 픽셀 구분자를 빼면(ppm) 절반 이하로 떨어진다.** `255 0 0 0 0 255`처럼 흘러가는 정수를 3개씩 끊어 세는 건 못 한다. 읽기 능력의 경계가 "토큰 하나 = 픽셀 하나"에 있다.
- **`#`/`.` 격자에서 원시 시각이 조금 있다.** 36%는 우연의 3.6배지만 진짜 형태 인식은 아니다. 세로 막대(1), 꽉 찬 덩어리(8), 위가 무거운 것(7)처럼 잉크 분포의 거친 통계로 구분되는 것만 맞추고, 곡선 모양으로 갈리는 2·3·4·5·6은 전부 9로 뭉갠다. 점자·런렝스는 한 답으로 붕괴한다(94%, 76%).
- **행은 세고 열은 못 센다.** 32칸 너비에서도 "input이 몇 행에 있나"는 22~25/25인데 "몇 열에 있나"는 10/25이고 틀린 것 대부분이 한 칸 차이다. 줄바꿈은 확실한 경계지만 한 줄 안에서 16개 넘게 세는 건 흔들린다. 칸을 정확히 짚는 건 너비 8~16까지, 그 위는 행 먼저 고르고 그 행을 다시 잘게 보는 두 단계로.
- **칸마다 단어 하나.** 글자 하나로 줄이면 토큰이 줄 안에서 뭉쳐서 위치를 잃는다. encode의 ppm 결과와 같은 이유: 토큰 하나 = 칸 하나여야 한다.
- **세는 건 약하다.** `mode`는 격자가 커지고 색이 늘수록 떨어진다. 인덱싱(한 칸 짚기)은 되고 집계(64칸 세기)는 흔들린다. limits 실험의 "애매한 입력에서 분배가 흔들린다"와 같은 결.

## 실행

```sh
uv run python experiments/vision/run.py --dry-run
op run --env-file=<(echo 'TYPESAFE_API_KEY="op://Agent/typesafe jev key/credential"') \
  -- uv run python experiments/vision/run.py            # --axis encode|pixel --format … --limit N
uv run python experiments/vision/report.py
```

MNIST는 첫 실행에서 `data/`로 내려받는다(gitignore). 토큰 추정은 base64에서 실측의 절반 정도로 낮게 잡힌다 — base64는 글자 1~2개가 토큰 하나다.
