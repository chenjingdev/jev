# Jev가 두는 오목

TypeSafe의 판단 모델 Jev가 백을 잡는 15×15 오목. 흑은 사람이 클릭하거나, 같은 엔진의 봇이 두거나, Claude Opus가 두거나, Gomocup 우승 엔진 Rapfi가 둔다. 규칙은 렌주: 흑은 삼삼·사사·장목 금수에 정확히 다섯으로만 이기고, 백은 제한 없이 다섯 이상. 좌표는 렌주 공식 표기(가로 a~o, 세로 1~15, 1이 맨 아래). 2026-09-19, `jev-1.13.0`.

테트리스·체스와 같은 패턴이다. **보는 것은 코드가, 고르는 것은 Jev가.** 기본 대국 모드에서는 엔진이 둘 만한 빈 자리를 잘라내어 자리마다 사실 한 줄을 붙인 "정답지"를 만들고, Jev는 그중 하나를 Choice로 고른다. 확률 분포가 보드 위에 파란 원으로 찍히고 가장 높은 자리에 백돌이 놓인다.

> **현재 버전(뉴런망)**: 수마다 Jev 요청 3번 — 감각층(위험·공격·수비·전개 Noul 4개 + 형세) → 운동층(발화한 센서마다 자리 Choice + 습관) → 판정층(중재 + 코치 거부권). 테트리스의 [`neurons-spec.md`](../tetris/docs/neurons-spec.md)와 같은 골격이고 코드는 `neurons.py`. 컨트롤의 "뉴런망" 토글을 끄거나 `?brain=single`이면 아래 설명의 단일 요청 경로(`brain.py`)로 돌아간다. 성능은 같고(아래 표) 값은 3배지만, 손으로 쓴 우선순위 목록이 사라지고 층이 보인다.

## 실행

```sh
op run --env-file=<(echo 'TYPESAFE_API_KEY="op://Agent/typesafe jev key/credential"') \
  -- uv run python gomoku/server.py            # http://localhost:3460
```

키는 서버 프로세스에만 있고 브라우저로 가지 않는다. 페이지를 열면 흑 차례. 교차점을 누르면 Jev가 백을 둔다(흑 차례에 금수 자리는 빨간 ×). 컨트롤의 "흑"을 엔진 봇·Opus·Rapfi로 바꾸면 자동 대국(`?black=bot|opus|rapfi`). Opus는 수당 5~40초 걸리고 생각한 글이 카드에 뜬다. Rapfi는 `sh gomoku/rapfi_setup.sh`로 한 번 빌드해 두면(`gomoku/rapfi/`, git 밖) 수당 0.1초에 두고 카드에 깊이와 평가치가 뜬다(`?depth=1`로 탐색 깊이 제한). `?clean=1`은 컨트롤을 숨기고, `?demo=1`은 봇을 켜고 판이 끝나면 새로 시작한다(촬영용). 엔진 테스트는 `uv run pytest gomoku -q`.

`demo.mp4`는 **Opus(흑) 대 Jev(백)** 한 판이다: 렌주, 뉴런망, 18수. `BLACK=opus FF=8 node gomoku/record_headless.mjs`로 찍고 `speedup.py`로 Opus가 생각하는 구간(수당 5~60초)만 8배속으로 붙여 실시간 6분 30초를 77초로 만들었다. 배속 구간에는 화면에 `⏩ 8배속` 배지가 켜지고, Jev 구간은 실시간이다. 첫 테이크에서 백 승(Opus 상대 승률이 반반이라 운이 따랐다). 마지막 수에서 Opus의 생각 칸에 "이론상 패배입니다… 유일한 기회는 백이 실수하면"이 뜨고, 피질에는 위험 뉴런의 `j7` 7% 대 공격·습관의 `i6` 93%. 재촬영: 서버를 띄우고 위 명령, 또는 봇 상대 실시간은 `node gomoku/record_headless.mjs`.

## 구조

| 파일 | 무엇 |
|---|---|
| `engine.py` | 순수 함수. 보드, 승리 판정, 렌주 금수(`forbidden`), 자리마다 패턴 분석(five / open four / four / open three / three / open two, 공격과 방어; `shape`는 `X.XXX` 같은 띈 모양도 "다섯을 완성하는 빈칸 수"로 읽는다), 후보 열거와 순위, 봇. `vcf`/`deepen`은 2수 읽기(연속 넷 강제승) — 재보니 해로워서 기본 off. |
| `brain.py` | 요청 하나. 질문 셋과 state를 만들고 SDK를 직접 불러 usage·지연을 받는다. |
| `server.py` | 정적 페이지 + `POST /api/jev`(단일 요청), `/api/sense`·`/api/motor`·`/api/verdict`(뉴런망, 층마다 요청 하나 — 페이지가 요청이 나가고 도착하는 걸 층별로 보여주기 위해), `/api/bot`, `/api/opus`, `/api/forbidden`. 게임 상태는 브라우저에 있다. |
| `index.html` | 캔버스 보드와 피질 SVG. 수마다 테트리스 스펙 6.5의 타임라인: R1이 나가면 흰 스캔라인이 보드를 훑고 감각층으로 점선이 흐름 → 도착하면 센서 원이 활성도만큼 점등(0.5 이상 발화 글로우) → R2가 나가면 발화 원에서 운동층으로 점선 흐름 → 도착하면 제안이 80ms 간격으로 보드에 **뉴런색 와이어 + 알약**으로, 패널엔 칩과 시냅스 선 → R3 도착 시 와이어가 고스트 돌로 바뀌며 %가 0에서 카운트업, 중재×(1−거부) 막대, 거부된 제안은 빨간 빗금과 `VETO`, 선택은 흰 테두리 펄스 → 600ms 뒤 착점. 답이 오기 전에 움직이는 건 점선 흐름뿐이고 밝기는 전부 돌아온 숫자다. |
| `rapfi.py` | [Rapfi](https://github.com/dhbloo/rapfi)(Gomocup 우승 엔진, GPLv3, 가중치 CC0)를 흑으로: 별도 프로세스에 피스크보크 프로토콜로 국면을 보내고 `x,y` 한 줄을 받는다. 렌주 룰(`INFO rule 4`), 수당 시간, 깊이 제한. 우리 엔진이 심판이라 거부된 수는 기록하고 랜덤 폴백. `rapfi_setup.sh`가 클론·빌드해 `gomoku/rapfi/`에 둔다(저장소에는 안 들어감). |
| `opus.py` | Claude Opus를 흑으로: 이 맥의 `claude -p`(구독) 호출, 렌주 규칙을 시스템 프롬프트에, 답은 `MOVE: h8`. 불법·금수는 한 번 되묻고 랜덤 폴백. 페이지(`/api/opus`)와 `play.py`가 같이 쓴다. |
| `neurons.py` | 테트리스의 3층 뇌를 옮긴 것: 감각(위험·공격·수비·전개 Noul) → 운동(발화한 센서마다 Choice + 습관) → 판정(중재 + 코치 거부권). 수당 요청 3회. 아래 "엔진을 얼마나 빼도 되나". |
| `play.py` | 브라우저 없이 여러 판을 돌려 수치를 남긴다 → `results.json`. `--sheet bare\|facts\|labelled`·`--brain neurons`·`--cap`은 `results_ablation.json`·`results_big.json`. `--black opus\|opus-sheet`는 Claude Opus를 흑으로(`claude -p`, 아래), `--black rapfi`는 Rapfi(`--rapfi-ms`, `--rapfi-depth`), `--white bot|rapfi`는 Jev 대신 봇·Rapfi를 백으로, `--black jev --rule free`는 Jev가 선수(색 반전 보드) → `results_rapfi.json`. |
| `sight.py` | Jev가 판을 보는지 직접 검사: 실제 봇 대국에서 백의 닫힌 넷 국면을 추출해 "다섯을 완성하는 자리"를 빈칸 전체·근처·정답지 24개 중에서 고르게 한다. 보드 표기(ASCII 격자 / 좌표 목록 / 착수 기보 `1.h8 2.i9`)도 바꿔 가며 → `results_sight.json`. 화면은 `/sight`(`sight.html`). 아래 "Jev는 판을 보는가". |
| `record.sh` | 크롬리스 Chrome + `screencapture -v` 30fps 촬영(bug-hunter 방식). |
| `record_headless.mjs` | Playwright 녹화기로 화면 없이 촬영. 판이 끝날 때까지 한 테이크, 백이 이길 때까지 반복. `?scale=1.5`로 1920×1080을 1280×720처럼 배치. `BLACK=opus FF=8`이면 페이지의 국면 타임라인(opus/jev/idle)을 `takeN.json`으로 남긴다. |
| `speedup.py` | 타임라인대로 Opus가 생각하는 구간만 N배속으로 잘라 붙여 `demo.mp4`. 그 구간엔 페이지가 `⏩ 8배속` 배지를 띄운다(`?ff=8`). |

### 정답지

돌에서 두 칸 안의 빈 자리를 전부 분석해 점수순 상위 24개를 남긴다(limits 실험: 선택지 폭이 넓어지면 Choice가 흔들린다). 이기는 자리·막아야 할 자리·URGENT 자리는 24개 밖이어도 끼워 넣는다. 자리마다 설명 한 줄:

```
j10   MUST BLOCK: black completes five here on the next move
h8    DOUBLE THREAT: makes a four and an open three at once; black cannot stop both
i7    URGENT: black plays here next and gets an open four (anti-diagonal) that cannot be stopped; block now
h7    makes an open three (anti-diagonal); also takes a point where black could start an open three (vertical)
g6    makes an open two (vertical); 4 adjacent stones
```

이 문장이 곧 Jev가 보는 전부다. state에는 보드(칸마다 기호 하나를 띄어 쓴 `words` 철자 — vision 실험에서 너비 16의 위치 정답률 0.80), 마지막 수, 흑과 백이 각각 이미 가진 열린 셋·넷 목록도 넣지만 결정은 설명이 끌고 간다.

### Jev에게 묻는 것

요청 하나에 질문 셋. 서로의 답은 보지 못한다.

| 질문 | 종류 | 쓰임 |
|---|---|---|
| move | Choice | 후보 id마다 설명을 붙여 하나를 고르게 한다. 지시문에 우선순위를 번호로 적었다: 다섯 완성 → MUST BLOCK → 열린 넷·DOUBLE THREAT(이기는 수) → URGENT → 넷·열린 셋 만들기. 그리고 "막기만 하면 진다, 강제된 게 없으면 흑이 셋을 *시작할* 자리를 미리 막지 말고 내 줄을 키워라". |
| threat | Noul | "흑이 다음 수에 다섯을 만든다" — 위협 감지 미터. |
| standing | Score | 흑 우세 / 대등 / 백 우세 — 형세 미터. |

정확한 문구는 `brain.py`의 `MOVE`, `THREAT`, `STANDING`. 현재 기본인 뉴런망에서 실제로 묻는 것은 `neurons.py`의 `SCENE` + 센서 4개(`SENSE`), 운동 뉴런 4개(`MOTOR`) + 습관(`MOVE_FACTS`), `ARBITRATE`, `VETO`, 그리고 형세 `STANDING`이다.

## 수치

## 엔진을 얼마나 빼도 되나

"엔진 말고 포석만 주면 안 되나, 테트리스처럼 센서가 발동하고 그에 맞는 행동을 고르게 하면?"에 대한 답. `play.py --sheet …`, `--brain neurons`, 봇 흑 8판씩, `results_ablation.json`. "엔진"은 둘로 갈린다 — **보는 것**(보드를 패턴 사실로 바꾸기)과 **판단하는 것**(MUST BLOCK 같은 판정 단어, 번호 매긴 우선순위). 조건마다 Jev에게서 뺀 것이 다르다.

| 조건 | Jev가 받는 것 | 전적 | MUST BLOCK 막음 | URGENT 막음 | 엔진 1순위 일치 | 수당 토큰·지연 |
|---|---|---|---|---|---|---|
| `bare` 포석만 | 보드 + 좌표 24개 | 0승 8패, **전부 9수** | 1/8 | 0/8 | 0/32 | 1.2k · 256ms |
| `facts` 사실만 | 설명, 판정 단어·우선순위 없음 | 0승 8패, 14수 | 4/11 | 9/15 | 20/52 | 1.5k · 261ms |
| `labelled` (기본) | 사실 + 판정 단어 + 우선순위 | 3승 5패, 45수 | 52/52 | 45/45 | 106/178 | 1.8k · 260ms |
| 뉴런 + `facts` | 센서 4개 → 역할 지시문 + 사실만 | 0승 8패, 20수 | 13/16 | 15/21 | 39/76 | 5.6k · 799ms |
| 뉴런 + `labelled` | 센서 4개 → 역할 지시문 + 판정 단어 (우선순위 없음) | **3승 5패**, 45수 | 45/45 | 43/46 | 126/176 | 5.9k · 801ms |

8판은 표본이 작아서 위 두 생존 조건은 **24판씩** 더 돌렸다(`results_big.json`, seed 100~):

| 조건 | 전적 | MUST BLOCK | URGENT | 이기는 자리 | 엔진 1순위 일치 | 위험 센서 발화 (필요할 때 / 아닐 때) |
|---|---|---|---|---|---|---|
| 단일 요청 `labelled` | 4승 19패 1미완 | 174/175 | 141/144 | 4/5 | 314/561 (56%) | – |
| 뉴런 + `labelled` | 5승 19패 | 151/155 | 138/141 | 5/5 | 322/478 (67%) | 296/296 / 1/182 |

8판의 3승 5패는 운이 좋았던 것이고, 선수인 봇 상대 승률은 두 쪽 다 **20% 안팎**으로 같다. 뉴런판이 놓친 강제수 7개는 전부 중재가 후원자 많은 제안을 고르거나 코치가 맞는 수를 거부한 경우다.

**봇은 얼마나 센가.** 봇끼리 40판: 흑 26 · 백 13 · 미완 1. 랜덤 상대 40:0. 같은 알고리즘끼리도 선수가 65%를 가져가므로, Jev(백)의 20%는 "후수 불리 + 같은 엔진의 탐욕 봇을 백에 앉혔을 때(33%) 대비 약간의 손해"다. 봇 자체는 1수 읽기 탐욕이라 수읽기가 없다.

**판정층 문구 수정(v2).** 놓친 7개가 전부 판정층이라 세 줄을 고쳤다: 중재의 제안 설명에 센서 활성도를 적고(`DANGER (fired at 0.91) proposed this`), 중재 지시문에 "다섯 완성·방어가 최우선, 그 다음은 강하게 발화한 위험·공격이 수비·전개·습관보다 앞서며 **후원자 수로 정하지 않는다**", 코치 지시문에 "다섯을 완성하거나 막는 수는 절대 멈추지 마라". 엔진은 건드리지 않았다.

| 조건 (같은 seed 24판) | 전적 | MUST BLOCK | URGENT | 엔진 1순위 일치 | 수당 토큰 |
|---|---|---|---|---|---|
| 뉴런 v1, 후보 24 | 5승 19패 | 151/155 | 138/141 | 67% | 5.3k |
| 뉴런 v2, 후보 24 | **9승 15패** | 135/138 | 137/138 | 68% | 5.4k |
| 뉴런 v2, 후보 12 | **9승 15패** | 134/134 | 143/143 | 73% | 4.6k |

37.5% — 후수 봇 기준선 33%를 넘었다. 후보 12개가 강제수를 하나도 안 놓치고 토큰도 적어 뉴런판의 기본이 됐다.

- **포석만 주면 우연이다.** 흑이 다섯 개를 그냥 놓는다(9수 = 최단). vision 실험 그대로: 보드 문자열에서 위치·패턴을 읽지 못한다. 후보를 24개로 걸러 준 것도 엔진의 도움인데 그래도 이렇다.
- **사실을 줘도 판단은 못 한다.** "black completes five here on the next move"라고 써 줘도 그 자리를 절반도 못 고른다. 이기게 하는 것은 사실이 아니라 **판정 단어와 우선순위**다.
- **센서는 완벽하다.** 위험 뉴런(요약 사실만 봄, 후보 목록은 안 봄)은 막아야 할 때 91/91 발화, 아닐 때 2/85. 테트리스의 감각층이 오목에서도 그대로 된다.
- **그래도 자리는 표식이 짚어 준다.** 센서가 "위험"이라고 해도 운동 뉴런이 표식 없는 문장에서 그 자리를 못 찾고(p 0.2~0.4), 찾아도 중재가 후원자 많은 제안을 고르거나 코치가 맞는 수를 거부한다(뉴런+facts 9번 놓친 수 전부 이 둘). 표식을 돌려주자 45/45 — 그리고 **번호 매긴 우선순위 없이** 단일 요청판과 같은 3승 5패. 즉 "무엇이 급한가"는 센서가 대신할 수 있고, "어느 자리인가"는 엔진의 판정 단어가 있어야 한다.
- 값은 3배: 요청 3회, 토큰 3.3배, 지연 0.8초. 얻는 것은 손으로 쓴 우선순위 목록이 사라지는 것과 층이 보이는 것(24판에서 습관을 뒤집은 수 68/478, 거부권 34번).

## 렌주 금수와 2수 읽기

Opus에게 진 판이 전부 4→33 콤보(넷으로 한 수 강제하고 그 사이 삼삼 완성)라서 둘을 넣었다. 봇은 점수표를 그대로 두고(2수 읽기는 Jev 정답지에만), 금수는 양쪽에.

**렌주 금수** (`forbidden`): 흑은 삼삼·사사·장목 금지, 정확히 다섯으로만 승리. 봇끼리 40판이 자유룰 흑 26:백 13에서 **20:20**으로 — 이 봇 수준에서 선수 이점은 금수 규칙이 통째로 가져간다. 처음엔 패턴이 연속 돌만 봐서 띈 삼(`X.XX`)·띈 넷(`X.XXX`)이 안 보였는데, Rapfi를 붙이자 드러났다(아래). 지금은 "다섯을 완성하는 빈칸이 몇 개냐"로 넷을, "한 수 더 두면 열린 넷이 되느냐"로 열린 삼을 읽는다. 남은 단순화: 삼을 열어 주는 그 수가 금수인 경우는 따지지 않는다.

**2수 읽기** (`vcf`, `deepen`): "넷 → 상대 강제 응수 → 결정타(다섯·열린 넷·쌍수)"를 찾아 백에는 `FORCED WIN`, 흑의 것이면 시작점·응수점·끝점에 표식. 49수 국면에서 11ms. 처음엔 깊이 3에 표식을 문장 **맨 앞**에 붙였더니 24판 **0승** — "한 템포 뒤 강제승" 표식이 "당장 열린 넷"보다 급해 보였고 Jev는 앞머리 표식에 반응한다. 판정 표식을 모든 설명의 맨 앞으로 통일하고 2수 읽기 방어를 `WATCH`로 낮춰 맨 뒤에 붙이자 회복됐지만, 24판으로는 여전히 없는 쪽이 낫다.

| 조건 (렌주, 같은 seed 24판, 뉴런 v2 후보 12) | 전적 | MUST BLOCK | URGENT | 엔진 1순위 일치 |
|---|---|---|---|---|
| 2수 읽기 없음 | **13승 11패** | 210/212 | 148/153 | 77% |
| 2수 읽기 (깊이 1, WATCH) | 9승 15패 | 208/208 | 162/165 | 77% |
| 2수 읽기 없음, 띈 모양을 읽는 엔진 (2026-09-20, seed 100~) | 13승 9패 2미완 | 189/189 | 168/169 | 77% |

그래서 기본은 **렌주 + 2수 읽기 없음**. 봇끼리 50%인 규칙에서 Jev(백) 54% — 같은 엔진의 탐욕 봇과 대등하다. Rapfi 때문에 엔진이 띈 넷·삼을 읽게 된 뒤에도(아래) 같은 자리다: 13승 9패. 8판 표본은 세 번 다 속였다(3승 5패→20%, 7승 0패→54%, 6승 2패→37%); 이 프로젝트에서 8판은 방향만 보고 결론은 24판으로 냈다.

## Opus와 두면

"봇 알고리즘이 오목엔 과분하게 잘 맞는 거 아닌가, Opus랑 두면 공평하지 않나"에 대한 답. `play.py --black opus|opus-sheet`, Claude Opus를 이 맥의 `claude -p`(구독, API 키 없음)로 불러 흑을 두게 한다. 보드는 Jev와 같은 `words` 철자로 주고, 짧게 생각한 뒤 `MOVE: h8`로 답하게 한다. 불법 좌표는 한 번 되묻고 그래도 안 되면 랜덤 합법수로 대체하며 기록에 남긴다. Jev는 뉴런 v2·후보 12, 8판씩(`results_opus.json`, seed 300~).

| 흑 (선수) | 전적 (흑 : Jev) | Jev의 강제수 | 흑의 수당 시간 | 흑의 불법수 |
|---|---|---|---|---|
| 엔진 봇 (24판) | 15 : 9 | 277/277 | 0 | – |
| Opus, 보드만 | **4 : 4** | 36/39 | 중앙값 15초 | 0 (되물음 1) |
| Opus + Jev와 같은 정답지 | 5 : 3 | 86/86 | 중앙값 29초 | 7 (되물음 15) |
| Opus + 같은 정답지, 렌주로 재측정 (2026-09-20) | **6 : 2** | 64/64 | 중앙값 16초 | 3 (되물음 11) |

- 선수를 쥔 Opus는 Jev와 반반이다. 같은 자리의 탐욕 봇(62.5%)보다 약하다 — 봇이 세서가 아니라 텍스트 보드에서 LLM이 넷·셋을 놓치는 일이 실제로 있어서. 접전은 34~39수까지 갔다.
- 정답지를 줘도 Opus는 세지지 않았다(8판이라 5:3은 오차 안). 대신 두 배 느려지고 불법 좌표가 7번 나왔다 — 목록이 길어지자 좌표를 헷갈린다.
- 시간: Opus 15~29초/수, Jev 0.8초/수(요청 3회). Jev는 수읽기를 못 하지만 "지금 뭐가 급한가"를 0.3초에 판단하고, 엔진이 사실을 대 주면 Opus와 대등하게 둔다.
- 렌주로 바꾸고 정답지 우선순위 문단까지 색만 바꿔 똑같이 주자(공정 조건) Opus가 6:2. Jev는 강제수를 한 번도 안 놓쳤는데(64/64) 진다 — 같은 정답지 위에서 Opus는 두세 수 뒤 조합을 읽고 Jev는 표식만 따른다. 이것도 8판이라 오차 안이지만 방향은 일관된다.
- 8판은 작다. 24판이면 Opus 호출 시간상 한 시간쯤 걸린다. 그래서 검증된 엔진을 붙였다 — 다음 절.

## 검증된 엔진과 두면: Rapfi

"Opus는 너무 느린데, 검증받은 봇 AI는 없나"에 대한 답. [Rapfi](https://github.com/dhbloo/rapfi)는 Gomocup(오목 AI 대회) 우승 계열의 오픈소스 엔진(알파베타 + NNUE, GPLv3)으로 렌주 룰 가중치가 따로 있다. `rapfi_setup.sh`가 이 맥에서 NEON으로 빌드하고, `rapfi.py`가 수마다 프로세스를 띄워 피스크보크 프로토콜로 국면을 보낸다. 수당 0.1초, 깊이 6~7에서 답이 온다. 코드는 우리 것과 섞이지 않고 파이프로만 만난다.

붙이자마자 나온 건 승패가 아니라 우리 쪽 결함 둘이었다. 먼저 돌 순서: Rapfi는 BOARD의 첫 돌을 흑으로, 색은 교대로 온다고 가정하므로 행 순서로 보내면 엉뚱한 패스가 끼어 "외통 +M3"을 외치며 이상한 데를 두고, 우리 봇 상대로 75수짜리 판을 7:4로 겨우 이겼다. 흑백 교대로 보내니 27수에 12:0. 다음은 **우리 심판의 오심**: 그 뒤 36판에서 Rapfi의 수를 우리 `forbidden`이 7번 "삼삼"이라고 거부했는데(전부 Rapfi가 "+M5, 5수 외통"을 보던 순간), 재현한 국면은 `X.XXX`(띈 넷) + 열린 삼, 즉 합법인 4-3이었다. 우리 패턴이 연속 돌만 세어 띈 넷을 삼으로 읽은 것. 이걸 고치자(`shape`) 이후 120판에서 거부 0, 그리고 Jev의 정답지도 같은 눈으로 보게 됐다.

- **Jev는 우리 봇과 대등하고(13:11), 우리 봇은 검증된 엔진 앞에서 0승이다.** 앞 절의 "봇이 오목에 과분하게 잘 맞는 건 아닌가"는 아니다 — 탐욕 봇은 약하다. Opus가 그 봇과 반반이었던 것이지, 봇이 세서 Jev가 밀린 게 아니다.
- **깊이 1 Rapfi도 24:0.** 탐색을 거의 꺼도(NNUE 평가 한 겹) 진다. 정답지의 한 수 뒤 사실로는 4-3·VCT 같은 두세 수 조합을 볼 수 없고, Jev가 표식을 100% 따라도(강제수 147/149) 표식이 붙기 한 수 전에 이미 끝나 있다. 핸디캡 `strength`는 랜덤성 주입인데 이 상대들에겐 거의 안 먹힌다.

## Jev는 판을 보는가

2026-09-20 검토에서 기존 실험의 입력 오류를 발견했다. 기존 생성기는 흑 6개·백 8개를 놓고 백 차례라고 했고, 임의로 섞은 돌을 교대 기보로 바꾸면서 13번째 백돌을 흑돌로 전달했다. 기존 20국면을 재현하면 전부 한 돌의 색이 달라지고, 10국면에서는 채점용 정답에 둬도 다섯이 완성되지 않는다. 따라서 기존 기보 성적과 “공식 기보도 못 읽는다”, “문자열만 본다”, “정답지가 필수임을 입증했다”는 결론을 철회한다. 기존 데이터는 `results_sight_invalid_v1.json`에 오류 감사용으로 보존하며 유효한 비교 결과로 사용하지 않는다.

수정한 `sight.py`는 중앙 h8부터 기존 전술 봇끼리 실제로 흑백을 번갈아 두게 한다. 공격·방어를 거친 대국에서 백의 연속 넷과 유일한 완성점이 있는 백 차례를 추출한다. 흩어진 잡음 돌을 추가하거나 착수 순서를 사후에 만들어내지 않는다. 흑돌은 백돌보다 정확히 하나 많으며, 실제 수순을 재생해 보드·돌 색·차례·정답을 요청 전에 검증한다. 합법성은 이 프로젝트의 단순화된 렌주 심판 기준이다. 대회 오프닝 절차나 완전한 렌주 금수 판정을 구현했다는 뜻은 아니다.

화면 `/sight`의 기본값은 **흑 차례 + 번호 없는 연속 수순 + 정답과 다양한 후보 5개 좌표**다. 돌에 수 번호를 표시하고 전체 수순도 보여준다. 같은 국면을 격자·색별 좌표 목록·색을 적은 기보·번호와 좌표만의 기보로 표현해 비교한다. 모든 빈칸 조건에는 엔진 설명이나 후보 순위가 들어가지 않는다. 선택지는 모든 빈칸·돌 근처·엔진 후보 24개·정답과 다양한 후보 5개이며, Jev에게는 모두 좌표만 전달한다.

## 표기·후보 순서·회전 재검증 (2026-09-20)

`sight_diagnostics.py`로 같은 20국면을 고정하고 6표기 × 6조건 = 720요청을 실행했다(`jev-1.13.0`, $0.1011). 모든 조건은 **전체 빈칸, 설명 없는 좌표 선택지**다. 기존 번호 기보, 번호 없는 연속 수순, 공백 수순, 색별 좌표, SGF를 비교한다. SGF는 출력 후보가 a1 형식인 경우와 SGF 두 글자 좌표인 경우를 따로 측정해 변환 부담을 분리한다.

번호 없는 연속 수순은 [RenjuNet 실제 대국 페이지](https://www.renju.net/tournament/3627/game/190997/)의 표기 방식을 참고했고, SGF는 [명세](https://www.red-bean.com/sgf/properties.html)의 `GM[4]FF[4]SZ[15]`와 `B`/`W` 노드를 사용한다. 외부 대국을 API에 보내지 않았으며 기존 봇 대국의 같은 내용을 각 형식으로 직렬화했다. `1.h8 2.…`는 우리가 번호를 붙인 표기이지 유일한 공식 저장 형식이 아니다. 15×15 교차점은 [국제 렌주 규칙](https://www.renju.net/rifrules/)과 일치한다.

조건은 원본, 동일 요청 재실행, 후보 순서만 결정적으로 섞기, 90/180/270도 회전이다. 회전할 때 기보·정답·모든 후보 좌표를 함께 돌리고 후보의 순번은 보존한다. 각 요청은 무작위 순서로 실행한다. 회전 일치율은 선택을 역회전해서 원본 선택과 비교하며, **정답률과 다른 지표**다.

|---|---|---|---|---|
| 번호 기보 | 0/20 | 19/20 | 4/20 | 7/60 |
| 번호 없는 연속 수순 | 1/20 | 16/20 | 5/20 | 9/60 |
| 번호 없는 공백 수순 | 1/20 | 16/20 | 3/20 | 7/60 |
| 색별 좌표 목록 | 3/20 | 13/20 | 7/20 | 16/60 |
| SGF → a1 좌표 | 1/20 | 16/20 | 4/20 | 8/60 |
| SGF → SGF 좌표 | 0/20 | 17/20 | 7/20 | 5/60 |

번호 기보에서는 동일 요청을 다시 보내면 19/20에서 같은 수를 골랐지만, 후보 순서만 바꾸면 4/20만 같은 수였다. 세 방향 회전에서 원래 선택과 대응하는 위치를 고른 경우는 7/60이었다. 따라서 이번 입력에서는 단순 재실행 변동보다 후보 배열 순서의 영향이 크고, 회전에 따른 선택 일관성도 낮다. 표기를 바꾸거나 SGF 좌표 변환을 없애는 것만으로 높은 정답률은 나오지 않았다. 이 결과는 판 크기 오류나 특정 표기 하나만의 문제가 아니라 현재 질문·모델 조합이 위치 관계를 안정적으로 처리하지 못한다는 해석을 지지한다. 내부 알고리즘, 학습 기보 형식, 다른 질문의 성능까지 단정하지 않는다. 낮은 정답률 때문에 회전 일치율은 대부분 오답 선택의 일관성을 측정한다.

독립 검사기는 엔진의 좌표·승리 판정 함수를 재사용하지 않고 각 표기를 다시 읽어 보드와 정답을 검사했다. 20국면 × 4방향 모두 일치했다. `results_sight_diagnostics.json`에 요청 본문(키 제외), 모델의 원래 선택, 전체 응답 확률, 원본 국면, 조건과 요약을 저장했다. 720요청 모두 좌표 설명이 비어 있고 응답 확률의 좌표 집합이 선택지와 일치함을 확인했다. 원본/순서 변경 비교는 전송한 후보 순서에 관한 것이며 서비스 내부 처리 방식은 알 수 없다.

화면 `/sight`에서 새 표기·판 회전·후보 순서 섞기를 직접 선택할 수 있다. 화면의 기본 후보 순서는 회전된 판에서 새로 열거하므로, 후보 순번까지 고정한 위 통계는 배치 스크립트로 재현한다.

## 정답 주변 다섯 개 실험 — 폐기한 후보 방식 (2026-09-20)

같은 20국면에서 전체 빈칸(평균 175개)과 붙어 있는 빈칸 5개를 6표기로 비교했다. `five`는 정답을 포함하는 빈칸 다섯 개를 가로·세로·대각선 인접으로 연결하고, 작은 영역에 모이도록 선택한다. 후보 전술 점수는 쓰지 않고 전달 순서는 결정적으로 섞는다. Jev에게는 모든 후보를 `{좌표: null}`로 주며 정답·수의 설명을 전달하지 않는다. 보드와 질문은 같은 것을 사용한다. seed 1의 후보 집합은 `b5 c5 d5 e5 f5`이고 실제 전달 순서는 `c5 d5 f5 b5 e5`다.

| 표기 | 전체 빈칸 | 인접한 5개 |
|---|---|---|
| 번호 기보 | 1/20 | 8/20 |
| 번호 없는 연속 수순 | 0/20 | 11/20 |
| 번호 없는 공백 수순 | 1/20 | 8/20 |
| 색별 좌표 목록 | 2/20 | 9/20 |
| SGF → a1 좌표 | 1/20 | 8/20 |
| SGF → SGF 좌표 | 0/20 | 9/20 |

5개 조건에서는 8~11/20(40~55%)로 올라갔다. 5개에서 균등 무작위 선택의 기대 정답률은 20%다. 다만 **후보 수 감소와 정답 주변으로 범위를 좁힌 효과를 함께 측정**했다. 입력 순서도 전체 빈칸은 행 순서, 다섯 개는 섞인 순서이므로 개수만의 인과 효과로 해석하지 않는다. 정답을 포함하도록 후보를 구성한 실험이며, Jev가 스스로 그 영역을 찾아냈다는 뜻도 아니다. 원본 국면·다섯 후보·측정값은 `results_sight_five.json`에 저장했다(240요청, $0.0206).

이 방식은 정답 위치를 후보 생성에 사용해 영역을 알려주는 문제가 있어 폐기했다. 위 표와 `results_sight_five.json`은 이전 방식의 기록이며, 현재 `five`로 재현되지 않는다.

## 정답과 다양한 착수 후보 다섯 개

현재 `five`는 정답 한 칸에 공격·수비·포진 후보를 하나씩 더하고, 마지막 한 칸은 흑이면 금수 후보, 백이면 다른 주변 착수 후보를 넣는다. 각 역할에 맞는 점수를 가진 후보 중에서 이미 선택한 자리와 떨어진 곳을 우선해 여기저기 분산한다. 해당 역할의 모양이 없으면 주변 빈칸으로 대체한다. 후보를 정답 근처 한 줄에 모으지 않는다. 최종 다섯 좌표는 순서를 섞고 설명은 모두 `null`로 보낸다. 역할·점수·어느 자리가 금수인지·정답 표시는 Jev에게 전달하지 않는다.

삼삼·사사·장목 금수는 흑에게만 적용된다. 화면에 흑/백 차례를 추가했고, 기본은 흑 차례와 번호 없는 연속 수순이다. 흑 국면도 흑백 교대 봇 대국에서 추출하며, 흑백 돌 수가 같고 합법적인 즉시 승리점이 하나 있는 국면을 쓴다. 금수 후보가 있는 국면을 고르고, 삼삼이 있으면 우선한다. 실제 착수 수순에는 금수를 두지 않고 선택지에만 오답으로 포함한다. 백에게는 삼삼을 금수라고 표시하거나 가르치지 않는다.

배치 실험은 `sight.py --player black --kinds five --reps compact`로 흑 차례를 지정할 수 있다.

금수 판정은 기존 엔진의 단순화된 렌주 심판 기준이다. 가짜 삼의 재귀적 예외와 같은 완전한 대회 규칙 검증을 대신하지 않는다. 모델에는 흑의 일반 금수 규칙만 설명하며 특정 좌표에 대한 판정은 알려주지 않는다. `target_offered`는 평가용 응답 필드이고 후보 다섯 개에 항상 정답이 들어간다. 이전 후보 방식의 성적은 현재 방식의 성능으로 사용하지 않는다.

## 기초 단계별 실험: 좌표·색과 즉시 승리 (2026-09-20)

## 0단계: 색을 묻지 않는 돌 위치 확인 및 프롬프트 비교

사용자 지적에 따라 “백돌 찾기”에 앞서 색 무관의 돌 존재 확인을 분리했다. `occupancy.py`는 같은 9수/29수 짝에서 돌이 있는 좌표 하나(흑·백 균형)와 빈칸 네 개를 제시한다. 기존 단계의 백돌 1개·흑돌 2개·빈칸 2개와 다른 문제다. `moves`는 계속 번호 없는 연속 수순이며 입력 상태·후보·순서는 프롬프트 간 동일하다. 정답·설명은 전달하지 않는다.

프롬프트 네 가지를 seed 1~10의 20문제로 비교했다: 짧은 영어, 짧은 한국어, 좌표 경계 명시, 기존 긴 설명. **네 가지 모두 20/20**이었다. 정답률 우선·동률이면 문구 길이 순이라는 선택 규칙으로 다음 한국어 문구를 골랐다.

> moves에 실제로 등장하는 착수 좌표를 선택하세요. 돌의 색은 구분하지 마세요.

선택 후 seed 11~20의 별도 20문제에서 짧은 문구와 기존 긴 문구를 비교했다. 두 문구 모두 원본 20/20, 동일 요청 반복 20/20, 후보 순서 변경 20/20이었다. 9수/29수 각각 10/10이었다. 프롬프트 선정 80요청과 별도 검증 120요청, 총 200요청 모두 적중했고 비용은 $0.0041이었다. 별도 검증의 60회는 20문제의 반복·변형이지 독립 문제 60개가 아니다.

이는 이번 형식과 표본에서 돌이 놓인 좌표의 존재 확인은 잘 된다는 증거다. 기존 긴 프롬프트도 만점이므로 프롬프트 수정으로 정확도를 개선했다고 주장할 수 없다. 앞선 낮은 성적은 색 구분을 요구한 다른 과제였으며, 이를 단순히 좌표를 못 읽는다고 해석하면 안 된다. 이 단계는 문자열에 좌표가 있는지를 확인하는 것으로도 풀 수 있어 공간 이해를 입증하지는 않는다. 다음에 조정할 대상은 흑백 판독 질문이다.

`/basics` 기본 단계는 0단계이며 프롬프트 네 가지를 직접 바꿔볼 수 있다. `occupancy_prompt.json`에 선택한 문구, `results_occupancy.json`에 분리된 선정/검증 결과와 요청 원문을 저장했다. 재현은 `op run` 환경에서 `uv run python gomoku/occupancy.py --workers 4`다.

## 0단계 경계 실험 v1 — 1행 편향 발견

공식 스킬 검토 후 0단계 입력을 `{"moves": "..."}`만 남기고 영어 질문으로 변경했다. 질문은 **Which candidate coordinate appears as a move in `moves`? Choose that coordinate.**이며 게임 종류·판 크기·차례를 입력하지 않는다. 선택지는 계속 정답 한 좌표와 설명 없는 오답 네 좌표다.

`occupancy_boundaries.py`는 일반 문제와 접두 좌표 함정 문제를 짝으로 구성한다. 예를 들어 기보에는 `g10`이 있지만 `g1`에는 돌이 없을 때, 일반 문제의 오답 하나만 `g1`로 교체한다. 같은 짝에서는 기보·정답·다른 후보와 후보 위치를 유지한다. 9수/29수 양쪽에서 함정 좌표가 실제로 비어 있는지 검사한다.

seed 1~10으로 영어 질문 두 개(짧은 질문/좌표 경계 상세 설명), 상태 두 개(moves만/기존 game·to_move 포함), 문제 두 개(일반/경계 함정)를 교차해 160요청을 측정했다. 모두 적중했다. moves만 준 조건에서도 두 질문 모두 40/40이어서 짧은 영어 문구를 선택한 후 seed 11~20을 검증했다.

별도 검증에서는 두 질문 각각 일반 20/20, 경계 함정 20/20이었다. 동일 요청 반복과 선택지 순서 변경도 각각 같은 성적이었다. 검증 240요청과 선정 160요청, 총 400요청 모두 적중했고 비용은 $0.0077이다. 반복을 독립된 문제로 세지 않는다. 20개의 생성 seed로 만든 9수/29수 쌍을 사용했다.

이 표본에서는 잘못된 접두 좌표를 걸러내며 완전한 좌표의 존재를 확인할 수 있었다. 단순 부분 문자열 검색으로도 풀렸던 이전 실험보다 강한 검사다. 그러나 좌표 토큰의 정확한 조회로 해결되는 과제이므로 공간 추론이나 흑백 구분을 증명하지 않는다. 모든 문구·상태가 만점이어서 입력 정리로 정확도가 개선됐다고 주장하지 않는다.

`results_occupancy_boundaries_v1_biased.json`에 요청과 평가 결과, `occupancy_boundary_prompt.json`에 선택한 질문을 저장했다. 현재 `/basics`에서 일반/경계 함정과 짧은/상세 영어 질문을 비교할 수 있다. 이 단계는 회전하면 접두 함정의 성질이 사라질 수 있어 원본·반복·순서 변경만 제공한다. 테스트는 변형 전후 정답 보존·진짜 빈칸 여부·부분 문자열 일치·최소 입력을 검증한다.

재현: `op run`으로 키를 주입한 환경에서 `uv run python gomoku/occupancy_boundaries.py`.

후속 검토에서 모든 가짜 접두 좌표가 1행이고 실제 정답은 전부 다른 행인 편향을 발견했다. 단순 부분 문자열 일치 후 1행을 제외하는 규칙도 400/400이었다. 따라서 이 버전의 만점만으로 좌표 경계 구별을 입증할 수 없으며 아래 균형 실험으로 대체했다.

## 0단계 경계 실험 v2 — 1행 정답 균형

선정용 seed 1~10과 검증용 seed 11~20 각각에서 실제 정답의 절반을 1행으로 만들었다. `i10`·`j10`이 모두 있는 기보에서 `i1`·`j1` 중 하나만 실제로 두고, 다른 하나는 경계 함정으로 사용한다. 두 열 모두 정답과 오답으로 등장한다. 다른 절반의 문제는 1행 이외의 실제 착수 좌표가 정답이다. 한 문제의 정답은 여전히 정확히 하나이고 선택지 다섯 개는 설명 없이 섞어 전달한다.

1행 돌을 멀리 갑자기 추가하지 않고 중앙에서 인접한 착수를 이어 구성했다. 이 때문에 판은 이전 9/29수 대신 17/37수다. 많은 돌 판은 같은 앞 16수 뒤에 주변 착수 20개를 넣고 같은 마지막 수를 두며, 정답·후보·후보 순서를 유지한다. 구성 수순은 기존 심판으로 금수·중복·종료 후 착수를 검사했다. 선수의 실전 포석을 재현했다는 뜻은 아니다.

두 영어 질문과 상태 비교·일반/경계 비교를 포함해 선정 160요청, 별도 검증 240요청을 실행했다. **전체 비교에서 Jev는 395/400**, 기존 “부분 문자열 중 1행 제외” 규칙은 **200/400**이었다. 1행 실제 정답은 전체 조건에서 195/200이었다. 틀린 5회는 모두 선정용 seed 5의 game·to_move를 추가한 rich 상태에서 발생했다. moves만 준 조건은 선정 80/80, 별도 검증 240/240이었다. 같은 문제의 반복 오류이므로 이를 독립 실패 5문제로 해석하지 않는다. 선정/검증에 쓰인 기보는 각각 20개이며 서로 같은 수순이 없다. 나머지 요청은 이 기보들의 조건 변화와 반복이다.

선택된 짧은 영어 질문의 별도 검증 경계 문제는 원본 20/20, 반복 20/20, 후보 순서 변경 20/20이었다. 각각 1행 정답 10개와 다른 행 정답 10개를 포함하며 17수/37수 모두 통과했다. 상세 질문도 같은 성적이었다. 비용은 $0.0079.

`results_occupancy_boundaries.json`에는 `version: row1-balanced-v2`, 요청·응답·1행 정답 여부·가짜 접두 좌표 선택 여부를 기록한다. 테스트 23개로 짝 비교·정답 유일성·행 균형·옛 간편 규칙 실패·지역적 합법 수순을 검증했다. UI는 새 17/37수 문제를 사용한다. 이번 결과는 알려진 1행 배제 편향으로는 설명되지 않지만, 범위가 제한된 좌표 조회 실험이며 공간 추론이나 흑백 구분까지 입증하지는 않는다.

## 흑백 구분: 프롬프트와 입력 구조 연구

`colour.py`는 주어진 좌표 하나의 돌 색을 `black`/`white` 중에서 고르게 한다. 이전 “좌표 다섯 개 중 백돌 찾기”와 다른 과제이며, 무작위 기대 정답률은 50%다. `state`는 `moves`와 `coordinate`만 포함한다. 좌표의 수 번호·정답 색·돌 목록의 색 분류는 전달하지 않는다. 각 10 seed 묶음에서 9수/29수, 흑/백 정답을 동일 개수로 구성하고 색 선택지 순서도 균형 있게 배치한다.

원문 기보를 고정한 프롬프트 선정 40문제는 흑 선공·교대 설명 22/40, 수 번호 홀짝 설명 21/40, 두 수씩 묶어 읽기 26/40, 구조화 지시문 25/40이었다. 선정한 두 수 묶기 질문은 별도 seed 11~20 원본 40문제에서 23/40(9수 15/20, 29수 8/20)이었다. 기본 규칙 설명은 24/40이므로 문구의 개선이 검증됐다고 볼 수 없다. `results_colour.json`에 선정 160요청과 별도 검증(반복·선택지 순서 반전·90도 회전 포함) 320요청을 저장했다($0.0089).

같은 질문으로 입력 경계만 바꿨다. 선정용 40문제는 연속 문자열 26/40, 공백 분리 32/40, 좌표 배열 37/40이었다. 배열을 선택해 기존의 seed 11~20에서 후속 확인한 결과는 아래와 같다. 이 seed들은 이전 실험에서 이미 평가했으므로 완전히 새로운 최종 시험이라고 부르지 않는다. 배열에는 좌표만 있고 수 번호·색은 없다. `results_colour_encoding.json`의 compact 결과는 앞선 실행을 재사용했고 추가 200요청 비용은 $0.004였다.

마지막 조건은 `colour_pairs.py`로 사전 정의한 구조 보조 실험이다. 입력을 `[["h8","i8"],["g8","j8"],...]`처럼 두 수씩 묶고 첫 번째는 흑, 두 번째는 백이라는 일반 규칙을 설명한다. 색 문자열이나 정답을 데이터에 넣지는 않지만 **코드가 수순의 홀짝 묶음을 미리 계산한 것**이다. 따라서 높은 정답률을 “Jev가 원문 기보의 수 번호를 스스로 셌다”는 증거로 사용하지 않는다. 이 조건은 전체 80개 질의에 원본·반복·순서 반전을 적용한 240요청에서 234개를 맞혔다($0.0053). 기존 seed를 재사용한 탐색적 후속 검증이다.

현재까지의 해석: 좌표를 찾는 것과 수순에서 색을 복원하는 것은 다른 문제다. 연속 기보에서는 질문 문구만으로 안정적인 흑백 판독을 만들지 못했다. 좌표 구분에 더해 홀짝 묶음까지 명시하면 성적이 크게 올라가므로, 수순을 분해·세는 부담이 영향을 준다는 해석을 지지한다. 내부 원인을 확정한 것은 아니며 100%도 아니다.

화면 `/basics`에 지정 좌표 흑백 판독을 추가했다. 4가지 질문과 연속/공백/배열/두 수 묶음 입력을 비교할 수 있다. 두 수 묶음은 메뉴에 코드 보조임을 표시하며 실제 입력 JSON을 그대로 보여준다. 색 확률을 좌표 확률로 잘못 그리지 않고, 질의한 좌표만 보드에 표시한다. 재현은 `op run` 환경에서 `colour.py`, `colour_encoding.py`, `colour_pairs.py` 순으로 실행한다.

## 두 수 묶음으로 다섯 완성하기 — 후보 거리 균형

`completion_encoding.py`에서 흑백 구분을 도왔던 두 수 묶음 형식을 즉시 승리점 선택에 적용했다. 과제는 같은 백의 연속 넷을 다섯으로 완성하는 빈칸 찾기다. `state`에는 기보만 넣으며, 후보 다섯 개에는 좌표와 `null` 설명만 있다. 모델에게 승리점·줄 방향·전술 평가를 주지 않는다. 두 입력의 공통 질문은 백 차례, 15×15 판, 좌표 방향, 가로·세로·대각선 연속 다섯이라는 조건을 명시한다. 바뀌는 부분은 기보의 묶음 형식과 그 읽는 법이다.

첫 실행에서 후보 편향을 발견했다. 정답이 중앙에서 유일하게 가장 먼 후보인 경우가 18/20이라, 이를 공간 이해 성적으로 해석할 수 없었다. 초기 실행은 `results_completion_encoding_v1_distance_biased.json`에 감사 기록으로 보존했다. 현재 후보는 **정답·동일한 중앙 거리의 오답 1개·더 먼 오답 1개·더 가까운 오답 2개**로 바꿨다(Chebyshev 거리). 모두 두 밀도 판에서 빈칸이며 기존 돌에서 두 칸 이내다. 따라서 가장 먼 후보를 고르는 규칙은 현재 정답을 맞히지 못한다. 이 검사는 알려진 거리 편향을 제거한 것이지 모든 후보 편향이 없음을 보장하는 것은 아니다.

20 seed × 9수/29수 × 연속/묶음 × 원본·반복·순서 변경·세 방향 회전 = 480요청, $0.0113. 각 비교에서 기보의 의미·정답·후보·후보 순서를 동일하게 유지했다. 많은 돌 판에는 주변 돌뿐 아니라 기보 길이와 다른 위협도 늘어난다. 이전 단계에서 사용한 구성 국면을 재사용한 탐색적 비교이며 새로운 실전 기보의 일반화 성적은 아니다.

|---|---|---|---|---|---|---|---|
| 연속 기보 | 9수 | 13/20 | 12/20 | 12/20 | 9/20 | 9/20 | 8/20 |
| 연속 기보 | 29수 | 0/20 | 1/20 | 5/20 | 2/20 | 3/20 | 3/20 |
| 두 수 묶음 · 코드 보조 | 9수 | 18/20 | 19/20 | 18/20 | 19/20 | 18/20 | 18/20 |
| 두 수 묶음 · 코드 보조 | 29수 | 10/20 | 9/20 | 9/20 | 8/20 | 10/20 | 9/20 |

묶음 형식은 9수 판에서 모든 조건이 18~19/20으로 유지됐고, 29수 판에서는 8~10/20으로 낮아졌다. 흑백 구조를 코드가 보조하면 이 단순한 줄 완성 과제도 더 잘 풀지만, 돌이 많은 판은 아직 안정적이지 않다. 원문 기보에서 스스로 색을 복원하고 전략을 판단하는 능력을 입증한 것은 아니다. 후보를 바꾼 전후 성적이 크게 달라졌으므로, 이전 실험의 정답률을 모델의 고정된 한계로 취급하지 않는다.

실제 요청·확률·조건별 성적은 `results_completion_encoding.json`(version: distance-balanced-v2)에 저장했다. 회전 입력·후보와 정답의 대응, 거리 편향 조건, 밀도쌍의 후보 일치 등을 테스트 32개로 검증했다. 화면의 기본 단계는 다섯 완성이며 연속 기보와 두 수 묶음을 직접 전환할 수 있다. 재현은 `op run` 환경에서 `uv run python gomoku/completion_encoding.py`다.

## 만들면서 알게 된 것

- **정답지의 문장이 승패를 갈랐다 (1→2판본).** 첫 판본은 방어 설명을 "stops black's open four"라고 썼다. 흑이 이미 넷을 가진 것처럼 읽히고 긴급도가 없다. 봇 8판에서 Jev는 0승 6패(2판은 120수에서 끊음)였고, 11수 패배는 전부 같은 모양이었다 — 엔진 1순위가 흑의 열린 셋을 막는 자리인데 Jev는 자기 열린 셋을 만드는 자리를 골랐고, 흑이 열린 넷을 만들어 끝났다. 문장을 "URGENT: black plays here next and gets an open four that cannot be stopped; block now"로 바꾸고 지시문에 우선순위를 번호로 적자 강제수는 138/138이 됐다. 버그헌터의 "명제 한 절이 순위를 통째로 바꾼다"와 같은 결.
- **막기만 하면 진다 (2→3판본).** 2판본은 강제수를 다 잡고도 1승 4패 3미완 — 영상에서도 두 판을 막기만 하다가 졌다. 원인은 정답지 쪽이었다. "denies black an open three"(흑이 셋을 *시작할* 자리를 미리 막음)에 자기 열린 셋 만들기의 0.9배 점수를 줘서 소극적인 수가 상위권에 깔렸고, 4-3이나 쌍삼처럼 **이기는 공격**은 표시조차 없었다. 방어 가중치를 내리고(미리 막기 0.35), 쌍수를 `DOUBLE THREAT`/`URGENT`로 표시하고, 지시문에 "강제된 게 없으면 내 줄을 키워라"를 넣자 3승 5패, 미완 0, 엔진 1순위 일치 46%→60%. 남은 패배는 봇이 4-3을 완성한 판이다.
- **강제수는 전부 잡고, 그 밖에서는 열에 여섯만 엔진을 따른다.** WINS·MUST BLOCK·URGENT가 붙은 자리는 한 번도 놓치지 않았다. 표식이 없는 수에서는 2위·3위도 고른다 — 그 자리들의 점수 차가 작아서(같은 열린 셋을 막는 양끝처럼) 틀렸다고 하기 어렵다.
- **선수인 봇을 반 못 이긴다.** 같은 엔진이 순위 1위를 그대로 두는 봇이 흑을 잡으면 Jev는 5판 중 3판을 진다. 정답지에는 한 수 뒤의 사실만 있고 "두 수 뒤에 4-3이 된다" 같은 계획은 없어서다. Jev가 더한 것은 문장 위의 우선순위 판단이지 수읽기가 아니다. 랜덤 흑은 10~14수에 전부 이긴다.
- **threat 미터는 진짜 반응한다.** 막아야 할 자리가 있을 때 0.80, 없을 때 0.26(랜덤 흑 상대로는 0.09). 같은 요청 안의 다른 질문이라 move의 답을 보지 못하는데도 같은 상황을 읽는다.
- **촬영 삽질.** 이 맥에서 다른 에이전트가 동시에 창을 띄우면 크롬리스 Chrome이 뒤로 밀려 영상 한가운데 터미널이 찍혔다. `record.sh`에 1초마다 창을 앞으로 당기는 루프를 넣었지만, 다른 세션이 같은 화면을 `screencapture`로 녹화하기 시작하자 둘이 서로 창을 뺏었다. 그래서 화면을 아예 안 쓰는 `record_headless.mjs`로 갔다 — bug-hunter 때 CDP screencast 프레임 간격이 고르지 않다고 버렸던 방식이지만, Playwright의 recordVideo(25fps webm)를 30fps로 다시 인코딩하니 볼 만하다.

## 한계

- 정답지에 수읽기가 없다. 엔진이 한 수 뒤만 보므로 Jev도 한 수 뒤만 안다. 검증된 엔진(Rapfi)에는 깊이 1로 줄여도 24판 전패.
- 렌주 금수의 단순화: 삼을 열어 주는 수가 금수인 경우(가짜 삼)를 따지지 않고, 한 줄 안의 사사(`XX.X.XX`류)는 안 본다.
- 후보 24개 밖의 자리는 Jev가 볼 수 없다.
