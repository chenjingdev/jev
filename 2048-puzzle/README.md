# Jev가 맞추는 2048 그림 퍼즐

TypeSafe의 System One 모델 **Jev**가 2048을 한다. 타일이 숫자 대신 그림 조각이라, 타일이 커질수록 그림이 드러나고 2048 타일이 그림 전체다. 2026-09-19~20, `jev-latest`.

> **종료. 실패한 실험이다.** 게임은 돌아가고 2048에 닿은 영상도 있지만, Jev다운 것이 아무것도 안 나왔다.
>
> - **플레이가 Jev에게서 나오지 않았다.** 사람이 보는 것(지금 격자)만 주면 무작위와 같은 64. 엔진이 네 방향을 대신 밀어본 결과 격자를 주면 128, 합친 수를 문장으로 써 주면 256, 전략("구석에 두고 정렬해라")까지 프롬프트에 쓰면 512~1024. 즉 성적은 전부 엔진 계산과 사람이 쓴 프롬프트에서 나왔고, Jev는 그 지시에 맞는 후보를 고르는 `if`문 자리에 있었다. 2048 도달 판의 선택 93%가 "합치는 쌍이 가장 많은 방향"이었다 — 코드 세 줄짜리 그리디와 같다.
> - **판단이 어려운 지점이 게임에 없다.** 방향이 넷뿐이고 아무렇게나 눌러도 굴러가는 게임이라, 코드로 못 쓰는 조건이 없다. 판단 모델을 붙일 자리가 애초에 없었다.
> - **성향층(테트리스식)도 상수로 붕괴했다.** "지금 합칠 때인가/구석 지킬 때인가/빈칸 만들 때인가"를 물으면 corner가 100% 발화하고 답이 판에 따라 안 바뀐다. Jev 가중치 판과 고정 가중치 판이 다섯 판 모두 수까지 같았다.
> - 유일하게 남는 것은 **위기 게이지**: "곧 막힐 것 같은가"의 확률이 실제 남은 수와 같이 움직였다(100수 이상 0.27 → 마지막 10수 0.62). 게임 하나를 지탱하기엔 작다.
>
> 남기는 이유는 측정표다. 자세한 수치는 아래 "측정".

Jev는 그림을 못 본다. 그림은 브라우저에서만 그리고, Jev에게는 4×4 격자를 글자로, 슬라이드 네 방향의 결과를 엔진이 잰 숫자로 보낸다. Jev는 그중 하나를 고른다. 테트리스와 같은 패턴이다.

## 규칙

- 보드는 보통 2048. 한 수마다 상하좌우 중 하나로 밀고, 같은 타일이 닿으면 합쳐지고, 빈칸에 2(90%)나 4(10%)가 하나 생긴다.
- 그림은 4×4로 16조각. 값 2^k 타일은 앞에서부터 `round(16·k/11)`조각을 보여준다 — 2는 1조각, 4는 3조각, 64는 9조각, 2048은 16조각 전부. 조각 순서는 가운데 넷부터 바깥으로 도는 순서(`PIECE_ORDER`). 아직 안 드러난 조각은 2048 원작의 타일 색으로 덮여 있어서 숫자를 안 읽어도 타일 값이 색으로 보인다.
- 오른쪽 위 "맞춘 조각"은 이번 판에서 만든 최대 타일이 보여주는 조각 수. 다음 조각이 몇 타일에서 나오는지도 적힌다.
- 기본 그림은 코드로 그린 풍경(파일 없음). 아무 그림 파일이나 보드에 끌어다 놓으면 정사각형으로 잘라 그 그림으로 바뀐다. 그림은 브라우저 밖으로 나가지 않는다.

## 실행

```sh
npm install
op run --env-file=.env.tpl -- npm start      # http://localhost:3462
npm test                                     # 엔진 테스트, 키 불필요
```

키는 서버 프로세스의 환경변수에만 있고 브라우저로 가지 않는다. `.env.tpl`에는 1Password 참조만 있다. 키 없이 `npm start`만 치면 안내 문구를 찍고 종료한다.

키: Space 일시정지, N 새 게임, C 촬영 모드(컨트롤 숨김). `?mode=eyes`(또는 컨트롤의 버튼)는 **눈 모드**: Jev에게 지금 격자만 주고 방향을 고르게 한다 — 엔진 숫자도 결과 격자도 전략 문장도 없이. 아래 측정대로 무작위 수준이라 금방 끝난다. `?seed=123`으로 같은 판을 다시, `?speed=slow|normal|fast`, `?clean=1`, `?img=경로`.

## Jev에게 묻는 것

수마다 요청 하나, 질문 둘. 갈 수 있는 방향이 하나뿐이면 묻지 않고 간다. 정확한 문구는 `questions.js`.

| 질문 | 종류 | 쓰임 |
| --- | --- | --- |
| move | Choice | 합법인 방향마다 요약문을 설명으로 붙이고 하나를 고르게 한다. 확률이 보드 사방의 화살표 밝기와 오른쪽 막대가 된다. |
| danger | Noul | 판이 곧 막힐 것 같은가. "위기" 게이지. |

state는 `board`(행 4개, 칸마다 단어 하나 — vision 실험에서 Jev가 정확히 짚는 형식), `facts`(빈칸, 최대 타일과 그 위치, 정렬된 줄 수/8, 거칠기, 남은 합칠 쌍), `candidates`(방향별 `summary`와 `board_after`). 요약문 예:

```
slide UP; merges 3 pairs (16+16, 4+4, 4+4) for +48; empty cells 5 → 8 before the new tile;
largest tile 32 stays in the top-left corner; 8 of 8 lines ordered (was 7); roughness 7 (was 10);
5 mergeable pairs left.
```

브라우저는 다음 판의 스폰까지 시드로 미리 알기 때문에, 이번 수가 미끄러지는 동안 다음 수를 먼저 묻는다. 그래서 화면에서는 수당 0.6초 정도(보통 속도)로 흐른다.

## 측정

`experiments/judge.mjs`로 세 가지 방식을 각 5판(시드 1000~1004) 돌린 결과. `experiments/results.json`.

| 지시문 | Jev가 받는 것 | 최대 타일 5판 | 중앙값 | 평균 수 |
| --- | --- | --- | --- | --- |
| – | 무작위 (합법 수 중 아무거나) | 64 64 256 128 64 | 64 | 113 |
| 규칙만 | **eyes** — 사람 눈에 보이는 것: 지금 격자뿐. 선택지는 "slide up" 넷 | 64 64 128 16 64 | **64** | 93 |
| 규칙만 | **bare** — 위 + 방향별 결과 격자(엔진이 대신 밀어본 것) | 128 128 128 128 64 | 128 | 130 |
| 규칙만 | board — 위 + 요약문에 합친 쌍과 점수 | 512 256 256 256 512 | 256 | 333 |
| 규칙만 | metrics — 위 + facts + 구석·정렬·거칠기 숫자 | 512 128 256 256 256 | 256 | 256 |
| 규칙 + 전략 | board | 256 256 256 256 128 | 256 | 271 |
| 규칙 + 전략 | **metrics (게임이 쓰는 것)** | 512 1024 512 1024 512 | **512** | 589 |
| 규칙 + 전략 | metrics, 브라우저에서 (시드 1001~1006) | 2048 512 512 512 512 512 | 512 | 596 |

"규칙만"은 SCENE(2048 규칙 설명) + "이 자리에서 가장 좋은 슬라이드를 골라라". "규칙 + 전략"은 거기에 "최대 타일을 구석에, 거기로 가는 줄을 큰 수→작은 수로, 그 정렬을 지키는 합치기, 빈칸 아끼기"를 덧붙인 것(`questions.js`의 `MOVE_TEXT`).

- **플레이는 프롬프트에 있다.** 사람이 보는 것만 주면(eyes: 지금 격자 하나) 무작위와 같은 64 — 16에서 끝난 판도 있다. 엔진이 네 방향을 대신 밀어본 결과 격자를 보여주면(bare) 128. 합친 쌍과 점수를 문장으로 써 주면 256. 구석·정렬·거칠기 숫자를 더 줘도 전략 문장이 없으면 그대로 256이고, 전략 문장이 붙어야 512~1024로 오른다. 즉 어떤 숫자를 잴지 고른 것도, 그 숫자를 어떻게 읽을지도 사람이 프롬프트에 쓴 것이고, Jev는 그 지시에 맞는 후보를 고른다. 테트리스의 "ASCII만으로는 판단 못 한다"와 같은 결론이되 한 걸음 더: 숫자만으로도 부족하고 **읽는 법까지** 줘야 한다.
- 2048 도달 판(1,207번 판단)에서 선택된 방향은 93%가 "합치는 쌍이 가장 많은 방향"이었다. "구석 유지" 문구가 있는 후보를 고른 건 21%. 사실상 최대 합치기 그리디이고, 그 그리디가 사람이 짜도 512~1024까지 가는 전략이다.
- 2048 타일은 11판 중 1번(1,209수). 방향 하나짜리 Choice로는 보통 512가 천장이고 2048은 운이 따라야 한다.
- **위기 게이지는 진짜다.** metrics 방식에서 `danger` 평균을 실제 남은 수로 묶으면 100수 이상 남았을 때 0.27, 30~100수 0.35, 10~30수 0.42, 마지막 10수 0.62. 판이 끝나갈수록 올라간다. 숫자 없는 방식에서는 0.23→0.35로 거의 안 움직인다 — 숫자 없이는 위기도 못 읽는다.
- 요청당 지연 260~275ms, 입력+출력 1,770토큰, 수당 $0.00007. 600수 한 판에 약 $0.045.

```sh
node experiments/judge.mjs 5 random                     # 키 불필요
op run --env-file=.env.tpl -- node experiments/judge.mjs 5 eyes,bare,board,metrics,plain-board,plain-metrics
```

## 성향만 정하게 하면? (`experiments/intents.mjs`)

수를 고르게 하지 말고 **지금 뭐가 급한지**만 Jev에게 묻는 구조를 시험했다. 의도 뉴런 셋(Noul): merge(지금 합칠 때인가), corner(구석과 정렬을 지킬 때인가), room(빈칸부터 만들 때인가). Jev는 후보를 보지 않고 격자와 facts만 보고 셋의 확률을 낸다. 엔진이 합법 수마다 기준 셋(합친 쌍 비율, 구석 유지 + 정렬 줄 수, 결과 빈칸 비율)을 0~1로 재고 `Σ 확률 × 기준`이 가장 큰 수를 둔다. 같은 엔진에 가중치를 고정하거나 무작위로 준 것과 비교하면 Jev의 판단이 더한 것이 정확히 보인다. 각 5판(시드 1000~1004).

| 가중치 | 최대 타일 5판 | 중앙값 | 평균 수 |
| --- | --- | --- | --- |
| Jev의 세 확률 | 256 256 256 512 128 | 256 | 296 |
| 셋 다 1 (Jev 없음) | 256 256 256 512 128 | 256 | 296 |
| 수마다 무작위 | 256 256 256 256 128 | 256 | 259 |
| merge만 / corner만 / room만 | 256 / 256 / 256 | 256 | 258~328 |

- Jev 판과 "셋 다 1" 판이 다섯 판 모두 **수까지 똑같다**. Jev의 성향이 사실상 상수였기 때문이다: corner는 1,482수 중 100% 발화(1등 99%), merge 69%, room은 6%. 판이 어떻게 바뀌어도 답이 안 바뀌니 가중치가 고정값과 같은 argmax를 낸다.
- 이 구조 자체가 위의 "전략 프롬프트 + Choice"(512)보다 약하다(256). 기준 셋을 선형으로 더한 단순 엔진의 한계이고, Jev 탓은 아니다.
- 테트리스에서는 같은 구조(감각층 발화)가 수를 바꿨는데 여기서는 안 바꾼다. 차이는 아마 상태의 다양성: 2048의 4×4 facts는 판이 진행돼도 "구석에 있고, 정렬 6~8, 빈칸 4~9" 근처를 맴돌아서 뉴런이 갈릴 재료가 적다. 요청당 270ms, 5판 $0.08.

## 구조

- `public/engine.js` — 순수 함수. 슬라이드/합치기, 스폰(시드 RNG), 합법 수, `facts`, 요약문, 후보 열거. 브라우저와 테스트와 측정 스크립트가 같은 파일을 쓴다.
- `public/app.js` — 캔버스 보드(그림 타일, 슬라이드·팝 애니메이션, 사방 화살표 히트맵), 오른쪽 패널, 게임 루프, 그림 드롭.
- `questions.js` — Jev가 읽는 문장과 요청 검증·조립.
- `server.js` — 정적 파일과 `POST /api/move`.
- `experiments/judge.mjs` — 힌트 단계별 측정. `experiments/intents.mjs` — 성향 뉴런 측정.
- `record.sh` — 촬영.

## 리플레이

`?replay=<이름>`은 `public/replays/<이름>.json`(시드 + 수마다 Jev의 답)을 읽어 Jev를 부르지 않고 그 판을 다시 튼다. 시드가 같아서 스폰이 같고, 화면의 확률·위기 값은 전부 녹화 당시 Jev가 준 값이다. `seed-1001.json`은 헤드리스 Chrome으로 빠름 속도에서 돌린 판 중 **2048에 닿은 판**(1,209수, 23,524점, 요청 1,207번). 같은 조건으로 돌린 나머지 다섯 판(시드 1002~1006)은 전부 512에서 끝났다.

## 촬영

`record.sh`는 크롬리스 Chrome 창을 메인 화면에 띄우고(`?clean=1&speed=fast&seed=…`) macOS `screencapture -v`로 그 영역을 30fps로 녹화한 뒤 판이 끝난 지점(서버 로그의 마지막 수 시각)까지 잘라 세 파일을 만든다: 한 판 전체(`full.mp4`), `SPEEDUP`배 빨리 감은 타임랩스(`demo.mp4`), 마지막 1분 실시간(`ending.mp4`, 화살표가 읽히는 속도). 빠름 속도로 수당 0.32초라 600수 판이 3분쯤이고, 3배면 1분 안쪽이다. 타임랩스라도 수마다 Jev의 답이 그대로다 — 잘라 붙인 게 아니라 빨리 감은 것.

```sh
op run --env-file=.env.tpl -- npm start > /tmp/jev-2048-server.log 2>&1 &   # 끝 지점은 이 로그에서 읽는다
SECONDS_TO_RECORD=360 SEED=1001 SPEEDUP=3 ./record.sh                       # 라이브 한 판
QUERY="clean=1&speed=fast&replay=seed-1001" SECONDS_TO_RECORD=400 TRIM_END=382 SPEEDUP=6 ./record.sh   # 저장된 판
```

`demo.mp4`(6배속, 63초)와 `ending.mp4`(마지막 1분 실시간, 2048이 만들어지는 부분)는 두 번째 명령으로 찍었다. `screencapture`는 촬영 중 디스플레이가 꺼지면 아무 말 없이 멈추고 빈 파일을 남기므로 스크립트가 `caffeinate -d`로 화면을 깨워 둔다. 라이브로 찍은 첫 판(시드 1001)은 브라우저에서는 132수 128에서 끝났다 — Jev의 답이 매번 같지 않아서 측정 때의 1024가 재현되지 않는다. 그래서 헤드리스로 여섯 판을 먼저 돌려 2048에 닿은 판을 저장하고 그 리플레이를 찍었다. 영상 속 수는 전부 Jev가 실제로 고른 수이고, 편집은 빨리 감기뿐이다.

## 만들면서 알게 된 것

- 방향 넷 중 하나를 고르는 건 테트리스의 34개 후보보다 훨씬 쉬운 Choice라 확률이 자주 한쪽으로 쏠린다 — 초반 60수에서 1등 확률이 0.9 이상인 수가 62%, 0.7 아래는 8%. 히트맵의 재미는 그 8%, 코너를 지킬지 합칠지 갈릴 때 나온다.
- 시드 RNG 덕에 다음 수를 미리 물을 수 있었다. Jev의 지연이 애니메이션 뒤로 숨는다.
- 이 데모에서 Jev가 한 일은 "사람이 쓴 전략에 맞는 후보 고르기"다. 전략을 빼면 256, 숫자까지 빼면 128. 영상은 그 사실을 알고 봐야 한다. 다음에 해볼 것: 테트리스처럼 층을 쌓거나(코너 지키기·합치기·빈칸 확보 의도 뉴런), 두 수 앞 결과 격자를 후보에 넣기.
