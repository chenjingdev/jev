# 9줄 바둑: GNU Go 후보 중 Jev가 고르면 이기나 (2026-09-22)

체스 실험(`../chess/README.md`)은 깊이 2 엔진끼리 붙이면 84~90%가 반복 무승부라 승률로 결판을 못 봤다. 바둑은 덤을 7.5집(반집)으로 두면 규칙상 무승부가 없고, 순환 금지 규칙 때문에 같은 국면 반복도 없다. 그래서 같은 질문을 바둑으로 다시 물었다: **약한 엔진이 낸 후보 수 중에서 Jev가 고르면, 엔진 혼자 두는 것보다 이기나.**

## 설계

- 판: 9×9, 중국 규칙(면적 계산), 덤 7.5. 두 번 연속 패스로 종국, `final_score`로 승패. 무승부는 발생할 수 없고 코드가 `0` 점수를 받으면 예외를 낸다.
- 엔진: GNU Go 3.8 레벨 1(`brew install gnu-go`), `--capture-all-dead`. `reg_genmove`는 시드와 무관한 결정론이다. 단, 답이 국면뿐 아니라 질의 이력(내부 읽기 캐시)에도 걸려 있어, 수순만 `play`로 되감으면 100판 중 2~4판에서 다른 수가 나온다. 재현할 때는 원 대국이 낸 GTP 질의(`reg_genmove`, `top_moves`, `is_legal`)를 수마다 똑같이 낸다(`counterfactual_replay.branch`).
- 후보: 엔진 자신의 수(`reg_genmove`)를 1순위로 두고, `top_moves`의 대안 중 최고값에서 2.0집 이내인 합법수를 더해 최대 3개. 후보가 2개 이상인 시점에만 선택자가 개입한다(약 판당 6~7회).
- 선택자: Jev(`jev-1.13.0`, Choice), 시드 고정 무작위(같은 후보 중 균등), 없음(단독). 제1원칙 그대로: Jev에게는 착점 목록(`stones`), 차례, 덤, 수 번호, 직전 수, 따낸 돌 수만 보낸다. 엔진 값·순위·엔진의 선택은 보내지 않는다(`test_request_hides_engine_information`).
- 오프닙: GNU Go의 `genmove`는 시드로 바뀌지 않아 빈 판에서 시작하면 단독 대 단독은 항상 같은 판이 된다. 그래서 체스처럼 시드 오프닙 50개(`make_openings.py`, 6수, 엔진 근사 최선수 6개 중 균등 추출, 대칭 제거 전 40개 서로 다름)를 만들고, 오프닙마다 흑백을 바꿔 두 판씩 100판을 둔다.
- 잣대: 승률이 1차. 2차로 **반사실 재현**(`counterfactual_replay.py`): 선택자가 엔진과 다른 수를 고른 모든 시점에서 그 수를 둔 갈래와 엔진 수를 둔 갈래를 각각 단독끼리 끝까지 두어 승패(1/0)를 비교한다. API 없이 재현되고, 판 안의 결정별 차이 합은 실제 결과 − 같은 오프닙·같은 색의 단독 결과와 정확히 일치한다. 이 항등식을 세 실행 298판 전부에서 확인했다(단위 시험은 `test_identity_with_random_control`). 체스에서와 같이 이 일치는 재현 코드의 정확성 확인이고, 결정 단위 값은 한 판 안에서 서로 이어져 있어 아래 SE는 근사값이다.

```bash
brew install gnu-go
.venv/bin/python go/make_openings.py --plies 6                 # openings-50.json (시드 20260922)
.venv/bin/python go/go_batch.py --name l1plain-100 --selector none
.venv/bin/python go/go_batch.py --name l1rand-100 --selector random
op-away run op run --env-file=go/.env.tpl -- .venv/bin/python go/go_batch.py --name l1jev-100 --selector jev
.venv/bin/python go/counterfactual_replay.py l1jev-100 --suffix counterfactual-v2
.venv/bin/pytest go -q
```

## 결과: 100판씩, 같은 오프닙 50쌍

| 조건 | 승 | 패 | 승률 | 95% 구간 | 평균 집 차(하이브리드 기준) | 개입 |
|---|---:|---:|---:|---|---:|---:|
| GnuGo L1 단독 vs 단독 | 50 | 50 | 50.0% | (동일 판 두 번, 정확히 1-1) | 0.0 | 0 |
| GnuGo L1 + 무작위 | 47 | 53 | 47.0% | 37~57% | −1.5 | 404 / 700 결정 |
| GnuGo L1 + Jev (1차, 98판¹) | 35 | 63 | 35.7% | 26~45% | −3.2 | 370 / 617 |

¹ 1차는 한 쌍(op-029)이 GNU Go가 `top_moves`에 낸 불법수(A9)로 중단돼 98판이다. 이후 후보를 합법수로 거르도록 고치고(`gnugo.py`, `test_ranked_moves_only_lists_legal_alternatives`) 2차를 돌렸다.

Jev 두 번을 합치면 70승 128패, 35.4%(구간 29~42%). 단독 50%와는 z ≈ −4.1로 확실히 다르고, 무작위 47%와는 two-proportion z = −1.94, p ≈ 0.05(색을 바꾼 쌍이 음의 상관이라 이 p는 보수적이다). 시범 10판(`l1jev-10`, 1승 9패)은 같은 오프닙 세트의 처음 5쌍이라 100판의 부분집합이고 독립 확인은 아니다. **결판이 반드시 나는 환경에서 Jev의 선택은 엔진 혼자 두는 것보다 확실히 나쁘고, 무작위보다도 나쁜 쪽이다.**

무작위의 개입은 판 결과를 거의 안 바꾸고(순가치 0), Jev의 개입은 판마다 약 3.8회 있고 한 번에 −0.04점이라 판당 −0.15점, 즉 승률 −15포인트로 실제 대국 결과(단독 50% → 35%)와 정확히 맞는다(항등식이므로 당연하다).

### 어디서 지나: 방향별로 보면

Jev가 엔진과 다른 수를 고른 결정에서, 고른 수가 엔진 수보다 변에서 몇 번째 줄(선)인지 비교했다. 1차 370회 기준 엔진이 두려던 수는 1선 136·2선 133·3선 63·4선 39·천원 2, Jev가 고른 수는 1선 39·2선 106·3선 115·4선 96·천원 17이다. 즉 Jev는 변을 버리고 가운데를 고르는 경향이 뚜렷하다(가운데 쪽 197회, 변 쪽 45회, 같은 선 128회; 2차 202 / 50 / 128).

그런데 손실이 어디서 나는지는 이 경향과 다르다:

| 개입 방향 | 1차 n | 순가치 | 합계 | 2차 n | 순가치 | 합계 |
|---|---:|---:|---:|---:|---:|---:|
| 가운데 쪽으로 | 197 | −0.030 | −6.0 | 202 | −0.035 | −7.0 |
| 변 쪽으로 | 45 | −0.178 | −8.0 | 50 | −0.160 | −8.0 |
| 같은 선 | 128 | 0.000 | 0.0 | 128 | 0.000 | 0.0 |

가장 잦은 "가운데로" 개입은 한 번에 −0.03이고, 12%밖에 안 되는 "변으로" 개입이 한 번에 −0.17(1차 0승 8패, 2차 1승 9패)로 전체 손실의 절반 이상을 낸다. 같은 선 안에서 바꾼 128회는 두 번 다 정확히 0이다. 그러니 "중앙 선호가 원인"은 행동을 기술한 것이고 비용의 설명은 아니다. 정직한 요약은 **Jev의 개입은 어느 방향으로도 득이 없고, 엔진이 3·4선을 두려는데 변으로 내려간 소수의 개입이 치명적**이라는 것이다. 왜 그 수들이 치명적인지(사활이 걸린 자리를 놓치는지, 이미 죽은 곳에 두는지)는 국면을 따로 열어 봐야 한다. 시기별로는 20수 이내 −0.06, 21~40수 −0.035, 41수 이후 0.00(끝내기에는 후보가 1개뿐인 시점이 많아 개입이 드물다)이다.

## 체스와 나란히 놓으면

| | 체스 (깊이 2 vs 깊이 2, 결정론) | 체스 (노이즈 ±10) | 바둑 9줄 (GnuGo L1) |
|---|---|---|---|
| 무승부 | 84~90% | 57% | 0% |
| 무작위 선택자 | 47.0% (`d2rand-vs-d2-100`) | 50.5% | 47.0% |
| Jev 무문턱 | 47.5% (`d2jev-vs-d2-100`) | 52.5% | 35.4% (2회 합산) |
| 결정당 반사실 순가치 | Jev −0.002 = 무작위 −0.002 | 미측정 | Jev −0.038/−0.040 vs 무작위 −0.007 |

체스에서는 "무작위와 같다"였고, 바둑에서는 "무작위보다 나쁘다"다. 왜 다른지는 아직 가설이다. 하나는 표현이다: 체스는 기물 이름이 붙은 칸 목록이었고 바둑은 색만 붙은 좌표 목록이어서 Jev가 국면을 더 못 읽을 수 있다. 다른 하나는 후보의 성격이다: 체스 후보 3개는 엔진 눈에 35단위 이내로 비슷한 수들이었지만, 9줄 바둑 레벨 1의 후보에는 2.0집 이내라도 사활을 가르는 수가 섞여 있어 잘못 고르면 판이 넘어간다. 어느 쪽인지는 표현을 바꾼 실험(아래 한계)으로 가른다.

## 표현을 바꾸면 가려내나: 오프라인 구분 시험 (2026-09-22)

위 두 가설을 새 대국 없이 가르는 시험이다. 반사실 재현(v2) 세 파일에서 "두 후보 중 하나는 이기고 하나는 지는" 결정 174건을 모아 수순·후보가 같은 것을 합치니 103자리가 남았다(Jev 1차·2차가 거의 같은 수를 골라 2차는 4자리만 새로 보탰다). 같은 103자리를 세 가지 표현으로 Jev에게 묻고, 선택지 순서를 뒤집어 한 번 더 물었다(순서 편향 상쇄). 값·순위·형세 점수·엔진의 선택은 어느 조건에도 넣지 않았다.

| 조건 | Jev에게 준 것 |
|---|---|
| bare | 대국 때와 같은 표현: 돌 위치 사전 + 좌표 두 개 |
| reasons | bare + 후보마다 GnuGo `move_reasons` ("D8 수비", "D7·E5 연결", "집 확장" 등; "unsafe"·"defenseless" 같은 판단어는 제거) |
| status | reasons + 돌무리별 생사(`dragon_status`: alive/dead/critical) + 언급된 돌무리의 읽기 결과(`attack`/`defend`: 잡히나·살리나) |

정답은 "GnuGo L1이 이어 두었을 때 이긴 수"라서 대국에서 쓴 기준과 같고, 바둑 실력의 정답은 아니다. 엔진 자신의 선택이 56%밖에 못 맞추는 것이 그 기준의 잡음 크기다. 103자리 중 46자리는 두 후보의 라벨이 완전히 같아(둘 다 "집 확장" 등) 라벨로는 가를 수 없고, 57자리에서 라벨이 갈린다.

| 정답률 (순서 두 방향 평균) | 103자리 | 라벨 갈림 57 | 라벨 같음 46 |
|---|---:|---:|---:|
| 우연 | 50% | 50% | 50% |
| 엔진 선택(`reg_genmove`) | 56.3% | 63.2% | 47.8% |
| 라벨 개수 많은 쪽 (동수 제외, 50자리) | 54.0% | | |
| 대국 당시 Jev 선택 (43자리) | 39.5% | | |
| Jev bare | 50.5% | 44.7% | 57.6% |
| Jev reasons | **61.2%** | 59.6% | 63.0% |
| Jev status | **61.2%** | 57.9% | 65.2% |

**확인된 것.**
- bare는 우연이다. 순서를 뒤집어도 103자리 중 95자리에서 같은 수를 골랐고(순서 무관, 나름의 선호는 있음), 대국 당시 선택을 43자리 중 41자리(95%)에서 재현했다. 대국의 35%는 그 선호가 이 자리들에서 틀린 쪽이었다는 뜻이다(Jev 출처 자리는 "골라서 진 자리"로 뽑힌 선택 효과가 있다).
- 라벨을 붙이면 오른다. 두 순서 206회 쌍 비교에서 bare→reasons 44자리 좋아지고 22자리 나빠져 z=2.71. **라벨 맞바꾸기 대조**: 라벨이 갈리는 57자리에 status 요청을 두 후보의 라벨만 서로 바꿔 다시 보내면 57자리 중 48자리에서 선택이 뒤집히고 정답률은 61%→44%로 떨어진다(`discrim-103-swap.json`). Jev는 라벨을 읽고 따르며, 라벨이 정답과 60% 정도 맞는 만큼만 맞춘다.
- 생사·읽기(status)는 라벨 위에 아무것도 더하지 않는다. reasons→status 20 대 20, z=0.00. 라벨이 갈리는 57자리에서도 57.9% 대 59.6%다.
- 엔진보다 낫지는 않다. 라벨이 갈리는 57자리에서 엔진 63%, Jev 60%. 전체로는 Jev 61% 대 엔진 56%지만 그 차이는 엔진이 라벨 같은 46자리에서 48%인 데서 나온다.

**주의할 것.**
- 순서 편향은 라벨을 붙였을 때 생긴다. 먼저 보인 선택지를 고른 비율이 bare 46%, reasons 70%, status 68%였고, 특히 라벨이 같은 46자리에서는 순서를 뒤집으면 절반 넘게 선택이 바뀐다(순서 유지 20/46, 18/46). 처음 한 방향 결과(status 65.0%)는 그 셔플에서 정답이 먼저 온 자리가 많아 부풀려진 것이다. 이 절의 숫자는 두 방향 평균이다.
- 라벨이 같은 46자리에서 reasons·status가 63~65%인 것은 대부분 순서 잡음 위의 우연이지만, 그 안에서 순서와 무관하게 같은 수를 고른 자리는 16/20, 16/18로 맞았다. 표본이 작아 기록만 한다.
- 확신도는 여기서도 정답률과 무관하다(status 한 방향 기준 0~0.25 구간 16/19, 0.75~1.0 구간 16/25).

**읽는 법.** 좌표만 주면 Jev는 우연이고, 엔진이 "이 수가 무엇을 하는가"를 말로 붙여 주면 라벨을 따라 60%까지 오른다. 표현 가설이 살고, 후보 성격 가설(어떤 표현이든 잘못 고르면 판이 넘어간다)은 이 자리들에서 약해진다. 다만 오른 만큼은 라벨 자체가 가진 정보이고, Jev가 라벨 위에 자기 판단을 더해 엔진을 넘는 증거는 없다. 대국으로 옮기면 승률이 오르는지는 별개의 시험이며, 라벨 표현은 값·순위는 없지만 엔진 분석(수의 목적, 사활, 읽기)을 담고 있어 제1원칙 안이라고 볼지는 결정이 필요하다.

- 스크립트: `discrimination_test.py` (`--no-api` 기준선만, `--limit N` 시범, `--reorder-from` 순서 대조, `--swap-from` 라벨 맞바꾸기 대조). 자리 재현은 반사실 재현과 같은 질의 흉내를 쓰고 103자리 모두 엔진 수가 재현됐다.
- 증거: `matches/discrim-pilot-20.json`(시범, 부분집합), `matches/discrim-103.json`(본 시험 한 방향, 309회·입력 233,612토큰), `matches/discrim-103-reversed.json`(순서 뒤집기, 309회), `matches/discrim-103-swap.json`(라벨 맞바꾸기, 57회·52,967토큰), `matches/discrim-features-check.json`(API 없이 뽑은 사실과 기준선).

## 비용과 한계

- API: 시범 10판 80회·58,840토큰, 1차 617회·448,209토큰, 2차 626회·455,947토큰. 판당 약 6회 호출로 체스(25회)의 1/4이다. GNU Go는 수당 23ms, 100판 배치가 API 없이 10초 안에 끝난다.
- 레벨 1 하나만 봤다. 더 강한 레벨이나 13·19줄, 후보를 엔진 대신 다른 방식으로 만들 때는 다른 결과가 나올 수 있다.
- Jev에게 준 표현은 착점 목록 하나다. ASCII 판 그림이나 "3선/4선", "귀/변/중앙" 같은 말로 바꾼 표현은 시험하지 않았다(체스에서 UCI 대신 의미 표현으로 바꾸자는 아이디어와 같은 갈래).
- 외부 심판(KataGo)은 붙이지 않았다. 체스에서 Stockfish 심판이 실제 상대에 대한 가치와 어긋났고, 여기서는 무승부가 없어 대국 결과와 반사실 재현만으로 충분했다.
- 증거: `matches/l1plain-100*`, `l1rand-100*`, `l1jev-10*`, `l1jev-100*`, `l1jev-100b*`와 각 `.counterfactual-v2.json`(인용본) 및 `.counterfactual.json`(폐기본), 쌍별 `.json`/`.sgf`/`.log`는 `matches/<이름>/`.
