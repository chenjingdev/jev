# Claude Code의 Jev 바둑 시험 방법론 검토 — 2026-09-22

판정: 기존 시스템의 성능 측정과 실패 원인 탐색에는 유용하다. 그러나 “Jev가 형세·공격/수비·수싸움을 구분하는가”를 직접 검증한 시험은 아니며, 현재 README의 일부 통계와 해석은 증거보다 강하다.

검토 대상은 `go/README.md`, 대국·반사실 재현·구분 시험 코드, 저장된 원본 결과다. 외부 문서는 TypeSafe와 GNU Go 공식 문서, Anthropic의 평가 지침을 대조했다. 실험 코드와 기존 결과는 수정하지 않았다. 새 Jev API 호출은 없고, 기존 Go 테스트 12개가 통과했다(`.venv/bin/pytest go -q`, 19.96초).

## 제대로 한 부분

- 엔진 단독·동일 후보 무작위·Jev를 비교하고, 같은 오프닝에서 흑백을 교대한 설계는 유용하다.
- 순서 뒤집기와 라벨 맞바꾸기는 모델이 어떤 입력에 반응하는지 확인하는 좋은 진단이다.
- 원본 응답과 기보를 보존했고, 엔진 점수·순위·정답 필드를 요청에서 제외한다.
- GNU Go의 질의 이력까지 재현하도록 고친 것은 중요하다. 반사실 값의 합과 실제 결과 차이가 일치하는 항등식은 실행 일관성 검사이며, 독립적인 추가 성능 증거는 아니다. README도 이 점은 명시한다.

## 수정해야 할 판단

### 1. 세 단계의 구분 능력은 아직 시험하지 않았다

`discrimination_test.py:36–49,154–168`의 질문은 모든 조건에서 “가장 좋은 실전 국면을 만드는 수를 골라라”다. 집 확보·연결·생존·상대 약점 공략을 한 번에 요구한다. `status`도 별도 형세판단이나 수싸움 질문이 아니라 같은 질문에 생사·읽기 정보를 추가한다.

이 방식 자체가 잘못된 Choice 사용은 아니다. 다만 측정하는 것은 최종 후보 선택이며, 좁은 중간 판단 중 어디에서 실패했는지는 알 수 없다. [TypeSafe 공식 구성 지침](https://docs.typesafe.ai/concepts/how-to-build-with-system-one)은 필요한 문맥을 주고 좁은 판단을 코드로 합성하도록 안내한다. [공식 workflow 평가](https://evals.typesafe.ai/)도 중간 판단을 분리한다. 이것이 바둑에서 반드시 성공한다는 보장은 없지만, 현재 시험으로 그 가능성을 기각할 수는 없다.

### 2. “표현만 변경”과 “엔진 분석 제공”을 분리해야 한다

`reasons`에는 엔진이 추론한 수의 목적, `status`에는 생사·전술 읽기 결과가 추가된다. [GNU Go 문서](https://www.gnu.org/software/gnugo/gnugo_6.html)는 공격·수비 이유가 전술 읽기와 사활 분석에서 생성됨을 설명한다. 점수와 순위를 숨겨도 계산된 분석을 제공하는 효과는 남는다.

따라서 50.5% → 61.2%는 **엔진 설명을 추가한 조건의 개선**이다. 좌표 표현 문제만 해결했다거나 후보의 위험성 가설을 반박한 결과는 아니다. 두 가설은 동시에 성립할 수도 있다.

라벨을 바꾸자 선택이 48/57개 뒤집힌 것은 라벨에 강하게 반응한다는 증거다. 그러나 라벨만 준 조건과 돌 배치만 제거한 조건이 없으므로 “라벨의 정보만 따라가고 자신의 판단은 전혀 더하지 않는다”까지 입증하지는 않는다.

### 3. 표본은 실제 의사결정 전체를 대표하지 않는다

`collect_positions()`는 엔진과 다른 수를 선택했던 시점 중, GNU Go L1으로 이어 두었을 때 두 갈래의 승패가 달라진 사례만 남긴다. 실패 분석용으로는 합리적이지만, 모델 자신의 과거 선택과 결과로 표본을 고른 효과가 있다. 승패가 같았던 국면과 엔진에 동의했던 국면은 빠진다.

103개 중 52개는 원래 후보가 3개였는데 시험에서는 2개로 줄었다. 그러므로 같은 종류의 입력 표현을 사용했어도 원래 대국 과제 전체를 그대로 재시험한 것은 아니다.

재계산 결과, 무작위 대조군에서 먼저 수집된 60개 국면에서는 bare 58.3%, reasons 61.7%로 차이가 3.3%p다. 전체의 10.7%p와 다르다. 이 60개도 승패가 갈린 시점만 고른 표본이며 완전히 독립된 검증 세트는 아니다. 이 하위집단 분석 역시 사후 탐색이므로 확정 결론으로 쓰지 않는다.

### 4. 반복 측정을 독립 표본처럼 계산했다

- 대국: 두 Jev 실행의 공통 98판 중 95판은 승패가 같고, 83판은 수순 전체가 같다. 반복 실행은 일관성을 보여주지만 새 오프닝 198판의 정보량은 아니다. README 35행의 합산 z·p 및 “보수적”이라는 설명은 반복 실행과 오프닝 중복까지 고려하지 않았다.
- 구분 시험: 순서를 바꾼 206회는 103개 문제의 반복 측정이다. 그 문제들은 27개 서로 다른 오프닝 수순, 대칭을 합치면 26개 오프닝 계열에서 나왔다. README 113행의 206회 독립 쌍 비교 z=2.71은 이런 의존성을 반영하지 않는다.

두 순서의 점수를 먼저 국면별로 평균하고, 같은 오프닝 계열의 모든 국면을 묶어 bootstrap 50,000회로 재계산했다. 대국은 흑백 두 판을 쌍으로 평균한 뒤 오프닝 계열로 묶었다. 구간은 탐색용 percentile 95% 구간이며, 표본 선택 편향·프롬프트 개발·모델 변화의 불확실성까지 해결하지 않는다.

| 구분 시험 지표 | 관측치 | 오프닝 계열로 묶은 95% 구간 |
|---|---:|---:|
| bare 정확도 | 50.5% | 40.3–59.1% |
| reasons 정확도 | 61.2% | 51.9–69.4% |
| reasons − bare | +10.7%p | +1.8–+21.1%p |
| reasons − 엔진 선택 | +4.9%p | −4.1–+13.2%p |
| status − reasons | 0.0%p | −1.7–+2.2%p |
| 무작위 출처 60국면의 reasons − bare | +3.3%p | −6.6–+16.0%p |

즉 통계를 고쳐도 전체 표본의 개선 신호는 남는다. “통계가 틀렸으니 개선도 없다”는 판단은 맞지 않는다. 엔진보다 우수하다는 증거는 부족하다. 생사·읽기 추가의 관측 평균 이득은 0이지만, 다른 질문·표본에서도 쓸모없다고 일반화할 수 없다.

대국 2차의 Jev 35%도 관측 사실이고, 오프닝 계열로 묶은 구간은 약 26.9–43.2%다. 기존의 좌표 기반 선택자가 이 환경에서 단독 엔진보다 나빴다는 해석은 유지된다. 이것을 Jev 전체의 바둑 판단 능력이나 새로 설계할 단계별 시스템의 한계로 확대하면 안 된다.

### 5. 정답과 주장 범위를 맞춰야 한다

현재 정답은 “GNU Go L1이 양쪽을 계속 두었을 때 이긴 갈래”다. 이 특정 상대·후속 정책에 대한 개입 평가에는 맞지만, 객관적인 최선수나 공격·수비 개념 이해의 정답은 아니다. 엔진의 자기 선택 정답률이 56.3%라는 사실만으로 정답의 잡음률을 추정할 수도 없다.

README의 “엔진보다 낫지는 않다”는 “엔진보다 낫다는 증거가 부족하다”로, “생사·읽기는 아무것도 더하지 않는다”는 “이 질문과 표본에서 평균 정확도가 같았다”로 표현하는 것이 정확하다.

## 다음 시험의 구체적인 형태

1. 먼저 목표를 나눈다. 라벨의 의미를 읽는지, 국면에 맞는 우선순위를 판단하는지, 최종 승률을 높이는지는 별도 시험이다. “수비라고 적힌 후보 찾기”는 입력 이해 검사이며 바둑 실력의 증거로 사용하지 않는다.
2. 완전히 새로운 오프닝 계열을 개발용·평가용으로 먼저 나눈다. 이전 Jev 선택의 성공·실패와 무관하게 국면과 후보를 수집한다. 실패 사례 집합은 별도의 진단용으로 유지한다.
3. 같은 국면에서 입력 조건을 분리한다: 좌표 원문, 계산된 분석을 추가하지 않은 판 표현 변경, 엔진 목적 라벨 추가, 목적 라벨만 제공, 생사·읽기 추가. 순서 반전은 모두 적용하고 동일 국면의 반복으로 집계한다.
4. 형세·수비 필요성·공격 기회처럼 정답을 정의할 수 있는 좁은 질문을 각각 측정한다. 앞 단계의 답이 필요한 다음 단계에는 실제 모델 답을 전달하고, 단계별 오류와 최종 오류를 함께 기록한다. 엔진이 이미 계산해 주는 사실을 Jev가 반복해서 읽는 것과 새 판단을 더하는 것을 구분한다.
5. 단독 엔진, 무작위, 같은 엔진 정보를 읽는 고정 규칙과 비교한다. 프롬프트·결합 규칙을 고정한 후 새 평가 오프닝에서 대국한다. 1차 지표는 같은 오프닝·흑백 쌍의 점수 차이며 API 시간과 비용도 함께 보고한다.
