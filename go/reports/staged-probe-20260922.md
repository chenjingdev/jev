# Jev 바둑: 정보 해석과 우선순위 선택을 분리한 시험

실행일: 2026-09-22. 모델: `jev-1.13.0`.

**결과:** 엔진 정보를 읽는 능력은 확인했다. 정보를 질문에 맞게 정리하면 아군의 위험 상태를 놓치는 문제도 줄었다. 그러나 그 정보를 보고 공격·수비 등의 우선순위를 선택하게 한 정책은, 새 국면에서 엔진이나 고정 규칙보다 좋은 결과를 보이지 않았다. 미리 정한 진입 기준을 충족하지 않아 전체 대국 시험으로 넘어가지 않았다.

## 1. 시험을 어떻게 바꿨나

- 정보 해석, 우선순위 선택, 실제 대국 효과를 별도 단계로 나눴다.
- 기존 103개 국면은 진단용으로만 사용했다. 질문을 만든 뒤 변경하지 않고 새로운 오프닝 30개에서 확인했다.
- 새 오프닝은 기존 40개 대칭 계열과 겹치지 않는다. 엔진 단독 수순에서 후보가 2개 이상인 시점을 모아, 오프닝당 최대 6개를 고정 난수로 추출했다. Jev의 과거 선택이나 승패로 고르지 않았다. 총 178개 국면이다.
- 정답·평가값·엔진의 선택 순위는 API 요청에 들어가지 않는다. 선택지 순서는 정방향과 역방향으로 모두 물었고 두 답을 국면/문제 안에서 평균했다.
- 사실을 읽는 문제의 정답은 **입력된 엔진 설명**이다. 이것을 객관적인 바둑 실력이나 정답 수 판별로 해석하지 않는다.

## 2. 정보를 읽을 수 있나

여섯 과제를 분리했다. 각 후보의 여러 목적을 독립적으로 물어, 공격과 수비 등을 하나의 배타적 분류로 강제하지 않았다. `threatens to attack`과 직접적인 `attacks`는 구분한다.

두 입력은 같은 원자료를 쓴다.

- **전체 입력:** 돌 배치, 차례, 후보 설명, 생사 지도, 전술 읽기 정보.
- **정리된 입력:** 차례, 돌무리별 색·생사, 후보 설명. 좌표별 색과 생사를 코드로 결합하여 돌무리 표로 만들었다. 새 엔진 분석을 추가하지 않았다.

호출 전에 고정한 통과 기준: 각 과제의 균형 정확도 90% 이상, 각 관측 정답 종류의 재현율 80% 이상, 순서 반전 답 일치율 90% 이상. 이 기준은 진단을 다음 단계로 넘기기 위한 운영 기준이며, 바둑 판단 능력 전체의 보증이 아니다.

기존 자료의 개발 진단은 156문제였다. 정리된 입력은 전부 맞혔다. 전체 입력은 아군 위험 판단에서 95.8%, 나머지는 100%였다. 이를 보고 질문이나 기준을 다시 바꾸지 않았다.

새 자료에서는 260문제, 입력별 정·역순 두 번씩 총 1,040판단을 했다. 다음 수치는 정답 종류를 균등하게 반영한 정확도이며, 반복 답을 독립된 새 문제로 세지 않았다.

| 과제 | 서로 다른 문제 | 전체 입력 | 정리된 입력 |
|---|---:|---:|---:|
| 엔진이 표시한 생사 상태 읽기 | 60 | 100% | 100% |
| 위험 표시가 있는 아군인지 판단 | 40 | 90.0% | 100% |
| 해당 후보가 수비하는지 | 40 | 100% | 100% |
| 해당 후보가 공격하는지 | 40 | 96.3% | 98.8% |
| 해당 후보가 연결하는지 | 40 | 100% | 100% |
| 해당 후보가 집/세력을 넓히는지 | 40 | 100% | 100% |

전체 입력은 실제로 위험 표시가 있는 아군 20문제 중 4개를 두 순서에서 모두 놓쳤다. 정리된 입력에서는 이 네 문제를 모두 맞혔다. 공격 구분의 남은 한 오류는 `strategically defends H7; expands territory`를 한 순서에서 공격이라고 답한 것이다. 따라서 이 표본에서는 필요한 정보를 모아 주는 입력 방식이 관계 판독에 도움이 되었다.

## 3. 읽은 정보로 유용한 우선순위를 정하나

새 178개 국면을 모두 유지하고 각 국면의 원래 후보 2~3개를 그대로 사용했다. 질문은 최선 좌표 대신 **수비·공격·연결·집 확장·판단 유보 중 무엇을 우선할지**를 묻는다. Jev가 고른 목적에 맞는 후보 중 엔진 순위가 가장 높은 수를 코드가 실행한다. 판단 유보 시에는 엔진 수를 유지한다.

돌무리 ID의 별칭을 GNU Go의 실제 돌무리로 연결하고, 색·생사·돌 수 및 후보 목적을 양쪽 정책에 똑같이 제공했다. 생사 상태 외에 GTP 응답에 붙는 추천 좌표는 제거했다. 엔진 점수·순위는 Jev에게 주지 않았다.

비교 정책은 사전에 고정했다.

1. 엔진의 원래 수.
2. 고정 규칙: 후보 중 위험한 아군을 지키는 목적이 있으면 수비, 아니면 위험한 상대를 공격, 아니면 연결, 아니면 집 확장, 없으면 엔진 유지. 실제 착점 선택 방식은 Jev와 동일하다.
3. Jev의 목적 선택.
4. 원래 후보 중 균등 무작위 선택의 기대값.

어떤 목적을 골라도 같은 수가 나오는 121국면에서는 API 호출이 필요 없었다. 실제 선택이 달라질 수 있는 57국면만 정·역순으로 물었다(114요청). 목적과 실행 수 모두 57개 중 56개에서 순서와 무관하게 같았다.

후보 445개 각각을 둔 뒤 양쪽을 GNU Go L1 단독으로 끝까지 진행했다. 이 점수는 **해당 후속 정책에서 한 번의 선택이 만드는 결과**다. 새로운 Jev 정책으로 한 판 전체를 두었을 때의 승률이 아니다.

| 선택 정책 | 후보 착점 뒤 엔진이 끝까지 둔 결과에서, 현재 차례 쪽이 이긴 비율 |
|---|---:|
| 엔진 | 49.4% |
| 고정 규칙 | 49.4% |
| Jev 목적 선택 | 48.3% |
| 균등 무작위 기대값 | 50.4% |

Jev는 엔진 수를 정·역순 합계 73/356번 바꿨다. 엔진 대비 결과가 좋아진 국면은 3개, 나빠진 국면은 5개였다. 평균 차이는 **−1.1%p**다. 같은 오프닝의 모든 국면을 묶은 paired bootstrap 50,000회 95% 구간은 엔진 대비 **−3.9~+1.7%p**, 고정 규칙 대비 **−3.4~+1.1%p**였다. 이 표본에서 우월성이나 동등성이 확정됐다는 뜻은 아니다.

호출과 채점 전에 “엔진과 고정 규칙 모두에 대해 95% 구간 하한이 0보다 클 때만 전체 대국으로 진행”을 고정했다. 통과하지 못했다. 조건을 사후에 완화하거나, 이 평가 표본에 맞춰 질문을 다시 고친 결과를 새 검증이라고 보고하지 않았다.

## 4. 실패 사례가 알려주는 것

손해가 난 다음 세 국면에서는 엔진 보고상 아군 돌무리가 모두 살아 있었다. 그런데 Jev가 후보의 `strategically defends` 설명을 보고 수비를 우선했다.

| 국면 | 엔진 수 | Jev 수 | 해당 GNU Go 후속 결과 |
|---|---|---|---|
| `holdout/op-000/p16` | E1 | E6 | 승 → 패 |
| `holdout/op-020/p22` | E6 | E4 | 승 → 패 |
| `holdout/op-023/p9` | D2 | H8 | 승 → 패 |

이는 “수비하는 수라는 설명”을 읽는 것과 “지금 그 수비를 다른 목적보다 우선해야 하는가”를 판단하는 것이 다른 과제임을 보여준다. 단, alive라고 해서 전략적 수비가 항상 불필요하다는 뜻은 아니다. 이 세 사례만으로 생존한 그룹의 수비를 전부 금지하는 규칙을 정답으로 만들면 안 된다.

다음 개선 후보는 목적별 긴급성·손실 크기를 더 명시적으로 판단하거나, 근거가 약한 개입을 엔진 유지로 돌리는 것이다. 이 자료에 맞춰 고친 경우에는 별도의 새 오프닝에서 검증해야 한다. 현재 확인한 것은 **입력 해석 개선**이며, **우선순위 정책의 성능 향상은 아직 확인하지 못했다.**

## 검증·재현·보존

- Go 관련 테스트 21개 통과. 위협과 직접 공격 구분, 아군 색/생사 결합, 정답 변경 시 요청 불변, 순서 반전의 정확한 짝짓기, 소수 정답 종류의 오류 집계, 엔진 순위·분기 결과 비노출, GTP의 critical 응답 파싱을 검사한다.
- 새 오프닝 30개의 대칭 계열 중복 없음, 기존 세트와 겹침 없음, 178국면 후보 보존, 445분기의 종국 점수, 각 오프닝 안의 엔진 기준 승자 일관성을 확인했다.
- 우선순위 시험 최초 실행은 `dragon_status`의 `critical F8 F8` 같은 응답을 상태 문자열 전체로 읽는 문제를 발견해 **invalid**로 표시했다. 그 실행의 결론을 사용하지 않고, 파싱을 수정하고 회귀 테스트를 추가한 `v2`를 인용했다. 최초 실행도 비용과 증거 보존을 위해 남겼다.
- 총 실제 API 사용량(폐기 실행 포함): 입력 1,075,396토큰, 출력 68,044토큰. API 요청 1,348회. 가격을 추정해서 비용으로 표기하지 않았다.
- 기존 대국 코드·README·결과 파일은 덮어쓰지 않았다.

코드: `go/understanding_probe.py`, `go/build_understanding_holdout.py`, `go/priority_probe.py`.

주요 결과:

- `go/matches/understanding-holdout-positions-20260922.json`: 새 오프닝과 선택된 178국면.

# 기존 결과와 겹치지 않는 이름을 쓴다. API 명령에는 유효한 Agent vault 토큰이 필요하다.
