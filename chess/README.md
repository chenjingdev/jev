# Jev 체스 판독 실험

Jev가 표준 체스 표기에서 말의 위치·색·종류를 읽고 한 수 체크메이트를 찾는지 분리해 검사한다. 사용자 목적은 모델의 한계 확인이다. 체스 엔진으로 정답을 계산해 모델의 선택지를 설명하지 않는다.

## 대국 실험의 현재 상태 (2026-09-22 재검증)

- 동일 오프닝 100판에서 양쪽 노이즈 ±10은 반복 무승부를 90→57판, 오프닝 이후 30착수 이내 반복을 52→7판으로 줄였다. 체크메이트는 10→43판으로 늘었다. 초반 반복 감소와 더 늦은 반복으로의 이동을 구분한 집계는 아래 **노이즈 실험 재검증** 절에 있다.
- Jev의 대국 점수 개선·동등함·무효는 아직 확정하지 않았다. 드물게 개입하는 무작위 대조군 100판을 추가했고, 점수율은 52.0%였다. 기존 confidence ≥0.4 Jev의 54.5%와 차이는 +2.5%p, 오프닝 단위 95% 구간은 −5.0~+10.5%p다.
- 한쪽만 노이즈를 넣은 비교에서 ±10의 점수율은 48.0%, 오프닝 단위 95% 구간은 43.0~53.0%였다. 성능 손실이 없음을 입증한 결과가 아니다.
- 완료본 8조건·800판의 재검증 자료는 `reports/noise-audit-20260922.json`, 재현 코드는 `reports/audit_noise_results.py`다. 실험을 이어갈 때 아래 **다음 실행 전에 고정할 항목**을 확인한다.

## 3D 엔진 아레나

`arena/`는 쓰레드 게시용 **9:16 세로형 관전 화면**이다. 위에는 정사각형 3D 보드, 아래에는 양쪽 엔진 이름과 큰 Jev 상태 표시만 남긴다. `Jev 비활성`은 회색, 기록된 선택이 있는 `Jev 활성`은 녹색, 엔진의 수를 바꾼 `Jev 개입`은 금색과 파동으로 구분한다. 후보 확률·성능 수치·설명·기보는 화면에서 제거했다. 아이보리·세이지 색상과 직교 카메라를 사용하며 보드 회전·확대와 3가지 시점 전환을 지원한다.

재생 버튼은 게시물 바깥에 있고, 게임 선택·시점·효과 미리보기는 접힌 `설정` 안에 있다. `이미지 저장`으로 조작 UI가 빠진 **1080×1920 PNG**를 내려받는다. 효과 예시가 켜져 있으면 예시 표시도 이미지 안에 함께 저장된다. 실제 대국은 아래 CLI로 실행하고, 화면은 그 기록을 재생한다. 화면에서 대국을 새로 실행하거나 실시간 스트리밍하는 기능은 아직 없다.

Jev가 수를 바꾼 장면은 엔진 원래 수를 청록색 점선, 실제 Jev 선택을 굵은 금색 화살표로 함께 표시한다. 도착 칸의 고리와 아래 두 좌표 카드로 경로를 구분하며, 이는 미래 예상 수순이 아닌 해당 한 수의 비교다. 일반 착수와 Jev가 엔진 선택을 유지한 착수는 이동 220ms + 대기 120ms로 빠르게 재생한다. 개입 착수는 비교 900ms → 이동 700ms → 결과 1,100ms로 약 2.7초 동안 보여준다. 이 시간은 관전 연출이며 실제 엔진/API 연산 시간이 아니다. 동작 줄이기를 사용하면 이동 애니메이션을 생략하고 같은 길이로 국면을 유지한다.

```sh
cd chess/arena
npm install
npm run build
cd ../..
python3 chess/arena_server.py
```

화면: http://localhost:3470

실제 Jev 대결: http://localhost:3470/?match=jev-smoke-03&ply=3 . 아래 기본 Sunfish 기록과 구분한다.

현재 `sunfish-smoke.json`은 Jev 없이 만든 기준선 대국이므로 `Jev 비활성`이라고 표시된다. `효과 미리보기`는 개입 표시와 보드 효과만 시험하며 예시 확률·지연 시간은 생성하지 않는다. 대국 로그를 변경하지 않으며 이미지로 저장할 때도 예시임을 명시한다. 실제 대국 로그의 move 항목에 아래 `jev` 필드를 넣으면 활성/개입 상태를 표시한다. `selected_move`가 없거나 오류 또는 `enabled: false`가 기록된 경우에는 비활성이다.

```json
{
  "uci": "g1f3",
  "jev": {
    "base_move": "g1h3",
    "selected_move": "g1f3",
    "intervention": true,
    "confidence": 0.73,
    "latency_ms": 18,
    "reason": "선택적 설명 문장",
    "candidates": [
      {"move": "g1f3", "probability": 0.73, "selected": true},
      {"move": "g1h3", "probability": 0.27, "selected": false}
    ]
  }
}
```

청록색 궤적은 엔진 기준 수, 금색 궤적과 입자는 Jev가 선택을 바꾼 수다. `confidence`와 `probability`는 0~1 범위의 로그 데이터로 유지하지만 간결한 관전 화면에는 표시하지 않는다. 정답이나 엔진 평가값을 Jev 입력에 넣지 않는 아래 제1원칙은 이 아레나에서도 그대로 적용한다.

3D 말·보드는 [3DAssets.dev의 Chess Set and Board](https://3dassets.dev/packs/classic-chess-essentials), 조명은 [Poly Haven Studio Small 09](https://polyhaven.com/a/studio_small_09), 목재 표면은 [American Walnut Veneer](https://polyhaven.com/a/american_walnut_veneer)를 사용했다. 모두 CC0이고, 내려받은 파일 옆의 `ATTRIBUTION.md`와 `arena/THIRD_PARTY_NOTICES.md`에 출처와 라이선스를 기록했다.

> **제1원칙 — Jev에게 정답을 제공하지 않는다.** API 입력에는 엔진 평가값, 최선 수, 체크·체크메이트 표시, 공격자, 합법 응수 목록·개수, must-block 같은 정답 파생 정보를 넣지 않는다. 일반 체스 규칙, 현재 기물·좌표·차례, 모든 항목에 동일하게 적용한 기계적 상태 변환, 닫힌 후보 목록만 허용한다. 엔진 정답은 모든 Jev 호출 뒤 채점에만 사용한다. 실험용 표본을 균형 있게 고를 때 정답을 사용할 수 있지만, 그 선택 사실과 라벨은 모델에 보내지 않는다.

**후속 결과:** 좌표를 숫자로도 표시하고 일반 이동 규칙을 명시한 기물별 Noul을 합치자, 체크 감지가 기존 20쌍 40국면에서 37/40으로 개선됐다. 따라서 아래의 이전 실험에서 실패했다는 사실을 “Jev가 공격 관계를 계산할 능력이 없다”는 확정으로 읽으면 안 된다. 단일 질문, 표현, 작업 분해를 바꾸면 성능이 크게 달라진다. 체크메이트 판별의 안정적인 해결은 아직 달성하지 못했다. 자세한 내용은 마지막 절 참조.

## 데이터와 정답

[Lichess 공개 퍼즐 데이터](https://database.lichess.org/#puzzles)는 CC0다. 전체 압축 파일을 저장하지 않고 앞부분을 스트리밍해, 아래 조건의 첫 백 차례 10개·흑 차례 10개를 선택했다. 이번 추출은 310행에서 끝났다. 선택된 원본 행의 주요 필드·출처·시점은 `positions.json`에 보존한다. 퍼즐 레이팅은 403~1703, 판 위 말 수는 11~30개다. 전체 데이터베이스의 균등 무작위 표본이 아니다.

- `mateIn1` 태그와 두 수짜리 풀이가 있는 국면.
- Lichess의 원본 FEN은 상대 수 이전이다. 첫 번째 UCI 수를 적용한 **이후 FEN**을 문제로 쓴다.
- `python-chess`로 유효 국면과 모든 합법 수를 검사해 체크메이트가 유일한 경우만 사용한다. Lichess 풀이 두 번째 수와도 일치해야 한다.
- 정답과 같은 말의 다른 합법 수가 네 개 이상이고, 그중 메이트가 아닌 체크가 있어야 한다.
- 메이트 후보는 정답 + 같은 말의 합법적인 오답 4개이며, 오답 중 하나는 체크지만 메이트가 아니다. 승격은 이 표본에서 제외한다. UCI 좌표만 쓰고 SAN의 `+`·`#`로 답을 드러내지 않는다.

원본 퍼즐 ID·풀이·레이팅·출처 URL은 모델 입력에서 제외한다. 정답은 화면의 사후 평가에만 사용한다. 공개 퍼즐이 모델 학습에 포함됐는지는 알 수 없다.

## 단계와 입력

| 단계 | 질문 | 후보 |
|---|---|---|
| 위치 | 말이 있는 칸은? | 실제 말 1칸 + 빈칸 4개 |
| 색 | 지정한 칸의 말은 흑/백? | black / white, 정답 수 10개씩 |
| 종류 | 지정한 칸의 말 종류는? | 정답 종류 + 다른 종류 4개 |
| 메이트 | 지금 체크메이트하는 수는? | 정답 1개 + 합법적인 비메이트 수 4개 |

질문은 영어, 모델은 `jev-1.13.0`, Choice의 옵션 설명은 모두 `null`이다. 5지선다 정답의 기본 순번은 20문제에서 각 위치에 4번씩 배치했다. 원본·동일 요청 반복·선택지 순서 변경을 비교한다. 동일한 문제와 선택지를 두 입력 방식에 사용한다.

1. **FEN 원문**: `state={"fen":"..."}`. 색·종류 과제만 `coordinate`를 추가한다. [python-chess의 FEN·수 검증 문서](https://python-chess.readthedocs.io/en/latest/core.html)를 사용했다.
2. **좌표별 말 목록 · 코드 보조**: `pieces={"a1":"white rook",...}`와 차례·캐슬링·앙파상 상태를 전달한다. 코드가 FEN을 말의 위치·색·종류로 풀어주는 조건이다. 이 조건의 기본 판독 만점은 모델이 FEN을 직접 해석했다는 뜻이 아니다. 공격 지도·체크 여부·메이트 정답은 전달하지 않는다.

## 측정 (2026-09-20)

실전 국면 20개 × 4과제 × 2입력 × 3조건 = 480요청, 추정 비용 $0.0114. `results.json`에 모든 요청 본문(키 제외), 출력 확률·confidence, 정답·조건·지연·토큰을 저장했다.

| 과제 | FEN 원본 | FEN 반복 | FEN 순서 변경 | 말 목록 원본 | 말 목록 반복 | 말 목록 순서 변경 |
|---|---|---|---|---|---|---|
| 말 위치 | 18/20 | 17/20 | 13/20 | 20/20 | 20/20 | 20/20 |
| 말 색 | 19/20 | 19/20 | 18/20 | 20/20 | 20/20 | 20/20 |
| 말 종류 | 18/20 | 18/20 | 18/20 | 20/20 | 20/20 | 20/20 |
| 한 수 체크메이트 | 6/20 | 7/20 | 6/20 | 7/20 | 5/20 | 7/20 |

이번 표본에서는 FEN 기본 판독 성적이 높지만 완벽하지 않고, 말 위치 선택은 순서 변경에 흔들린다. 전술 과제는 FEN을 목록으로 풀어줘도 5~7/20이다. 기본 판독과 메이트 판단의 난점이 다를 수 있다는 결과이며, 모델 내부 처리 과정을 확정한 것은 아니다.

## 해석의 한계

- 480개 독립 국면이 아니라 20국면의 여러 과제·입력·반복이다. 체스와 오목의 국면·규칙·표기·난이도도 다르므로 점수 차이로 학습 데이터 양을 추정하지 않는다.
- 이 색 질문 표본은 일반적인 진영 배치가 많다. 단순히 “1~4행이면 백, 5~8행이면 흑”이라고 답해도 18/20이다. 따라서 색 19/20을 정밀한 색 판독이 완전히 검증된 것으로 과장하지 않는다.
- 종류 정답은 폰 7·비숍 3·룩 2·퀸 2·킹 3·나이트 3개로 완전히 균등하지 않다. 전술 문제는 동일 말의 대안 수를 충분히 만들 수 있는 국면으로 제한했다.
- 오답이 모두 합법 수이므로 **합법 수 생성 능력은 측정하지 않는다**. 메이트 후보의 범위를 줄인 도움도 포함된다.
- 후보 설명은 없지만 `pieces` 방식은 판독을 코드가 보조한 입력이다. 모델이 스스로 해당 정보를 추론한 결과로 세지 않는다.

`test_probe.py` 22개가 통과했다. FEN을 별도로 해석해 말 위치·색·종류를 교차 검증하고, 모든 메이트 후보의 합법성·유일 정답·비메이트 체크 포함·정답 순번 균형·요청에 풀이 정보가 들어가지 않는 것을 검사한다.

## 백 나이트는 현재 어디에 있는가? (2026-09-20)

`knight.py`는 실제 Lichess 대국의 SAN 수순을 주고, 모든 수를 둔 뒤 백 나이트가 있는 칸을 고르게 한다. 기존 “지정 좌표의 말 색/종류”와 달리 **기보에서 원하는 말의 현재 위치를 찾는 과제**다.

기존 퍼즐의 원본 대국을 공개 PGN으로 내려받아 표준 초기 배치부터 합법 수순을 재생했다. 실제 대국 10개에서 초반(양측 합산 12회 착수)과 이후(36~39회 착수)를 각각 하나씩 골라 20국면을 만들었다. `knight_positions.json`에 원본 대국 ID, 출처, SAN movetext, UCI 수순, 현재 FEN과 평가용 정답을 저장한다. 플레이어 이름·풀이·평가 정보는 모델에 전달하지 않는다.

현재 백 나이트가 둘 이상이어도 **선택지 안에는 백 나이트 위치를 정확히 하나만** 넣는다. 시작 칸 b1/g1에 그대로 있는 나이트는 정답에서 제외한다. 오답에는 가능한 경우 나이트가 떠난 옛 빈칸, 흑 나이트, 다른 백 기물을 넣고 나머지를 채운다. 20문제 중 19개에 옛자리 오답이 포함됐다. 좌표 5개의 설명은 모두 null이고 정답 순번은 균등 배치했다. 판에 있는 모든 백 나이트를 자유 응답으로 열거하는 시험은 아니다.

두 입력에 동일한 선택지를 사용한다.

- **PGN 수순:** `{"pgn_moves":"1. e4 e5 2. ... *"}`. 표준 초기 배치에서 시작한 SAN movetext만 주며 현재 FEN은 보내지 않는다.
- **현재 FEN:** `{"fen":"..."}`. 수순 없이 현재 판만 준다.

공통 질문은 “현재 백 나이트가 있는 후보 칸을 고르라. 이전에 있던 자리가 아니라 모든 착수 이후의 위치를 고르라”이다. PGN에는 SAN의 N이 나이트라는 표기 규칙만 설명한다.

| 입력 | 초반 원본 | 이후 원본 | 전체 원본 | 동일 요청 반복 | 선택지 순서 변경 |
|---|---|---|---|---|---|
| 현재 FEN | 9/10 | 9/10 | 18/20 | 18/20 | 18/20 |
| PGN 착수 수순 | 10/10 | 9/10 | 19/20 | 20/20 | 20/20 |

120요청, 추정 비용 $0.0025. 원본 PGN에서 유일한 오답은 index 2: 현재 정답 c3 대신 옛자리 e2를 선택했다. FEN 원본 오답은 index 18(f3 대신 옛 c3), index 19(c3 대신 옛 b1)였다. `results_knight.json`에 실제 입력과 확률을 보존한다.

이 표본에서는 백 나이트의 위치를 수순에서 추적하는 선택 과제가 잘 됐다. 학습 데이터 양, 전체 체스판의 정확한 재구성, 모든 기물이나 더 긴 기보에서 같은 성능이 보장된다는 뜻은 아니다. 20국면은 독립 대국 20개가 아니라 10대국의 두 시점이며, FEN과 PGN의 1문제 차이를 우열로 확정하지 않는다.

검증 테스트 21개: SAN 재생과 UCI 재생의 FEN 일치, 독립 FEN 해석으로 백 나이트 위치 확인, 정답 유일성, 옛자리의 현재 빈칸 여부, PGN 요청에 현재 FEN/정답이 섞이지 않는지를 검사했다. 실행은 `op run` 환경에서 `.venv/bin/python chess/knight.py`, 테스트는 `.venv/bin/pytest chess/test_knight.py -q`다. `/` 화면에 백 나이트 위치 찾기와 PGN 입력을 추가했다.

## 입력 필드명만 바꾸는 비교 (2026-09-20)

`field_names.py`로 백 나이트 위치 과제의 `state` 키를 `pgn_moves`, `moves`, `data`, `x`로 바꿨다. 기보 문자열, 선택지와 나열 순서, 모델, 질문 ID, 지시문은 모두 동일하다. 지시문에서 특정 키를 참조하던 부분은 공통 문장 “The supplied text is standard SAN movetext...”로 한 번 바꿔 모든 실험군에 고정했다. 키만 바꾸면서 질문이 존재하지 않는 옛 필드를 가리키는 오류를 피했다. 따라서 과거 다른 문구로 실행한 19/20과 직접 비교해 향상됐다고 주장하지 않는다.

## 원래 기물의 이동·잡힘·캐슬링 추적

`tracking.py`는 실제 대국 10개에서 원래 폰 이외의 16기물(양측 나이트 4·비숍 4·룩 4·퀸 2·킹 2)을 추적한다. 같은 종류의 말을 구별하려고 “처음 b1에 있던 백 나이트”처럼 원래 출발 칸과 색·종류를 질문에 명시한다. 잡혔으면 `not_on_board`가 정답이다. 판에 같은 종류의 다른 말이나 승격한 말이 있어도 원래 기물의 정체성을 바꾸지 않는다.

## 현재 국면이 체크메이트인가

`checkmate.py`는 기존 20개 퍼즐의 같은 부모 국면에서 두 자식 국면을 만든다. 하나는 실제 메이트 수를 둔 뒤이고, 다른 하나는 메이트 후보와 같은 말로 **체크만 했지만 상대에게 합법적인 탈출 수가 남은** 뒤다. 총 40국면 모두 수를 둘 차례인 왕이 체크되어 있으므로, 체크 여부만 알아내서는 정답을 맞힐 수 없다.

Jev에는 정답·직전 수·합법 수 목록을 보내지 않는다. “현재 수를 둘 차례가 체크 상태이며 합법적인 탈출 수가 하나도 없는가”라는 동일한 Noul 하나만 묻고, 0.5 이상을 체크메이트로 판정한다. FEN 원문과 코드가 푼 좌표별 말 목록을 각각 3회 측정한다. `python-chess`는 API 호출 전에 모든 양성 국면이 실제 체크메이트이고, 모든 음성 국면이 체크지만 탈출 수가 있음을 독립 검증한다.

실행은 `op run` 환경에서 `.venv/bin/python chess/checkmate.py`, 검증은 `.venv/bin/pytest chess/test_checkmate.py -q`다. 결과와 실제 요청·확률은 `results_checkmate.json`에 저장한다.

측정 결과 Jev는 **240판단 모두 체크메이트가 아니라고 답했다.** 따라서 균형 표본의 정확도는 FEN 60/120, 말 목록 60/120이지만, 이는 음성 60개만 전부 맞히고 실제 체크메이트 60개를 전부 놓친 값이다.

| 입력 | 실제 메이트를 yes | 탈출 가능한 체크를 no | 평균 yes 확률: 메이트 / 비메이트 |
|---|---:|---:|---:|
| FEN | 0/60 | 60/60 | 0.064 / 0.066 |
| 좌표별 말 목록 | 0/60 | 60/60 | 0.109 / 0.111 |

같은 부모 국면의 대응쌍에서 실제 메이트 쪽 확률이 더 높았던 경우도 FEN 15/60, 말 목록 14/60뿐이었다(동률 22·23, 오히려 낮음 23·23). 즉 0.5 임계값만 잘못 정한 문제가 아니라 두 부류의 순서도 구분하지 못했다.

Noul의 yes/no 방향만 확인하려고 한 별도 호출에서는 `side_to_move_in_check=true, legal_move_count=0`을 명시하면 3회 모두 0.98, 합법 수를 1개로 명시하면 0.05·0.06·0.05가 나왔다. 이 입력은 체크메이트의 정의와 정답을 사실상 직접 준 것이므로 **체스 이해 능력의 대조군으로 볼 수 없다.** 확인되는 것은 Noul 값을 반대로 읽은 구현 오류가 없다는 점뿐이다. 체스 능력에 관한 유효한 결과는 FEN 또는 말 목록만 제공한 실험에서 두 부류를 구분하지 못했다는 것이다. 비용은 본 실험 $0.0052이며, 이 방향 확인 호출의 비용은 포함하지 않았다.

### 흑·백 차례 명시와 Noul 편향 재검사

첫 실험의 FEN 상태는 활성 색을 FEN의 `w`/`b`에만 담았고, 말 목록에는 `turn` 필드로 명시했다. 이 차이가 실패 원인인지 확인하려고 `checkmate_prompt.py`에서 40국면 모두에 `side_to_move: White|Black`, `opponent: Black|White`를 추가하고, 질문에도 매번 “White/Black is the side to move”와 “is White/Black currently checkmated?”를 직접 넣었다.

공식적으로 yes/no에는 Noul이 맞지만, Noul의 낮은 확률로 모두 no가 된 현상도 분리하기 위해 동일 상태에 `yes`/`no` Choice를 진단용으로 함께 시험했다.

| 입력·프리미티브 | 전체 | 실제 메이트를 yes | 탈출 가능한 체크를 no | 평균 yes 확률: 메이트 / 비메이트 |
|---|---:|---:|---:|---:|

## Jev 판단을 기물별로 분해해 체크 감지 개선

`jev_attack_pipeline.py`는 현재 판에서 모든 상대 기물을 나열하고 기물 하나마다 “이 말이 현재 우리 왕을 공격하는가?”라는 Noul을 보낸다. 상태에는 전체 기물의 색·종류·좌표와 숫자 좌표(a=1~h=8, rank=1~8)를 주고, 각 질문에는 그 기물의 일반적인 공격 이동 규칙과 경로를 막는 말 처리 규칙을 쓴다. 질문 ID 자체에는 의존하지 않고 질문 본문에 대상 기물과 왕을 명시한다. 특정 판의 공격 여부, 공격선, 합법 수, 엔진 평가는 제공하지 않는다.

예를 들어 하나의 질문은 `White bishop f5 (column 6, rank 5)`가 `Black king g6 (column 7, rank 6)`을 공격하는지를 묻고, 비숍의 대각선 규칙과 중간 기물이 공격을 막는다는 일반 규칙을 함께 준다. 모든 상대 기물을 빠짐없이 질문하므로 정답 공격자를 코드가 골라주는 방식이 아니다. 0.5 이상인 응답이 하나라도 있으면 코드가 체크로 집계한다. 이 OR 결과는 보정된 확률로 주장하지 않는다.

네 가지 방식을 사전에 정하고, 기존 `check_detection.py`의 부모 1~10번 20국면에서 점검한 뒤 **같은 질문과 0.5 기준을 고정해** 부모 11~20번 20국면을 평가했다. 이전 실험에도 쓰였던 국면이므로 신규 대국 일반화 검증과는 다르다. 동일 부모의 두 국면은 같은 묶음에 넣었다. 반복 호출을 독립 표본으로 합산하지 않았다.

| 방식 | 앞 10쌍 | 뒤 10쌍 | 합계 |
|---|---:|---:|---:|
| 좌표표에서 체크를 한 번에 질문 | 14/20 | 11/20 | 25/40 |
| 기물별 공격 여부 → OR | 18/20 | 19/20 | **37/40** |
| 기물별 이동 모양·전체 경로 비어있음을 따로 질문 → AND/OR | 18/20 | 18/20 | 36/40 |
| 이동 모양 → 각 장애물이 경로 내부에 있는지 개별 질문 → AND/OR | 13/20 | 15/20 | 28/40 |

기물별 공격 방식의 전체 혼동행렬은 TP 19, FN 1, TN 18, FP 2다. 이전 FEN 문자열 Noul은 첫 반복에서 22/40(TP 2, TN 20)이었다. 새 실험은 입력 표현, 이동 규칙 설명, 분해를 함께 바꾸므로 개선분 전체를 분해 하나의 효과라고 할 수 없다. 새 실험 안에서는 동일 좌표 상태를 주고 질문의 범위·설명·합성 방식을 비교했다. 너무 잘게 나눈 좌표 내부 판정은 오답이 누적돼 오히려 나빴다.

비교용 질문을 모두 뺀 실제 사용 함수 `infer_check(fen)`도 구현했다. 국면당 API 요청 하나로 기물별 공격 질문만 평가한다. 뒤 10쌍을 이 경로로 다시 실행한 결과도 **19/20(TP 10, TN 9, FP 1)**이었다. 이것은 같은 20국면의 재실행이며 새로운 표본으로 세지 않는다. 20요청·218판단, 입력 48,840토큰, 현재 입력 토큰 가격으로 약 $0.002051이다.

역할 구분:

- **Jev:** 기물의 공격 이동 규칙 적용, 좌표 관계 해석, 막는 말의 영향 판단.
- **코드:** FEN을 기물 목록·숫자 좌표로 변환, 모든 기물 질문 작성, Noul 임계값 적용과 AND/OR 집계.
- **python-chess:** 기존 국면 준비 및 평가용 정답 계산에만 사용. `infer()`와 `infer_check()`는 엔진 공격/합법 수 함수를 호출하지 않는다.

실제 요청·응답은 `results_jev_attack_development.json`, `results_jev_attack_evaluation.json`, `results_jev_attack_evaluation_per_piece.json`에 보존했다. 두 비교 묶음과 실제 경로 확인의 합산 입력 토큰 비용은 약 $0.016719이다. 재현 명령은 API 키를 주입한 환경에서 `.venv/bin/python chess/jev_attack_pipeline.py --split development`, `--split evaluation`, `--split evaluation --mode per_piece`다. 이미 결과 파일이 있으면 덮어쓰지 않고 중단한다.

### 다음 병목: 탈출 수를 찾는 질문

`jev_mate_pipeline.py`는 기물별 공격 판정을 다음 요청에 **검증되지 않은 Jev 예측**으로 전달하고, 아군 기물마다 “이 말로 왕을 안전하게 만드는 합법 수가 하나라도 있는가?”를 묻는다. 공격자가 있다고 판단하면서 아군 모두가 탈출 수 없다고 답하면 메이트로 합성한다. 합법 수 생성이나 정답 공격자 전달은 하지 않는다.

앞 10쌍 20국면에서 체크는 19/20을 감지했지만, 탈출 수 존재 판정은 전부 yes 쪽으로 흘러 메이트 판별은 10/20(TP 0, TN 10)이었다. 같은 새 좌표 상태의 직접 메이트 질문은 13/20(TP 4, TN 9)이었다. 따라서 기물별로 나눠도 “가능한 수를 스스로 찾아라”는 질문은 아직 해결되지 않았다. 개발 묶음에서 실패해 이 구조의 뒤 10쌍 평가는 실행하지 않았다. 결과는 `results_jev_mate_development.json`, 추가 입력 토큰 비용은 약 $0.004780이다.

후속 설계는 구체적인 이동 후보를 Jev가 선택하거나 전체 좌표 후보로 열거한 뒤, 각 후보의 이동 가능성과 이동 후 왕의 안전을 별도로 Jev에게 검증시키는 방식이다. 단, 일부 제안만 검증해서 탈출 수를 못 찾은 것과 **어떤 탈출 수도 없음**은 다르다. 체크메이트를 확정하려면 후보 누락과 잘못된 합법성 판단까지 검증해야 한다. 현재 결과는 체크 감지 개선이며 체크메이트를 풀었다는 결과가 아니다.

검증 테스트 6개는 전체 기물·후보 누락 여부, 좌표 변환, 정답 필드 미포함, 모델 응답을 바꾸면 합성 결과가 달라지는지, 부모 단위 개발/평가 분리를 확인한다. 실행: `.venv/bin/pytest chess/test_jev_attack_pipeline.py chess/test_jev_mate_pipeline.py -q`.

## 모든 상대 기물 × 모든 아군 기물의 공격 관계

`jev_attack_map.py`는 왕으로 한정했던 목표를 모든 아군 기물로 확장한다. 기준 진영은 기본적으로 현재 차례인 색이며, `infer_attack_map(fen, perspective="White"|"Black")`로 지정할 수도 있다. 상대 기물마다 아군 기물 전부와 짝을 만들고, 각 조합을 독립 Noul로 평가한다. 예를 들어 상대 10기물·아군 12기물이면 120질문이다. 위치나 이동 규칙으로 후보를 사전 제거하지 않고 전부 Jev에게 묻는다. 토큰 여유를 두어 최대 64질문씩 요청에 묶는다.

판별 대상은 현재 배치의 **공격 관계**다. 핀된 기물도 공격하는 칸은 포함하며, 실제로 잡는 수가 합법인지, 잡은 뒤 되잡히는지, 전술적으로 이득인지는 따로 검사해야 한다. 모든 색·종류·숫자 좌표와 일반 이동/가림 규칙만 제공한다. `python-chess`는 국면 준비와 API 응답 이후 채점에만 사용한다.

기존 체크/비체크 20쌍 40국면에서 아군 기물은 합계 419개, 상대→아군 조합은 4,507개였다. 그중 실제 공격 관계는 114개(2.5%)뿐이다. 앞 10쌍과 뒤 10쌍에 같은 질문과 0.5 기준을 적용했다. 관계 수를 독립 대국 수로 취급하지 않는다.

| 지표 | 첫 번째 기물쌍 판단 | Jev 재검증 추가 |
|---|---:|---:|
| 실제 공격 발견 | 101/114 (88.6%) | 95/114 (83.3%) |
| 없는 공격을 있다고 판정 | 151개 | 80개 |
| 공격이라고 한 것 중 실제 공격 | 101/252 (40.1%) | 95/175 (54.3%) |
| 내 말이 공격받는지의 말별 정확도 | 298/419 (71.1%) | 338/419 (80.7%) |
| 내 말마다 공격자 목록 완전 일치 | 279/419 | 329/419 |
| 판 전체 공격 관계 완전 일치 | 1/40 | 3/40 |

재검증은 첫 번째 Jev가 공격이라고 판단한 252개 관계에만 적용한다. 같은 판에서 “두 좌표가 해당 기물의 이동 모양에 맞는가?”와, 룩·비숍·퀸이면 “두 칸 사이가 다른 말에 막히지 않았는가?”를 별도 Noul로 묻고 모두 0.5 이상인 관계만 남긴다. 어떤 관계를 검증할지 고르는 데 엔진 정답을 쓰지 않는다. 총 440개 추가 판단이며, 71개 오탐을 제거하는 대신 실제 공격 6개도 제거했다. 추가 판단의 확률을 보정된 최종 확률로 합성하지 않고 AND로만 집계한다.

| 묶음 | 첫 판단 TP / FP / FN | 재검증 후 TP / FP / FN |
|---|---|---|
| 앞 10쌍 | 54 / 62 / 10 | 49 / 28 / 15 |
| 뒤 10쌍 | 47 / 89 / 3 | 46 / 52 / 4 |

오탐이 많아 전체 조합 정확도는 특히 조심해서 읽어야 한다. 첫 판단의 96.4%는 **전부 공격 아님이라고 답했을 때의 97.5%보다 낮다.** 공격을 실제로 찾는 능력과 오탐을 함께 봐야 한다. 재검증 후 전체 조합 정확도는 97.8%지만 여전히 공격 판정의 약 46%가 오탐이다. 이동 후보를 확정적으로 검증하는 체스 엔진 수준의 공격표는 아니다.

원본은 `results_jev_attack_map_development.json`, `results_jev_attack_map_evaluation.json`, 재검증본은 각각 `_verified.json` 접미사가 붙은 파일에 저장했다. 최초 92요청 비용 $0.025851, 추가 검증 40요청 비용 $0.004359로 합계 약 $0.030210이다. 원본 응답은 재사용하고, 재검증 파일의 요청 수·비용 필드는 **추가 검증 비용만** 센다.

API 키를 주입한 환경에서:

```sh
.venv/bin/python chess/jev_attack_map.py --split development
.venv/bin/python chess/jev_attack_map.py --split evaluation
.venv/bin/python chess/jev_attack_map.py --split development --verify
.venv/bin/python chess/jev_attack_map.py --split evaluation --verify
```

기존 결과 파일은 덮어쓰지 않는다. Python 호출에서는 `infer_attack_map()`의 결과를 `verify_attack_map()`에 전달하면 두 단계 공격 관계표를 얻는다. 각 관계에는 source·target 좌표, 최초 Noul 확률, 재검증 확률, 최종 boolean을 보존한다. 말별로는 예상 공격자 목록을 돌려준다. 이동 후에는 배치가 바뀌므로 이전 공격표를 그대로 쓰지 말고 새 판에서 다시 판별해야 한다.

`test_jev_attack_map.py`의 6개 검증은 모든 기물쌍을 정확히 한 번씩 묻는지, 배치 크기, 진영 전환, 공격과 합법 수 의미 구분, 모델 응답만으로 공격자 집계를 만드는지, 정답 라벨을 바꿔도 검증 요청이 같음을 검사한다.

### 공격 질문에 단순히 긍정하는가: 반대 명제 검사

전체 공격표의 첫 응답은 4,507개 중 yes 252개·no 4,255개였다. 실제 공격에는 yes 101/114(88.6%), 비공격에는 yes 151/4,393(3.4%)로 반응하므로 전부 yes를 내는 모델은 아니다. 그러나 yes 252개 중 151개가 오탐이므로 “공격을 대부분 찾았다”라는 재현율만 강조해서는 안 된다.

`jev_attack_polarity.py`는 질문 방향에 따라 긍정하는 문제를 검사한다. 각 부모의 체크 국면에서 실제 공격 하나와 **같은 공격자가 공격하지 않는 다른 대상** 하나를 골라, 공격 20개·비공격 20개의 진단 표본을 만들었다. 선택은 고정 난수와 정답 라벨에만 의존하며, 이전 Jev 확률이나 정오답으로 표본을 고르지 않았다. 정답은 API 입력에 들어가지 않는다.

같은 상태와 같은 일반 이동·가림 규칙 아래, 각 관계에 `Does A currently attack B?`와 `A does NOT currently attack B. Is this statement true?`를 독립 Noul로 물었다. 0.5를 기준으로:

| 실제 관계 | “공격한다”에 yes | “공격하지 않는다”에 yes |
|---|---:|---:|
| 실제 공격 20개 | 17개 | 9개 |
| 실제 비공격 20개 | 4개 | 17개 |

긍정형 질문의 정답은 33/40, 부정형은 28/40이었다. 두 명제에 **동시에 yes인 관계가 7/40**, 반대로 답한 관계가 33/40, 동시에 no인 관계는 0개였다. 평균 `abs(P(공격)+P(비공격)-1)`은 0.1735다. 이 결과는 두 표현이 논리적으로 일관되게 처리되지 않음을 보여준다. 다만 긍정 편향·부정문 해석 오류·질문 민감도 중 어느 내부 원인이 주된 원인인지는 이 결과만으로 확정할 수 없다. 응답이 서로 반대여도 정답이 보장되는 것은 아니다.

이는 균형을 맞춘 진단 표본이므로 전체 공격표의 40.1% 정밀도와 직접 비교할 정확도가 아니다. “좌표 정보를 전혀 구분하지 않고 모두 긍정한다”는 설명은 맞지 않지만, 원래 공격 여부 질문만으로 나온 yes를 확인된 공격 사실로 취급하는 것도 부적절하다. 결과는 `results_jev_attack_polarity.json`이며 20요청·80판단, 입력 토큰 비용 약 $0.001332이다.

## 순차 레이어: 좌표 차이 → 이동 형태 → 방해물

`jev_attack_layers.py`는 위 반대 명제 검사와 **같은 공격 20개·비공격 20개**를 사용해, 하나의 yes/no 질문을 검증 가능한 중간 출력으로 분해했다. 앞 층의 실제 Jev 선택을 다음 API 요청의 state/instructions에 전달한다. 같은 요청의 질문은 서로 답을 볼 수 없으므로 의존하는 층은 별도 요청이다.

1. `Choice`: target column − source column과 target rank − source rank를 각각 −7…+7 중 선택.
2. `Choice`: Jev가 선택한 두 차이와 해당 기물의 일반 이동 규칙을 받아 `valid / invalid` 선택.
3. 룩·비숍·퀸이고 2층이 valid이면 두 방식 비교:
   - 모든 다른 기물마다 `between / not_between` Choice를 병렬 평가하고 하나라도 between이면 막힘.
   - 모든 다른 기물 좌표와 `none`을 한 Choice에 넣어 실제 방해물 하나 또는 none 선택.
4. 코드가 `valid AND no blocker`로 공격 여부를 합성한다.

코드는 숫자 좌표와 모든 후보를 나열하고 Jev 응답을 연결할 뿐, 추론 중 좌표 차이·이동 형태·방해물 여부를 계산하지 않는다. python-chess와 수식은 모든 Jev 호출이 끝난 뒤 각 층을 채점하는 데만 사용한다. 정답 라벨과 과거 Noul 응답을 바꿔도 레이어 요청이 바뀌지 않는지 테스트했다.

| 방식/층 | 결과 |
|---|---:|
| 동일 표본의 단일 긍정형 Noul | 33/40 |
| 파일 차이 Choice | 40/40 |
| 랭크 차이 Choice | 40/40 |
| 이동 형태 valid/invalid Choice | 40/40 |
| 모든 장애물 between/not_between → 최종 공격 | 36/40 (TP 16, TN 20, FP 0, FN 4) |
| 방해물 하나/none Choice → 최종 공격 | **39/40 (TP 19, TN 20, FP 0, FN 1)** |

방해물 Choice가 적용된 슬라이딩 관계는 20개였다. 실제로 막힌 비공격 3개에서는 모두 실제 방해물을 골랐고, 열린 공격선 17개 중 16개에서 none을 골랐다. 한 오답은 g4 룩→d4 폰 사이에서 대상 너머의 c4를 방해물로 고른 경우다. 모든 장애물을 독립 평가한 방식은 열린 공격선에서 무관한 좌표를 between이라고 고른 오답이 누적됐다. 이 실험에서도 **더 세분화한다고 항상 좋아지지 않았고, 후보들이 경쟁하는 하나의 Choice가 더 안정적**이었다.

막힌 선 3개는 적으므로 `jev_blocker_choice.py`로 별도의 균형 진단을 했다. 전체 40국면에서 이동 형태가 맞는 슬라이딩 관계를 골라 열린 선 20개와 막힌 선 20개를 구성했다. 정답은 표본 선택과 사후 채점에만 사용하며, API에는 끝점을 제외한 모든 occupied square와 `none`을 제공한다.

| 방해물 Choice 진단 | 결과 |
|---|---:|
| 열린 선에서 none 선택 | 18/20 |
| 막힌 선에서 실제 방해물 선택 | 18/20 |
| 합계 | **36/40** |

레이어 결과는 39/40이지만 같은 20개 부모 국면에서 만든 진단 표본이며 새로운 대국에 대한 일반화 검증은 아니다. 좌표 차이와 이동 형태가 이 표본에서 완벽했다는 뜻이지 모든 좌표 조합에서 완벽하다는 뜻도 아니다. 그래도 같은 표본의 단일 Noul 33/40보다 명확히 좋아져, Jev의 최대 능력을 끌어내는 방향으로는 **참/거짓을 직접 묻기보다 닫힌 후보에서 중간 값을 선택시키고 코드가 합성하는 층 구조**가 유망하다.

실제 요청·응답은 `results_jev_attack_layers.json`, 추가 방해물 진단은 `results_jev_blocker_choice.json`에 보존했다. 레이어 실험은 74요청·517판단·비용 약 $0.008121, 방해물 진단은 40요청·40판단·비용 약 $0.004189이다. 검증은 `.venv/bin/pytest chess/test_jev_attack_layers.py chess/test_jev_blocker_choice.py -q`다.

## 정답 없이 탈출 수를 찾는 체크메이트 파이프라인

`jev_escape_choice.py`와 `jev_escape_verify.py`는 위 제1원칙을 적용한 체크메이트 판별 경로다. 체크메이트 10개·체크지만 탈출 가능한 국면 10개로 개발 묶음을 구성하되, 라벨과 실제 합법 수는 API 입력에 넣지 않았다.

첫 요청은 현재 진영의 **각 기물마다** a1~h8의 64개 목적지와 `none`을 Choice로 준다. 질문은 “이 정확한 기물이 합법적으로 이동해 이동 후 우리 왕을 모든 상대 공격으로부터 안전하게 만들 수 있는 목적지 하나”를 고르게 한다. 합법 수 목록, 체크 상태, 공격자, 응수 개수는 없다.

선택된 non-none 좌표는 다음 Jev 층으로 검증한다.

1. source→destination의 signed file/rank 차이를 각각 Choice로 선택.
2. 선택한 차이, 기물 일반 이동 규칙, 목적지의 현재 기물을 보고 이동 모양·목적지 점유가 valid/invalid인지 Choice.
3. 슬라이딩 기물이 valid이면 모든 기물 좌표와 none 중 방해물 Choice.
4. valid이고 방해물이 없으면 코드는 해당 좌표 이동을 모든 후보에 동일하게 적용해 새 기물표를 만든다. 이 단계는 합법성을 판정하지 않는다.
5. 새 판에서 모든 상대 기물→우리 왕 관계를 `jev_attack_layers.py`의 좌표 차이·이동 형태·방해물 Choice로 다시 계산한다. 왕이 공격받지 않는다고 Jev가 판단할 때만 탈출로 인정한다.

개발 20국면 결과:

| 단계 | 결과 |
|---|---:|
| 기물별 목적지 Choice | 196선택 중 non-none 149개 |
| 그중 실제 탈출 좌표 | 8개 |
| Jev 층 검증 뒤 남은 탈출 | 12개 |
| 남은 것 중 실제 탈출 | 6개 |
| 실제 탈출 제안 8개 중 검증 통과 | 6개 |
| 최종 체크메이트/비메이트 판별 | **11/20** |

최종은 메이트 6/10, 탈출 가능 체크 5/10이다. 틀린 메이트 4개에서는 Jev가 불가능한 이동을 합법·안전한 탈출로 통과시켰고, 틀린 체크 5개에서는 실제 탈출을 제안하지 못했거나 검증에서 제거했다. 선택층의 원본 판정은 모든 판에 탈출이 있다고 보아 10/20이었다. 레이어 검증은 1개만 개선했다.

이 top-1 경로는 422개 추가 API 요청, 5,402판단, 입력 1,924,073토큰, 약 $0.080811을 사용했다. 레이어가 국소적인 공격 관계에는 효과적이어도, 많은 후보의 오류가 누적되는 **존재/부재 탐색**에서는 이 구조로 충분하지 않았다.

### Choice 전체 확률을 보존한 top-10 beam

초기 구현은 각 기물의 65개 Choice 확률 중 1등만 남겼다. 저장된 첫 Choice를 사후 분석하니 실제 탈출이 top-1에 포함된 비메이트 판은 개발 6/10·평가 5/10이지만, **top-10에는 두 묶음 모두 10/10** 포함됐다. 이 분석으로 `K=10`을 개발 묶음에서 선택한 뒤 평가 묶음에는 고정했다.

`jev_escape_beam.py`는 기물별 top-10 non-none 좌표와 none만 두 번째 Choice에 넣는다. top-10은 오직 이전 Jev 확률로 정하며 엔진 합법 수·정답을 쓰지 않는다. 두 번째 Choice 결과를 기존 검증층에 전달한다.

| 파이프라인 | 개발 20국면 | 고정 평가 20국면 |
|---|---:|---:|
| 64칸 Choice 1등만, 검증 전 | 10/20 | 10/20 |
| 1등 좌표 + 레이어 검증 | 11/20 | 실행하지 않음 |
| top-10 → 두 번째 Choice, 검증 전 | 10/20 | 10/20 |
| **top-10 → 두 번째 Choice → 레이어 검증** | **16/20** | **12/20** |

개발 결과는 메이트 7/10·탈출 가능 체크 9/10이었지만, 평가에서는 각각 6/10·6/10으로 떨어졌다. 평가 검증층은 탈출 18개를 승인했는데 실제 탈출은 4개뿐이었다. 개발에 맞춰 선택한 beam 폭과 현재 검증 프롬프트가 새로운 절반에 일반화됐다고 볼 수 없다.

비용도 크다. top-10 두 번째 Choice는 개발 $0.005010·평가 $0.005633이고, 이후 검증은 개발 346요청·4,564판단·$0.068989, 평가 452요청·6,667판단·$0.100514다. 최초 64칸 Choice 비용은 개발 $0.019111·평가 $0.021533이다.

`jev_move_validator.py`로 구체적인 이동 전·후 기물표를 한 번에 `legal_safe / illegal_piece_move / blocked_path / king_still_attacked / uncertain` 중 선택하게 하는 검증기도 시험했다. 개발에서 실제 탈출 20개·가짜 top-10 후보 20개의 균형 표본에 27/40(TP 13, FP 6, TN 14, FN 7)이었다. 다수 후보 중 하나라도 존재하는지 검사하려면 후보별 오탐률이 매우 낮아야 하므로 이 정확도로는 전체 체크메이트 판별에 사용할 수 없다. 개발 단계에서 실패해 평가 호출은 하지 않았다.

실제 호출 함수는 두 개다. `infer_mate(fen)`은 top-1 경로, `infer_mate_beam(fen)`은 `64칸 Choice → Jev top-10 재선택 → Jev 레이어 검증` 전체 경로다. 둘 다 참조 정답을 받지 않고 `{"mate", "escape", "proposals", "stages"}`를 반환한다. 현재 평가 성능상 제품 판정기로 쓰면 안 되며, Jev-only 한계 실험 구현이다.

결과 파일은 `results_jev_escape_choice_{development,evaluation}.json`, `results_jev_escape_beam_{development,evaluation}.json`, `results_jev_escape_verify_development.json`, `results_jev_escape_verify_{development,evaluation}_beam.json`, `results_jev_move_validator_development.json`이다. 관련 검증은 `.venv/bin/pytest chess/test_jev_escape_choice.py chess/test_jev_escape_beam.py chess/test_jev_escape_verify.py chess/test_jev_move_validator.py -q`다.

## Stockfish + Jev 실제 대결 연결 검사 (초기 완료 기록)

이 절은 기존 완료본의 설정과 관측값이다. 이후 발견한 엔진 종류 변수 덮어쓰기 오류는 2026-09-22 수정했고, 실제 Stockfish 두 판 각 3착수 및 회귀 테스트로 실행을 확인했다.

초기 `jev_engine_match.py` 실행은 같은 Stockfish 19 두 프로세스를 사용했다. Sunfish의 UCI 옵션에는 MultiPV가 없어서 후보 점수 비교가 가능한 Stockfish를 이 실험에 사용했다. 양쪽 모두 한 수당 요청 예산 5,000노드, MultiPV 3, Threads 1, Hash 16MB이며 매 수 해시를 비운다. 엔진 출력의 마지막 **완성된 동일 깊이 MultiPV 묶음**을 사용하고, 탐색이 중단되어 일부만 갱신된 목록은 사용하지 않는다. 기록된 실제 노드 수는 요청 예산을 조금 초과할 수 있다.

대조군은 1순위 후보를 그대로 둔다. Jev 쪽은 최고 점수와 35cp 이내인 후보가 둘 이상이면 그 좌표만 Choice로 고르게 한다. 메이트 점수이거나 비교 가능한 후보가 하나뿐이면 엔진 수를 유지한다. 양쪽의 후보 탐색 작업도 동일하며, Jev 쪽에 추가 엔진 탐색은 없다. 다만 **Jev API 시간이 추가되므로 동일 시간 대결은 아니다.**

API state에는 현재 좌표별 기물, 착수 색, 캐슬링 권리, 앙파상 칸만 있다. criteria는 섞인 UCI 좌표와 null 설명이다. 엔진 점수·순위·원래 선택·예상 수순·체크/메이트 라벨은 전송하지 않는다. 전체 실제 요청과 응답, 사후 엔진 후보 점수, 선택 변경, 실제 노드 수와 API 지연을 JSON에 기록한다. 엔진이 후보를 추렸다는 보조는 있으므로 이 검사는 Jev 단독 체스 능력 검사가 아니다.

```sh
# output은 기존 증거 파일을 덮어쓰지 않도록 새 이름을 지정한다.
op-away run op run --env-file=chess/.env.tpl -- .venv/bin/python chess/jev_engine_match.py \
  --output chess/matches/jev-next --nodes 5000 --margin 35 --max-plies 400
.venv/bin/pytest chess/test_jev_engine_match.py -q
```

## 무작위 대조군과 약한 기본 엔진 (2026-09-21)

위 10판(3–7)만으로는 "Jev가 해를 끼쳤는지"와 "엔진 1순위를 흔든 것 자체가 손해인지"를 구분할 수 없다. 세 가지를 추가했다.

1. **무작위 대조군.** `jev_engine_match.py --selector random`은 Jev가 받았을 것과 같은 후보 목록에서 시드 고정 균등 무작위로 하나를 고른다. API 호출은 없고 기록은 `random_control` 필드에 남으며 `jev`는 null이므로 아레나에서 `Jev 비활성`으로 표시된다.
2. **약한 기본 엔진.** `weak_engine.py`는 재료 + 작은 위치 보너스, 깊이 2 네가맥스, UCI 문자열 동점 처리의 결정론적 엔진이다. Stockfish와 다른 후보 분포에서 선택자 효과를 시험하기 위한 별도 기반이다. `--base weak`로 같은 대국 스크립트에 연결되고, 후보는 상위 3개 중 자체 단위 30 이내다.
3. **사후 심판.** `referee.py`는 모든 선택 시점의 부모 국면을 Stockfish 20만 노드·`root_moves`=후보 목록·MultiPV로 한 번에 채점한다. 모든 후보가 같은 깊이에서 착수자 관점 점수를 받으며, 대국이 끝난 뒤에만 실행되고 Jev에게 전달되지 않는다. `arms_summary.py`가 네 조건을 합친다. 메이트 점수(±10000)가 평균을 지배하지 않도록 ±1000cp로 잘라 계산한다.


## 100판 대국: 무노이즈 조건의 관측값 (2026-09-22)

`make_openings.py`는 약한 깊이 2 엔진의 상위 3개 중 시드 무작위로 6착수를 골라 오프닝을 생성했다. Stockfish 10만 노드 평가 ±100cp 이내의 서로 다른 국면 50개를 남겼다(75회 시도). 각 오프닝에서 흑백을 바꿔 두 판씩 둔다. 오프닝은 이 약한 엔진이 생성한 표본이고, 표준 오프닝 전체를 대표하지 않는다. Stockfish의 표본 선별 점수는 Jev 입력에 포함되지 않는다.

## 확신 문턱: 관측 결과와 미확인 원인

`--min-confidence`보다 낮은 Jev 응답은 원문과 `jev_move`·`gated`로 보존하고, 실제로는 엔진 1순위를 둔다. 호출 자체를 생략하지 않으므로 이 옵션만으로 API 비용이 줄지는 않는다. confidence는 선택지 확률 분포에서 유도되는 값이며, 체스 승률이나 수의 객관적 우수성을 직접 뜻하지 않는다. 문턱의 효용은 별도로 평가해야 한다.

`--pairs N`은 오프닝 파일의 앞 N개를 사용하는 시범 실행 옵션이다. 파일에 있는 오프닝 수를 늘리는 옵션은 아니다. `--openings`로 별도 오프닝 묶음을 지정할 수 있다.

| 단독 엔진 | 첫 세트 | 5 | 90 | 5 | 50.0% |

새 오프닝은 `openings-50b.json`(생성 시드 20260922, 첫 세트와 국면 1개 중복), 12착수 세트는 `openings-50-12ply.json`이다. confidence ≥0.4 두 세트 합산은 24승 163무 13패(52.75%), 무작위는 24승 139무 37패(46.75%)다. 문턱 조건의 실제 변경은 각각 148·146회였다. 그러나 **개입 빈도, 개입 시점, 선택 내용이 동시에 달라졌으므로 개선 원인을 분리하지 못했다.** 빈도를 맞춘 무작위 게이트와 별도 평가 표본이 필요하다. 문턱 선택에 사용한 표본에서 다시 성능을 주장하지 않는다.

confidence ≥0.4 대 깊이4의 시범 10판은 0승 3무 7패였다. 작은 시범 결과로 깊이별 효과나 confidence의 유효성·무효를 일반화하지 않는다.

기록은 `matches/d2jevc02-*`, `d2jevc04-*`, `d2plain-vs-d2-100*`, `d2rand-vs-d2-100b`다. API 사용은 confidence ≥0.2 깊이2 100판 1,996회·1,431,580토큰, 깊이4 10판 198회·136,264토큰, confidence ≥0.4 첫 10판 185회·132,711토큰, 첫 100판 1,884회·1,353,866토큰, 새 세트 100판 1,950회·1,388,341토큰이다.

### 현재 노이즈의 정확한 정의

`weak_engine.candidates()`가 **먼저 상위 3개로 자르고**, `add_noise()`가 그 3개에 정수 균등 노이즈 ±N을 더해 재정렬한다. 모든 합법 수에 노이즈를 넣는 구현이 아니며, 정확한 동점만 깨는 구현도 아니다. UCI순으로 미리 제외된 동점 후보는 다시 들어오지 않는다. `--noise N`은 기본적으로 양쪽에 적용하고, `--opponent-noise 0`이면 단독 상대는 무노이즈다. 엔진 평가에는 재료뿐 아니라 작은 위치 보너스도 있다.

후보 생성 순서를 변경하면 다른 실험 조건이므로 기존 결과와 합치지 않는다. 아래 결과는 현 구현과 하나의 오프닝·시드 체계에 한정된다.

### 반복 무승부가 얼마나 줄었는가

Jev 없이 단독 엔진끼리 둔 동일한 50개 오프닝·흑백 교대 100판을 비교했다.

| 지표 / 각 100판 | 무노이즈 | 양쪽 ±10 |
|---|---:|---:|
| 삼중 반복 무승부 | 90 | 57 |
| 체크메이트로 승패 결정 | 10 | 43 |
| 오프닝 이후 30착수 이내 반복 무승부 | 52 | 7 |
| 위 조기 반복 중 잡힌 기물도 없는 판 | 40 | 6 |
| 대국 시작부터 60착수 이내 반복 무승부 | 68 | 29 |
| 종료 시 재료 차이 ≥300인 반복 무승부 | 20 | 22 |

**이 표본에서 초반 반복은 크게 줄었고, 실제 승패가 난 대국도 늘었다.** 다만 조기 반복이 모두 결판으로 바뀐 것은 아니다. 기존 조기 반복 52판을 같은 오프닝·색으로 대응시키면, 노이즈 후 **17판은 체크메이트, 29판은 더 늦은 반복 무승부, 6판은 여전히 조기 반복**이었다. 전체로는 기존 반복 90판 중 36판이 체크메이트로 바뀌고, 기존 체크메이트 10판 중 3판이 반복으로 바뀌어 순감소가 33판이다.

단위를 구분한다. `plies`는 6착수 오프닝 **이후의 한쪽 착수 횟수**다. 위 52→7은 30 ply(양쪽 15수 분량)를 기준으로 한 값이며, 대국 시작부터 양쪽 30수 이내라는 뜻이 아니다. 후자의 기준인 총 60 ply로 세면 68→29다.

재료 차이는 폰=100, 나이트=300, 비숍=300, 룩=500, 퀸=900으로 계산한 양쪽 합계의 절댓값이다. **재료 차이 ≥300은 강제승이 있거나 실제로 기물 한 개가 순수하게 더 있다는 판정이 아니다.** 20→22라는 집계만으로 반복의 원인, 노이즈로 해결 불가능함, 특정 반복 회피 구현의 필요성을 확정하지 않는다. 이 기준은 `weak_engine.py`의 나이트=320·비숍=330 평가와도 구분한다.

양쪽 ±30 조건은 22승 62무 16패였고, 오프닝 이후 30착수 이내 반복은 6판이었다. ±10보다 노이즈를 키운다고 전체 무승부가 단조롭게 감소한 것은 아니다.

### 노이즈가 엔진을 약하게 만드는가

한쪽만 노이즈를 넣고 무노이즈 단독 상대와 비교했다. 각 100판, 동일 오프닝 50쌍이다. 95% 구간은 오프닝 쌍을 단위로 100,000회 재표집한 percentile bootstrap이며 시드는 20260922다.

| 노이즈 쪽 대 무노이즈 단독 | 승 | 무 | 패 | 점수율 | 95% 구간 |
|---|---:|---:|---:|---:|---:|
| ±10 | 10 | 76 | 14 | 48.0% | 43.0~53.0% |
| ±30 | 20 | 65 | 15 | 52.5% | 46.0~58.5% |

이번 표본에서는 강도 변화의 방향이 확정되지 않았다. ±10 조건에서는 몇 %p 수준의 손실도 여전히 구간 안에 있으므로, 성능 손실이 없다는 동등성·비열등성 주장을 하지 않는다. 두 실험은 Jev를 사용하지 않았다. 기록: `d2plain-noise10-vs-d2plain-100`, `d2plain-noise30-vs-d2plain-100`.

| Jev | 24 | 57 | 19 | 52.5% | 2,466 / 1,496 |
| Jev confidence ≥0.4 | 23 | 63 | 14 | 54.5% | 2,592 / 238 |

같은 오프닝에서 두 색의 점수를 평균하고 조건 차이를 계산한 뒤, 그 오프닝 50개를 통째로 재표집했다. 아래는 조건 간 직접 비교의 탐색적 95% 구간이다. 다중 비교 보정과 여러 시드의 반복 실행 변동은 포함하지 않는다.

| 비교 | 점수율 차이 | 95% 구간 |
|---|---:|---:|
| Jev − 무작위 | +2.0%p | −7.0~+10.5%p |
| Jev ≥0.4 − 무작위 | +4.0%p | −4.5~+12.5%p |
| Jev − 단독 | +5.0%p | −4.5~+14.5%p |
| Jev ≥0.4 − 단독 | +7.0%p | −0.5~+14.5%p |

**Jev의 대국 점수 개선은 미확정이다. 동등함이나 무효도 입증되지 않았다.** 각 조건의 50% 대비 쌍 부호검정은 Jev와 무작위의 직접 비교 검정이 아니다. 무승부 감소는 Jev 없이 단독 엔진끼리도 나타나므로 그 환경 개선을 Jev의 효과로 세지 않는다. 필요한 대국 수는 검출할 차이·관측 분산·검정력·중단 규칙으로 정하며 특정 판 수만으로 결론을 보장하지 않는다.

기록: `matches/d2plain-vs-d2-100-noise10`, `d2rand-vs-d2-100-noise10`, `d2jev-vs-d2-100-noise10`, `d2jevc04-vs-d2-100-noise10`. Jev API 사용량은 문턱 없음 1,721,225토큰, 문턱 0.4는 1,812,445토큰이다.

## 개입 빈도를 맞춘 무작위 대조군: 탐색적 100판

개입 횟수 감소만으로 confidence 문턱 조건의 결과를 설명할 수 있는지 비교하기 위해 `--random-intervention-probability`를 추가했다. 이 옵션은 `--selector random`에서만 사용한다. 선택 가능한 후보가 둘 이상인 착수마다 독립적으로 확률 q로 엔진 수를 바꾸며, 바꿀 때는 엔진 1순위를 제외한 나머지 후보에서 균등 선택한다. 나머지 경우에는 엔진 수를 그대로 둔다. 옵션을 생략하면 기존의 전체 후보 균등 무작위 동작이 유지된다.

q는 실행 전에 기존 confidence ≥0.4 Jev 기록의 `238 / 2592 = 0.09182098765432099`로 고정했다. 환경은 기존 상위 3개 후보 노이즈 ±10·양쪽 깊이2·마진30·50개 오프닝·시드73419로 유지했다. 정확한 개입 횟수나 방문 국면을 같게 하는 것이 아니라 **선택 가능한 착수당 기대 개입 확률**을 맞춘 것이다. 새 결과를 본 뒤 q를 재조정하지 않았다.

| 각 100판 | 승 | 무 | 패 | 점수율 | 실제 변경 / 선택 가능 착수 |
|---|---:|---:|---:|---:|---:|
| 드문 무작위 개입 (새 실행) | 20 | 64 | 16 | 52.0% | 222 / 2,472 (8.98%) |
| Jev confidence ≥0.4 (기존 기록) | 23 | 63 | 14 | 54.5% | 238 / 2,592 (9.18%) |

같은 오프닝끼리 비교한 Jev−드문 무작위 차이는 **+2.5%p, 95% 구간 −5.0~+10.5%p**다. 드문 무작위−단독은 +4.5%p [−3.0, +12.5], 드문 무작위−기존 무작위는 +1.5%p [−7.0, +9.5]다. 모두 오프닝 단위 100,000회 bootstrap(시드20260922)이며 탐색적 구간이다. 이 결과로 Jev와 무작위의 동등함, 혹은 개입을 줄이면 유리하다는 원인을 확정하지 않는다.

이 비교는 이미 살펴본 오프닝과 기존 Jev 데이터를 재사용한 진단이다. 새로운 평가 세트의 확증 실험이 아니며, 선택 내용과 개입 시점의 효과를 서로 분리한 것도 아니다. 다음 평가에서는 q와 confidence 문턱을 고정하고 새 오프닝·시드를 쓰며, Jev−드문 무작위 차이를 주 비교로 삼는다. 단독 엔진은 기준선으로 함께 측정한다. 반복 회피나 노이즈 적용 범위 변경은 이 비교와 분리한다.

새 API 호출·토큰은 0이다. 모든 100판이 완료됐고 6,557착수, 2,472번의 난수 게이트·선택, 종료 결과를 재검증했다. Stockfish 실행 오류 수정과 희소 개입 제어를 포함한 관련 테스트 28개가 통과했다.

기록: `matches/d2sparserand-vs-d2-100-noise10-audit01`의 JSON·PGN·개별 로그. 실행 전 조건과 소스 해시는 `reports/sparse-random-audit01-protocol.json`, 재분석은 `reports/analyze_sparse_random.py`, 결과는 `reports/sparse-random-audit01-analysis.json`에 있다.

```sh
.venv/bin/python chess/ladder_batch.py --name sparse-next --selector random \
  --depth 2 --opponent-depth 2 --noise 10 --opponent-noise 10 \
```

## 반사실 재현의 용도와 제한

`counterfactual_replay.py`는 선택자가 엔진 1순위와 다른 수를 제안한 시점에서 두 갈래를 만든 뒤, 이후 양쪽을 **Jev 없는 단독 엔진**으로 진행시킨다. 이는 그 후속 정책에 조건부인 한 수의 결과 비교다. 강한 심판의 후보 평가와 다른 질문을 측정한다.

저장된 무노이즈 Jev 결과의 관측값은 다음과 같다. 결정들은 같은 판 안에서 상관되므로 개별 결정을 독립으로 본 신뢰구간이나 서로 다른 정책의 고확신 표본 합산을 성능 결론에 사용하지 않는다.

| 조건 | 실제 변경 수 | 결과 개선 / 동일 / 악화 | 변경당 평균 점수 차이 |
|---|---:|---:|---:|
| Jev 문턱 없음 | 1,178 | 148 / 880 / 150 | −0.002 |
| confidence ≥0.4 첫 세트 | 148 | 25 / 105 / 18 | +0.020 |
| confidence ≥0.4 새 세트 | 146 | 21 / 109 / 16 | +0.017 |

판마다 이 차이를 합쳐 실제 결과 차이가 나오는 것은 기준 정책의 가치 차이에서 중간 항이 소거되는 항등식이다. 따라서 그 일치로 **이후 개입의 상호작용이 없음을 증명할 수 없다.** 심판이 나쁘게 평가한 수가 이 재현에서는 좋은 결과를 냈다면, 서로 다른 후속 대응에서 결과가 달랐다는 사례로 기록한다.

현재 구현은 노이즈·시드를 재현 대국으로 전달하지 않는다. 노이즈 조건에 그대로 적용하면 실제 경기와 다른 환경을 평가하므로 사용할 수 없다. 또한 400착수 미완료를 0.5로 처리하므로 경기 코드의 `*`와 일치시키는 수정이 필요하다. 확인한 기존 Jev 반사실 파일 3개에는 미완료 갈래가 없었다.

## 다음 실행 전에 고정할 항목

- 엔진 코드 버전, 후보 생성 순서, 입력 정보, 오프닝·시드, 주 지표와 중단 규칙을 고정한다. Jev 입력에는 현재 수순·반복 이력이 없다.
- confidence 효과의 다음 평가는 위에서 추가한 드문 무작위 대조군과 새로운 평가 표본으로 진행한다. q·문턱을 재조정하지 않고 환경 개선과 Jev 효과를 분리한다.
- 노이즈를 전체 합법 수에 적용하거나 반복 회피를 넣으면 새 조건으로 기록하고 대조군도 다시 측정한다. 반복 회피의 효과는 아직 측정하지 않았다.
- Stockfish의 엔진 종류 `base`와 기준 착수 `base_move`를 분리한 수정은 완료됐다. 엔진 경로가 착수 사이에 유지되는 회귀 테스트와 실제 Stockfish 두 판 각 3착수로 확인했다. 이 수정은 약한 엔진의 기존 선택 정책을 바꾸지 않는다.

## 탐색 예산을 Jev가 배분할 수 있는가 (2026-09-21)

앞 절까지 Jev가 맡은 자리는 항상 **근접 후보 중 하나 고르기**였다. 이 절을 쓴 9/21 오전에는 그 효과를 Stockfish 심판 기준 결정당 10cp 안팎으로 봤다. 같은 날 밤 엔진과 다르게 고른 결정을 깊이 2끼리 끝까지 둬 보니 결정당 순효과가 Jev −0.0021(1,178건), 무작위 −0.0022(1,395건)로 같은 값이었다(위 "반사실 재현의 용도와 제한", `matches/d2rand-vs-d2-100.counterfactual.json`). 그래서 10cp는 이 상대에게 실제로 이긴 몫이 아니라 심판 점수로 남는다. 어느 쪽이든 두 수 더 보는 엔진과의 격차는 컸다. 깊이 4 상대 100판에서 단독은 11.5%, Jev는 5.5%였다. 그래서 자리를 바꿨다. 수를 고르는 대신 **어느 국면에 깊이를 쓸지** 고르게 하면, 효과가 cp가 아니라 탐색 깊이로 증폭될 수 있다.

대국을 돌리기 전에 판별력만 먼저 쟀다. Jev가 우연을 못 넘으면 대국은 돌릴 이유가 없다.

### 1단계: 정답 만들기 (API 0회)

`depth_gap.py`는 기록된 100판(`d2plain-vs-d4-100`, `d2rand-vs-d2-100`)에서 깊이 2 쪽이 실제로 마주한 국면 7,990개를 FEN으로 중복 제거해 7,396개를 만들고 400개를 표본했다. 국면마다 모든 루트 수를 깊이 4로 다시 채점해

    gap = raw4(깊이 4의 최선수) − raw4(깊이 2가 고른 수)

를 약한 엔진 자체 단위로 기록한다. `referee.py`와 같은 ±1000 클립을 쓴다. 소요 368초.

| | |
|---|---:|
| gap이 30단위 이상인 국면 | 41.8% |
| 평균 gap | 81단위 |
| 깊이 4가 수를 바꾼 국면 | 67.8% |
| 그중 gap이 0인 것 | 52개 |
| 깊이 4 / 깊이 2 시간비 | 55배 |

**라벨을 "수가 바뀌었나"로 잡으면 안 된다.** 수가 바뀐 271국면 중 52개는 gap이 0이다. `rank_moves`가 정확한 동점을 UCI 알파벳순으로 깨기 때문이고, 그 52개는 체스가 아니라 정렬이다.

### 2단계: 코드 기준선

Jev를 재려면 넘어야 할 선이 있어야 한다. 국면마다 코드로 셀 수 있는 값을 전부 순위로 써 보고 가장 잘 맞히는 것을 기준선으로 뒀다. 전술 신호(잡을 말, 무방비 기물, 체크)는 전부 우연이거나 그 아래이고 합치면 AUC 0.374로 동전보다 나쁘다. 가장 잘 맞히는 것은 **기물 수 + 합법수**로 AUC 0.739, 상위 10%에서 정밀도 0.85다. 합법수 구간을 고정해도 기물 수는 살아남고(구간별 AUC 0.56~0.78) gap을 합법수로 나눠도 상관이 0.393으로 같으므로 수가 많아 생기는 기계적 부산물은 아니다.

이 기준선 자체는 결과가 아니라 눈금이다 — 대국 진행 정도에 가깝고, 초반에 더 오래 생각하는 것은 엔진이 원래 하는 일이다. 아래 Jev 숫자를 읽기 위해서만 쓴다.

### 3단계: Jev 판별력 (400요청, AUC 0.5가 우연)

`budget_judge.py`는 국면당 요청 하나로 Noul 셋과 Score 둘을 묻는다. state에는 기물의 색·종류·좌표와 숫자 좌표만 있고(체크 감지 37/40을 낸 표현), 이동 규칙은 질문 본문에 쓴다. 엔진 점수·후보 목록·gap은 보내지 않는다. 채점은 같은 라벨에 대한 순위로 한다.

아래 표는 다음 절의 길이 고정 실행(`--every-square`, `judge-02-every-square.json`)이다. 두 표현 중 교란이 제거된 쪽이고, 말만 적은 첫 실행(`judge-01.json`)과 결론은 같다(두 값의 차이는 다음 절 표).

| 순위 기준 | AUC | 구간 안 AUC | 상위 10% 정밀도 | 상위 10% gap 회수 |
|---|---:|---:|---:|---:|
| 오라클 (상한) | 1.000 | 1.000 | 1.00 | 0.472 |
| 코드 기준선 (2단계) | 0.739 | 0.620 | 0.88 | 0.211 |
| Jev: 복잡한가 | 0.507 | 0.531 | 0.30 | 0.077 |
| Jev: 함정인가 | 0.387 | 0.493 | 0.25 | 0.057 |
| Jev: 무방비 말이 있는가 | 0.374 | 0.479 | 0.23 | 0.052 |
| Jev: 미해결인가 | 0.341 | 0.473 | 0.25 | 0.076 |
| Jev: 날카로운가 | 0.314 | 0.468 | 0.17 | 0.068 |
| Jev 복잡도 + 기준선 | 0.683 | 0.550 | 0.65 | 0.157 |
| Jev 날카로움 + 기준선 | 0.581 | 0.512 | 0.50 | 0.120 |

**이 다섯 질문으로는 못 고른다.** 가장 나은 질문이 우연이고 나머지 넷은 그 아래다. **이것을 Jev의 한계로 적었다면 틀린 기록이 됐을 것이다** — 4단계 참고. 기물 수 구간 안에서도 0.47~0.53으로 우연이다. 그리고 약한 양성이 아니다. 기준선 순위에 Jev 순위를 더하면 0.739가 0.683으로, 날카로움을 더하면 0.581로 **떨어진다**. 실행당 400요청·26초, 지연 중앙값 243~255ms, 입력 토큰은 말만 적을 때 608,522, 64칸 전부 적을 때 862,106이다. 설계대로 여기서 멈추고 대국(2단계)에 Jev 팔을 만들지 않았다.

### 4단계: 문구 하나가 0.507과 0.708을 갈랐다

3단계를 결론으로 적기 전에, 질문 하나하나가 **글자 그대로 물은 것**을 코드로 세어 채점했다. 답이 맞는지와 그 답이 과제에 쓸모 있는지는 다른 문제이기 때문이다.

| 질문 ↔ 코드로 센 그 질문의 정답 | AUC (말만) | AUC (64칸) |
|---|---:|---:|
| 날카로운가 ↔ 지금 체크인가 | 0.820 | 0.809 |
| 미해결인가 ↔ 320 이상짜리 잡기가 있나 | 0.696 | 0.713 |
| 날카로운가 ↔ 잡기+체크가 중앙값보다 많나 | 0.622 | 0.629 |
| 무방비 말이 있나 ↔ 실제로 무방비 말이 있나 | 0.599 | 0.577 |
| 미해결인가 ↔ 잡는 수가 하나라도 있나 | 0.577 | 0.581 |

전술 질문 넷은 알아듣고 답한 것이다. 근거가 없는 것은 `complexity` 하나뿐이었고(자기 최상위 레벨이 "말이 많이 얽혀 있다"인데 기물 수와 −0.013), 그래서 남은 용의자는 모델이 아니라 문구였다.

`budget_count_probe.py`는 같은 400국면·같은 길이 고정 state에 셀 수 있는 것을 직접 묻는다("몇 개나 남았나"). 정답은 `len(piece_map)` 한 줄이다. Jev는 AUC 0.995·ρ 0.953으로 거의 정확히 답하고, 그 답을 그대로 gap 순위로 쓰면 **AUC 0.708**이 된다. 3단계에서 보고한 0.507이 아니다. 예산 30%에서는 코드 기준선의 0.414와 Jev의 0.410으로 사실상 동률이다. 400요청·748,506입력토큰·26초.

**교훈은 체스가 아니라 문구에 있다.** "얼마나 복잡한가" 같은 사람 말로 물으면 우연이 나오고, 셀 수 있는 것을 직접 물으면 답이 나온다. 이 저장소에서 같은 일이 반복됐다 — 체크 감지 22/40 → 37/40, 슬라이딩 퍼즐의 힌트 한 문장. **null을 모델의 한계로 적기 전에 문구부터 바꿔 보고, 각 질문을 그 질문의 정답으로 먼저 채점한다.** 이 검사가 넷을 무죄로 하고 하나를 유죄로 했다.

Jev가 이 자리에서 대국에 못 들어가는 이유도 바뀐다. 못 해서가 아니라, 하는 일이 결국 말을 세는 것이라 코드 한 줄과 같은 신호를 더 비싸게 내놓기 때문이다.

### 왜 뒤집혔는가

원인은 체스를 못 읽어서가 아니다. Jev의 답은 **판에 남은 말 개수와 반대로 움직인다**.

| | 말만 적은 state | 64칸 전부 적은 state |
|---|---:|---:|
| 날카로운가 ↔ 기물 수 | −0.800 | −0.767 |
| 미해결인가 ↔ 기물 수 | −0.655 | −0.649 |
| 함정인가 ↔ 기물 수 | −0.537 | −0.516 |
| 복잡한가 ↔ 기물 수 | −0.167 | **−0.013** |
| 날카로운가 ↔ 코드 전술 점수 | 0.460 | 0.462 |
| 최고 AUC | 0.482 | 0.507 |

라벨도 기물 수와 같은 방향(+0.395)이므로, 판의 참에 반대로 붙은 답은 라벨에도 반대로 붙는다.

이것은 **지각의 실패가 아니다.** 4단계에서 보듯 Jev는 같은 state에서 판이 꽉 찼다는 것을 ρ 0.95로 읽는다. 꽉 찬 줄 알면서도 꽉 찬 판을 덜 날카롭다고 답한다는 뜻이고, 그래서 이건 못 보는 문제가 아니라 판단의 방향 문제다. 코드 전술 점수도 기물 수와 −0.29로 같은 방향이지만 Jev의 −0.80은 그보다 훨씬 크다.

**길이 때문도 아니다.** 말이 적으면 요청도 짧아지므로, 빈 칸까지 64칸을 모두 적어 길이를 고정하고 같은 400국면을 다시 돌렸다(입력 608,522 → 862,106토큰, 국면별 길이 평탄). 상관은 −0.800에서 −0.767로 거의 그대로다. 예외는 `complexity` 하나로, −0.167이 −0.013이 되어 그 질문의 약한 역전만 길이 효과였다. 길이를 고정해도 그 질문은 정보가 없을 뿐(AUC 0.507) 방향이 생기지는 않는다.

**읽기는 읽는다.** Jev의 "날카로운가"는 코드의 전술 점수와 ρ 0.46으로 같이 움직이고, 기물 수 4구간으로 나눠도 구간마다 0.31~0.38로 유지된다. 두 표현에서 모두 같다. 좌표 목록에서 잡는 수와 위협을 등급 있는 신호로 읽고 있다는 뜻이다. 앞의 깊이 1 실험은 "되잡히는 수를 좌표 목록에서 알아보지 못한다"로 끝났지만, 그쪽은 Jev가 수를 **고르는가**였고 이쪽은 등급 매긴 답이 코드 신호와 **같이 움직이는가**다. 과제도 측정도 다르므로 그 결론을 뒤집는 것이 아니라 다른 각도의 결과로 읽어야 한다. 다만 이 질문의 답은 과제에 쓸 수 없다. 두 수 더 보는 것이 값어치를 하는 쪽과 반대로 붙기 때문이고, 그래서 쓸 수 있었던 것은 4단계의 직접 묻는 질문 쪽이다.

### 해석의 한계

- 국면 400개는 전부 **깊이 2 엔진이 둔 판**에서 나왔다. 깊이 2끼리는 70%가 반복 무승부였으므로 기준선의 일부는 "깊이 2 엔진이 단순해진 판으로 흘러가 아무것도 중요하지 않게 된다"일 수 있다. 다른 강도의 엔진이 둔 판에서는 다시 재야 한다.
- **같은 예산 비교는 이 엔진으로 성립하지 않는다.** 깊이 4는 깊이 2의 55배이므로 10%만 깊게 봐도 총비용이 6.4배다. 짝수 깊이만 쓰기로 했으므로 중간 단계가 없어 예산을 맞출 방법이 없다. 이 실험이 답한 것은 "고정 깊이 2보다 센가"가 아니라 "쓸 수 있는 10%를 어디에 쓸지 고를 수 있는가"뿐이다. 비용당으로 보면 고르는 값어치는 크다 — 항상 깊이 4는 55배에 이득 100%, 오라클이 고른 10%는 6.4배에 47%로 비용 1배당 4배 낫다.
- 프롬프트 2종, 질문 8종, 약한 엔진 정의 1종, 임계값 30 하나다. 기준선 0.739는 같은 400국면에서 고른 조합이므로 별도 표본의 값이 아니고, 4단계의 0.708도 같은 400국면이다. 문구 하나를 바꿔 얻은 값이므로 **다른 문구를 더 찾으면 더 올라갈 수 있다**는 뜻이기도 하다.
- 상관과 AUC는 국면을 독립 표본으로 본 값이고 실제로는 100판 안에 뭉쳐 있으므로 낙관적이다.

### 다음

대국(2단계)에 Jev 팔은 만들지 않는다. 남는 질문 둘은 체스가 아니라 문구와 판단 방향에 관한 것이라 `experiments/` 쪽 측정감이다.

- **Jev는 왜 꽉 찬 판을 덜 날카롭다고 보는가.** 판의 참은 정확히 읽으면서(ρ 0.95) 날카로움 판단만 반대로 붙는다(−0.77). 지각이 아니라 판단의 방향 문제다.
- **어떤 문구가 먹히는가.** 여기서는 0.507과 0.708을 갈랐고, 체크 감지에서는 22/40과 37/40을 갈랐다. 지금까지의 패턴은 "셀 수 있는 것을 직접 물으면 먹히고, 사람이 쓰는 추상어로 물으면 안 먹힌다"인데, 이건 체스 밖에서 재는 편이 낫다.

```sh
uv run python chess/depth_gap.py --sample 400                                  # 라벨, 키 없이
op-away run op run --env-file=chess/.env.tpl -- uv run python chess/budget_judge.py --output chess/budget/judge-next.json
op-away run op run --env-file=chess/.env.tpl -- uv run python chess/budget_judge.py --every-square --output chess/budget/judge-next-es.json
op-away run op run --env-file=chess/.env.tpl -- uv run python chess/budget_count_probe.py --output chess/budget/count-next.json
uv run pytest chess/test_depth_gap.py chess/test_budget_judge.py -q
```

증거는 `budget/depth-gap.json`(라벨과 코드 신호), `budget/judge-01.json`(말만 적은 state), `budget/judge-02-every-square.json`(길이 고정), `budget/count-probe-01.json`(판의 참을 직접 물은 4단계)에 실제 요청·응답과 함께 보존한다. 이미 결과 파일이 있으면 덮어쓰지 않고 중단한다.
