# Jev 버그헌터

Python 파일을 던지면 함수마다 Jev에게 "버그 냄새가 나는가"를 묻고, 위험한 순서로 정렬해 돌려준다. 2026-09-19, `jev-1.13.0`.

버그를 **확정**하는 도구가 아니다. 정밀 검사(테스트·리뷰·정적 분석)를 **먼저 해야 할 함수를 빠르게 골라주는 감지기**다. 초파리가 다가오는 물체를 보고 반사적으로 도망가듯, Jev는 코드를 실행하지 못하는 System One 모델이라 "이 패턴이 소스에 보이는가"만 답한다. 그래서 질문은 전부 실행 없이 눈으로 확인 가능한 명제로 썼고, 깨끗한 함수에서는 거짓으로 읽히도록 다듬었다.

## 설계

함수 하나에 `sif.ask()` 요청 하나. 그 안에 질문 12개:

- **냄새 10개는 각각 Noul**(참/거짓 확률). 한 함수가 예외를 삼키면서 오프바이원일 수 있으므로 Choice로 하나만 고르게 하지 않고 냄새마다 독립적으로 묻는다. 임계값 0.5 이상이면 탐지.
- **심각도는 Score 하나.** `무해 → 사소 → 심각 → 치명` 위의 위치(0.0~3.0)를 반올림한다.
- **가장 유력한 종류는 Choice 하나.** 선택지 11개(없음 + 냄새 10개)에 설명으로 냄새 명제 전문을 붙였다. branches 실험에서 설명 없는 Choice가 약해졌으므로.
- 12개 질문은 병렬로 평가되고 서로의 답을 못 본다. 그래서 Choice가 고른 종류의 Noul이 낮을 수 있다. **정렬 키는 Noul 최댓값(`risk`), 동률이면 심각도.** Choice는 표시용.

상태는 `{"language", "file", "function", "source"}` 매핑으로 보낸다. 함수 추출은 `ast`로, 메서드와 중첩 함수도 각각 한 행이 된다.

| id | 이름 | Jev에게 묻는 명제 |
|---|---|---|
| none_unchecked | None 미검사 | None일 수 있는 값(Optional 인자, dict.get, re.match, find 결과 등)을 검사 없이 속성 접근·인덱싱·연산에 쓴다 |
| boundary | 경계 미처리 | 빈 입력, 길이 0, 마지막 인덱스, 음수 같은 경계 입력에서 잘못된 결과를 내거나 예외를 낸다 |
| off_by_one | 오프바이원 | range·슬라이스·비교 연산자에 하나 어긋난 경계가 있어 원소 하나를 빠뜨리거나 하나 더 본다 |
| swallowed_exception | 예외 삼킴 | except 절에서 예외를 잡은 뒤 로그·재발생·의미 있는 처리 없이 무시하거나 잘못된 기본값을 돌려준다 |
| resource_leak | 자원 누수 | 파일·소켓·커서·락을 열고 나서 예외나 조기 반환 경로에서 닫지 않는다 |
| mutable_default | 가변 기본값 | list·dict·set을 인자 기본값(`def f(x=[])`)으로 쓰고 그것을 변경하거나 돌려준다 |
| wrong_return | 반환 불일치 | 어떤 분기에서 반환을 빠뜨리거나, 다른 분기와 타입·의미가 다른 값을 돌려준다 |
| logic | 논리 오류 | 조건식·연산자·변수 이름이 의도와 어긋난다 (and/or 혼동, 반전된 비교, 덮어써진 결과) |
| type_mismatch | 타입 혼동 | str과 bytes, int와 str, float 동등 비교처럼 타입이 맞지 않는 값을 섞어 쓴다 |
| unsafe_input | 입력 신뢰 | 외부 입력(경로, SQL, 쉘 명령, HTML, eval 대상)을 검증이나 이스케이프 없이 그대로 쓴다 |

정확한 문구는 `hunter.py`의 `SMELLS`, `SEVERITY_INSTRUCTIONS`, `KINDS`.

## 실행

키는 1Password에서만 주입한다.

```sh
# 파일이나 디렉터리를 주루룩. 위험한 순서로 표
op run --env-file=<(echo 'TYPESAFE_API_KEY="op://Personal/typesafe jev key/credential"') \
  -- uv run python bug-hunter/hunt.py src/sif/core.py guardrail/

# 옵션: --top 10, --json(함수당 한 줄), --detail(냄새별 확률 전부), --threshold 0.6
# --dry-run이면 보낼 함수 목록과 요청 수만 찍고 API를 부르지 않는다
uv run python bug-hunter/hunt.py --dry-run src/

# 쌍둥이 샘플 24쌍 채점 → results.json
op run ... -- uv run python bug-hunter/run_samples.py
```

## 감시 모드 (영상용)

```sh
op run --env-file=<(echo 'TYPESAFE_API_KEY="op://Personal/typesafe jev key/credential"') \
  -- uv run python bug-hunter/watch.py src/sif/core.py        # http://localhost:3458
```

`watch.py`는 파일 mtime을 0.3초마다 보다가 저장이 감지되면 함수를 다시 자르고, **소스 해시가 바뀐 함수만** Jev에 보낸다. git과 무관하고 커밋 안 해도 된다. 변경 단위는 함수 본문이라 한 함수를 고치면 요청도 한 번. 같은 소스로 되돌리면 sif 캐시가 맞아서 0ms.

`panel.html`은 SSE(`/events`)로 받은 판정을 위험 순으로 그린다. 저장하면 화면이 1프레임 깜빡이고, 바뀐 함수는 2.5초 테두리가 남으며, 순위가 바뀌면 200ms 미끄러진다. 색은 임계값 0.5에서만 회색↔빨강으로 바뀐다(그라데이션 없음 — 반사 반응은 이진이어야 느낌이 산다). "소리 켜기"를 누르면 판정마다 틱 소리(빨강이면 높은 음). 우하단 카운터는 `functions · hot · changed · requests · 마지막 배치 시간`. 문법 오류 상태로 저장하면 마지막 판정을 유지하고 상단에 한 줄 띄운다.

연출 순서: 평온한 목록 → 한 함수에 버그 심고 저장 → 그 줄이 빨갛게 올라옴 → 몇 개 더 → Cmd+Z 저장 → 다시 내려감 → 카운터.

## 쌍둥이 샘플 결과

`samples.py`에 버그 함수와 그 버그만 고친 함수 24쌍(냄새당 2~3쌍). 한 줄이나 연산자 하나만 다르므로 이름·길이로는 구분할 수 없다. 두 쌍둥이는 같은 `file`·`function` 이름으로 보내고 소스만 다르다.

48호출. 첫 실행(아래 '배운 것'의 넓은 명제 버전)에서 입력 72,543 + 출력 14,593 토큰, latency 중앙값 285ms, p95 506ms. 아래 수치는 명제를 좁힌 뒤의 두 번째 실행.

| 지표 | 결과 |
|---|---|
| 버그 쌍둥이의 위험이 더 높음 | 21/24 |
| 버그 쌍둥이의 심각도가 더 높음 | 23/24 |
| 기대한 냄새가 버그 쪽에서 탐지 | 21/24 |
| 기대한 냄새가 고친 쪽에서도 탐지(오탐) | 0/24 |
| Choice가 기대한 냄새를 고름 | 19/24 |
| 고친 쪽 Choice가 "없음" | 15/24 |
| 평균 위험 | 버그 0.81 / 고침 0.41 |

실패한 3쌍은 전부 이유가 있다.

- `chunk` (0.24→0.30): `size <= 0` 검사를 뺀 게 버그 쌍둥이인데, 실제로는 `range(0, n, 0)`이 ValueError를 내므로 조용히 틀리지 않는다. 데이터셋 쪽이 약하다.
- `fetch_rows` (0.94→0.94): 커서 누수를 고쳤지만 두 쪽 다 `query`를 그대로 실행한다. Jev는 양쪽에 **입력 신뢰** 0.94를 줬고 Choice도 자원 누수 대신 입력 신뢰를 골랐다. 맞는 지적이다.
- `is_zero_balance` (0.17→0.18): `float == 0.0`을 못 봤다. 타입 혼동 명제에 "float 동등 비교"를 넣어도 놓친다. 이 냄새는 약하다.

Choice가 틀린 5쌍 중 위의 `chunk`·`fetch_rows`·`is_zero_balance`를 뺀 나머지: `pages_needed`는 오프바이원 대신 **경계 미처리**(올림 나눗셈 빠짐을 그렇게 읽음), `sum_first_n` 고친 쪽은 `values[i]`가 `n > len`이면 터지니 **경계 미처리**, `find_user`는 반환 불일치 대신 **논리 오류**(else에서 return). 다 틀린 말은 아니고 냄새 사이 경계가 겹치는 문제다.

## 실제 코드에서 배운 것

- 처음 `가변 기본값` 명제에 "호출 사이에 공유되는 상태를 변경한다"를 붙였더니 sif의 `configure`·`reset`·`_get_client` 같은 **의도적 모듈 싱글턴이 전부 0.9로 1위에 올라왔다.** 명제를 기본 인자 문제로만 좁혔더니 사라졌고 샘플 점수는 그대로였다. 명제 한 절이 순위를 통째로 바꾼다.
- 좁힌 뒤 sif+guardrail 35개 함수 중 0.5를 넘는 건 5개. `_truthy`(인자가 항상 str이라 오탐), `scale`·`_criteria`(둘 다 길이 검사를 하고 있는데도 경계 미처리; 경계를 **다루는** 코드와 **못 다루는** 코드를 구분 못 함), `screen`(`answers[...]` 직접 인덱싱), `_raw_answers`(주석 달린 의도적 bare except — 패턴으로는 맞다).
- 확률이 0.00/1.00으로 쏠리는 limits 실험과 달리 여기서는 0.1~0.97 사이에 고르게 퍼진다. 코드 명제는 문의 분류보다 애매해서 순위로 쓸 만한 해상도가 나온다.

## 한계

- Python만. `ast`로 함수를 자르므로 다른 언어는 추출기를 붙여야 한다.
- 함수 하나만 보고 판단한다. 호출자가 None을 절대 안 넘긴다는 사실은 모른다.
- 냄새 10개 밖의 버그(동시성, 성능, 잘못된 API 사용)는 안 보인다. 그런 건 명제를 추가하면 된다.
- 요청당 입력 약 1,500토큰. 큰 저장소는 `--dry-run`으로 요청 수를 먼저 보고 돌린다.
